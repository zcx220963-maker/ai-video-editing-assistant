### 0.1 第 4 项的疑问：**不需要调外部 API，一个 LLM API 就够——但只够一半**

你的原话是「我不想调外部 api，就一个 llm api 不够吗，opus5.5 不就是一个 api就可以做吗」。

答案是：**够，覆盖得了第③档；覆盖不了第④档。** 这不是选择问题，是两种东西的分界：

- Opus 5.5 在这一套里的角色是**产代码，不产像素**。画面由 Remotion 拿你写的 TSX 逐帧渲出来，
  所以「一个 API」确实撑得起一整条生产线。
- 代码能画的那四类（`SUBJECT_CHANNELS = rough / three / katex / vector`，见 `code_spec.py:1540`）
  **联网＝否、花钱＝否**：`three` 就是真 3D 场景，`vector` 就是矢量人物，`katex` 是公式，
  `rough` 是手绘斜纹。**3D 场景与真人矢量人物这两类，本来就在「代码自己画」这一档里，
  不是外部素材站的专属。**
- 外部素材站那四条腿（`wikimedia-commons` / `iconify` / `polyhaven` / `ambientcg`…）
  在合同 R13 §2 的结论里只对应**第②档的一个来源**，不是必经之路。它们今天是
  `STATE_PENDING`（探测过、没跑通），库里一行数据都没有——**这不影响任何一档的主路径**。
- 唯一的硬分界在第④档：**照片感、真实场景、电影感**。代码画不出「一张照片」——
  它能画出「很像照片的插画」，但那是第③档的产物。要真照片就必须有一个出图服务
  （或者一个外部图库），而那需要第二个 API。

所以：**第 4 项「外部素材站直接取图」不是一个必须补的洞**。它是一个可选来源，
属于第②档，而第②档今天已经有 132 件可检索的本地素材在跑（见第 3 节）。

## 1. ① 你上传的图能摆进某一镜 —— **已修好**（T65 索引腿）

### 病根

渲染侧只认一张表：

```
shots[].assets[].sha256  →  asset_library.get_by_sha  →  object_key  →  取字节投给渲染容器
```

而用户上传走的是 `materials` 表（归 owner、可删、能在素材册里看见）。
**两张表之间原来没有腿**：传完 `get_by_sha` 查不到 → 渲染前报「找不到这张图」。

### 落地

新增 `backend/agent_framework/asset_index.py`（唯一实现，约 160 行）：

| 判据 | 取值 | 为什么 |
|---|---|---|
| `object_key` | 原样指向 materials 那个对象 | 同一段字节在桶里存两份没有任何好处 |
| `source` | `user-upload` | 与 `imagegen` / `wikimedia-commons` / `iconify` 并列，四者互不相等 |
| `license` | `user-uploaded` | 权利由上传者声明，**不是 CC0** |
| `enabled` | `False` | `get_by_sha` 不看这一列（投递腿照旧），`search()` 看（别人的检索面看不见你的图） |
| 幂等 | 同 sha 只有一行 | `sha256` 上那条 UNIQUE 不是装饰 |
| 失败 | 只回空串，**绝不抛** | materials 行已写成，你在素材册里看得见这张图；两级保证不该用同一句话报 |

接在 `ingest_bytes` 里——那是**三条入料路径（前端 /upload、链接取料、Agent 工具）共用的
那一处**，所以一处接线三条路都通。散到各接口里写，迟早有一路漏掉，而漏掉的表现正是
「传了图却报找不到这张图」，排查的人会先去查渲染侧，方向从一开始就是错的。

### 顺手修掉一个真 bug

`objects.put` 原来只拦 `StorageUnavailable`。不够：MinIO 的 `ClientError` 未必都被包住，
内存替身落盘写文件会抛 `OSError`。**漏一种就足以让一次本来成功的上传在索引这一步炸掉**，
而用户在素材册里明明看得见那张图。改成拦 `Exception`，与模块自己的合同一致。

### 真库实测（`scripts/probe_t65_upload_index.py`，在 `creation-app` 里跑真 PG + 真 MinIO）

```
materials 行写成，sha256=dcf6b8a5…cd680
asset_library.get_by_sha 命中——渲染侧要的就是这一下
source='user-upload' / license='user-uploaded' / enabled=False
object_key 与 materials 那一个是同一个键（没存第二份字节）
按 object_key 取回的字节逐字节相同（75 vs 75）
search('probe') 看不见它
同一张图再传一次：asset_library 仍是同一行（UNIQUE 生效）
materials 那一层是新的一行（归属不同：两次上传各自可删）
收尾：删了 2 条 materials、1 条索引行；残留 0 行
── 14 条判据全过 ──
```

离线用例 `backend/tests/test_asset_index.py` **49 条全过**，含 D-红先两段
（`enabled=True` 时 `search` 看得见、`license` 可以是任意串 → 所以取值由模块钉死）。

### 还差的半边（T66 + 闸㉛）

「能摆进镜」与「**该不该**摆进镜」是两件事。已做的是使能半边：
`context.py` 给位图补了 `sha256=` / `ext=` 两段，并把附件段拆成三类
（位图 / 视频 / 音频），位图那一段写明「**能直接摆进某一镜**…把三键原样填进
`shots[].assets`…**但只有用户指名才能用**…也**不许凭记忆填一个 sha**」。

没做的是闸㉛（指名权的那道机器判据）。这里有一处**必须如实说明的偏差**：
R13 原文要的判据是「本次 run 的 `attachments`」，但 `attachments` **到不了 Storyline 进程**
（`grep attachments backend/storyline_server` 0 命中）。可行且今天会红的替代判据是会话域：

```
uploaded_shas  = storage.assets 里 source='user-upload' 的行（节点侧拿得到）
allowed_shas   = materials.list_visible(user_id, conv_id, kinds=("image",))
```

两个集合都 None → 未判；assets 里没有上传件 → 未判（「本片没用用户上传的图」）；
**有上传件但不在允许集合 → 打回**。

### T68：没配出图后端时，出图那条腿从正文里整条摘掉

`sections_for_plan` 加了 `imagegen_visible` 开关。没配后端时把 `imagegen` 从节点集里摘掉，
于是 `whiteboard-imagegen` 连同四块供给正文（`image-channel` / `asset-motion` /
`asset-parts` / `scale-safe`）**一起不注入**。

为什么不是「照发、让节点自己降级」：那一节的正文讲的是「出图腿的视觉规范」，
读者是「正在给某个镜头配图」的那个模型——而它这一轮调不到出图（`GenerateImageNode`
会回一条降级回执）。发出去等于教一条今天走不通的路，而且烧到第 9、10 镜才停下来问用户，
**正是那张四选项卡的根因**。

两条钉子：

- **默认 `True` ＝ 旧行为逐字相同**（不传开关与传 `True` 结果一致，四组计划都验了）。
  这一条是「新开关不许偷改旧行为」的回归钉子。
- **检索腿不受影响**：计划里还有 `search_illustration` 时供给正文照发。
  两条腿分别判，不是一刀切。

在 `agent.py` 的执行轮**现查** capability 再传进去，不缓存：密钥写在设置页、按用户失效，
「用户刚填好」与「重启服务」都能让同一台机器的读数翻过来——缓存的读数会把这台机器
**已经修好**的那段时间继续当坏的。

`backend/tests/test_t68_imagegen_visibility.py` **18 条全过**，含 D-红先一段
（开关被忽略时那一节就在结果里 → 第①条判据对它真红；判据分得开
「接了参数没接行为」这种最常见的假绿）。
