# 渲染前确认闭环 + 链路提速：设计说明

日期：2026-10-01
状态：已实现（本文件记录决策与实测证据）

---

## 1. 这一轮要解决的四个问题（来自用户原话）

1. **链路太慢**：转写、画面理解、编排渲染都慢。要求「不要影响最终效果」，
   且**首要确保任务链执行完整成功，再保证速度**。
2. **渲染前要让用户看到编排结果**：展示提取内容、分割结果、分镜、画面、声音的编排，
   用户决定「改」还是「直接渲染」；改则重做计划并再弹一次，**直到用户确认渲染为止**。
3. **模型不该替用户决定**：真机实例——用户说 90 秒，模型发现按 90 秒会截断最后一句金句，
   却直接截断、只在事后「告知偏差」。这种时候应该**问用户**。
4. **所有提问都要用弹窗式选项**，不要让用户打字；弹窗样式如用户提供的截图
   （标题 + 编号选项 + 推荐徽标 + 截断描述 + 铅笔自定义项 + 「下一题」）；
   详细计划在**右侧侧边栏**展示。

## 2. 关键侦察结论（决定了实现方式）

### 2.1 那个弹窗是「墓碑」，不是没写过

前端源码只有 `frontend/src/App.vue`（3752 行）+ `main.js` + `style.css`，没有组件目录。
截图那种卡片**从未实现过**，但它的**样式与数据模型都还在**，只是模板被删了：

- `App.vue:2888` 注释确证：`<!-- 计划确认弹窗已改为：输入框上方窄横条 + 右侧侧边栏链路展示 -->`
- 孤儿 CSS：`.pc-ver`（单选卡行）、`.pc-opt`（input 单选，`accent-color`）、
  `.pc-other`（「其他…」自由文本框）、`.pc-general`（补充 textarea）、`.pc-count`（字数）
- 孤儿状态：`planCardOf()`（`App.vue:1013-1055`）仍在构建每步的 `param_options → options[]`，
  但**没有任何模板渲染它**；`confirmFrameOf()`（`1088-1106`）产出的 `overrides`
  **永远是空的**——因为没有 UI 能填自定义项。

所以做法是**复活**而不是新造：把模板补回去，接上既有数据模型，顺带修掉 `overrides` 恒空。

### 2.2 提速必须先纠正一个测量错误

用户给的那份耗时（`语音转写 225.846s`、`成片渲染 20.186s`）来自工具帧的 `elapsed`。
但 `render_video` 属于 `LONG_RUNNING_NODES`（`storyline_server/server.py:41`），
`_invoke_long`（`:189-207`）只内联等 `render_grace_sec=20`（`settings.py:81`）就返回，
真实渲染在后台继续。所以 **20.186s 是 grace，不是渲染耗时**。

从 PG 取真机那一跑的权威时间（`artifacts.updated_at` + `render_jobs` + `checkpoint_entries`）：

| 项 | 时间 | 占比 |
|---|---|---|
| 总墙钟 | **957.3s** | 100% |
| **渲染** | **660.6s** | **69.0%** |
| asr | 226.7s | 23.7% |
| understand_clips | 29.5s | 3.1% |
| 11 个 LLM 决策轮 | 31.8s | 3.3% |
| 收尾 | 6.9s | 0.7% |

另外一个被推翻的假设：**`asr` 与 `split_shots` 本来就已经并发了**。
`iter2` 的单条 assistant 消息里 `tool_calls=["asr","split_shots"]`，
两者都在 `load_media` 后约 0.87s 起跑。`split_shots` 的 27.6s 完全藏在 asr 的 226.7s 里
（artifacts 写入 +28.46s vs +226.72s）⇒ **在切分镜头上再并行是 0 收益**。
（机制：`MCPTool.reads/writes` 来自 DAG 契约而非 `readOnlyHint`，
`asr` 写 `store:asr`、`split_shots` 写 `store:split_shots`，无交集 ⇒ 同批。）

## 3. 已实现的改动

### 3.1 渲染拍平（P1）——最大且零输出风险

`storyline_server/nodes/core_nodes.py` 的 `_render_with_moviepy` 原先套两层
`CompositeVideoClip`（内层画面 `:1586` + 外层字幕 `:1593`）。
MoviePy 2.x 的 `compose_on` 在背景带 alpha 时**每层每帧**都要新建整幅 RGBA 画布做
paste + alpha_composite（`moviepy/video/VideoClip.py:781-793`），内层 mask 每帧重算
（`compositing/CompositeVideoClip.py:130-139`）。套两层 = 整幅合成做两遍。

改成一层 `CompositeVideoClip([*layers, *sub_layers])`。等价性论证：字幕层自带
`with_start/with_position`，作为兄弟层与「先合成画面再与字幕合成」在数学上等价。

**实测（自己重测，不是转述）**：

| 用例 | 帧数 | 逐帧像素 sha1 |
|---|---|---|
| 真实素材 6 画面层 + 2 字幕层 | 75 | **75/75 一致**，40.7 → 24.4 ms/帧（1.67×） |
| A 字幕超出画面 | 68 | **68/68 一致** |
| B 目标时长超过画面 | 68 | **68/68 一致** |
| C 字幕恰好贴到片尾 | 57 | **57/57 一致** |

脚本：`.runtime/audit/verify_p1_flatten.py`、`verify_p1_edge.py`、`verify_p1_prod.py`。
边界用例是必要的——第一版探针里字幕都短于画面，`subclipped(0, duration)` 落在共同区间，
**证明不了边界**。

上面是「合成层」的微基准。**整片渲染另测了一次**（`verify_p1_prod.py`）：直接调用生产函数
`_render_with_moviepy` 渲同一条时间线两遍（唯一差别是拍平与否），产物再用 ffmpeg 解帧逐帧比对：

```
素材 mat-eb518e.mp4  时间线 5 段画面 + 4 条字幕，8.0s 640x352@25
先渲拍平版（当前生产行为）  完成 3.14s
再渲嵌套版（改动前的写法）  完成 4.82s
逐帧比对：帧数 flat=200 nested=200，一致 200
拍平 3.14s   嵌套 4.82s   提速 1.54x
按整跑 660s 渲染外推：430s（省 230s）
```

为什么必须单独测整片：真实渲染还含 ffmpeg 取帧/写盘/x264 编码，那部分不受拍平影响，
所以「整片省多少」**不能靠单帧比例外推**。实测 1.54×（低于单帧的 1.67×，
正说明编码那段是固定成本）——按真机 660s 渲染外推**省约 230s**。

### 3.2 统一提问机制：`ask` 帧 + `ask_user` 工具

- `agent_framework/ask_user.py`：`AskUserTool` + `normalize_question()`。
  输出固定形状 `{title, options:[{key,label,description,recommended}], allow_custom, custom_hint}`。
  容错（选项给字符串也行），但会**打回**会让弹窗出不来卡的输入（缺 title / 选项为空 /
  key 重复 / 超过 6 个 / 选项类型不对）——静默兜一个空问题比报错更糟。
- `hooks.py`：`on_approval_required` 增加可选 `ask` 参数（帧里多带一个 `ask` 字段）。
  没有 `ask` 时前端退回原形态，**两种形态共用同一个弹窗组件，老路径不砍**。
- `agent.py`：`_take_asked_question()` + 循环里拦一次。模型调 `ask_user` → 本轮挂起 →
  用户点选 → 从同一断点续跑。为什么在循环里拦而不是在工具里抛：工具只负责把问题整理成形，
  「停下来」是循环的职责，工具不该自己决定一整个轮次的生命周期。
- 工具返回给模型的说明明确要求「本轮到此为止，不要继续编造用户还没做的选择」。

### 3.3 编排预览读模型

`agent_framework/preview.py` 的 `build_preview(artifacts)`：纯函数、只读、不调 LLM。
输入是 Storyline 的 `node -> payload` 快照，输出前端可直接渲染的结构：
`summary / material / shots / story / timeline / audio / warnings`。

数据全部来自既有节点产物，**没有新增采集**：`plan_timeline*`、`group_clips`、
`understand_clips`、`asr`、`generate_voiceover`、`select_BGM`、`filter_clips`、`split_shots`、`load_media`。

它还会**主动指出偏差**。实测复现了真机那个问题：

```
warnings = ['画面轨只排到 12.8s，而时间线总长 90.0s——末尾会定格。',
            '转写内容到 166.1s，但成片只到 90.0s——末尾的话会被截断。']
```

缺产物时不报错、只是少画几块（空产物 → `ready=False`）。

### 3.4 挂起态刷新后不再丢

审批原先**不落库**（落库白名单只有 media / plan），刷新即丢，而且弹窗标题写的
「随时可再打开」是虚假承诺（关闭后无重开路径）。修法：

- `checkpoint.await_approval(..., ask=)` 把 `ask` 一起落进 `cp.approval`。
- `CheckpointsRepo.list_awaiting_approval_by_session()` +
  `CheckpointManager.awaiting_approval_for_session()`。
- `GET /convs/{id}/runs/active` 回 `approval`（含 `ask`）。挂起态不属于 `running`，
  所以要单独查一眼，否则这个端点查不到等确认的 run。

### 3.5 编排预览端点

`GET /preview/{conversation_id}`：只读、不触发剪辑、不调 LLM。读不到产物时回
`ready=False` 而不是 500。

## 4. 为什么没做 P2（拆整轮 barrier）

调研给出的 P2 是「把批间串行改成某 key 一被写入就让读它的批次起跑」，
收益 ~29.5s（占 957s 的 3%），理由是 `understand_clips` 只依赖 `split_shots`
（+28.46s 就绪）却等到 asr 结束（+226.72s）才起跑。

**没做，理由如下**：

1. 收益 3%，而改动落在**调度器核心**（`_run_tool_round` 的批间顺序）。
   用户明确要求「首要确保任务链执行完整成功，再保证速度」——在 3% 收益上
   动调度正确性不符合这个优先级。
2. 调研自己也标了约束：必须按**已写入的 store key** 判定，否则拦截器会把
   `split_shots` 重跑一遍（`orchestration.py:446-462`）。这类改动的失败模式
   （重复执行剪辑节点、产物作用域错乱）代价远高于 29.5s。
3. 它是**可在后续单独一轮安全推进**的独立工作，且有现成的复现脚本与基准；
   等渲染拍平（省 194–360s）落地、链路稳定后再做，收益/风险评估才准。

同理没做：**ASR 分段并发**（实测 CPU 上 1.03×，几乎零收益，
且会改段边界并破坏 `_filter_asr_hallucinations` 的上下文连续性抑制）、
**split_shots 内parallel**（完全被 asr 掩盖，且按时间窗切会在边界漏切点）。

`understand_clips` 的 `Semaphore(4)`（`core_nodes.py:498`）是硬编码，
但调大它的收益只有 ~13s 且**有改变输出的风险**（某批 429/超时 → 该批镜头走
「视觉理解降级占位」caption → 影响 `filter_clips` 选片 → 改最终成片），
所以本轮**不动**。

## 5. 实现过程中发现并修掉的既有缺陷

这三个都是**本来就存在**的问题，是这一轮的实测把它们逼出来的；不修则新功能根本跑不通。

### 5.1 `_repair_orphans` 会剥掉「待批」的 tool_calls → HITL 续跑必然失败

`AgentOnceRun.approve` 用 `_repair_orphans(cp.messages)` 修孤儿消息，但挂起点上
**待批的 tool_calls 本来就没有 tool 结果**（结果要等用户批准后才回填），于是被判成孤儿
全部剥掉。续跑时 `_settle_pending` 又补了一条 tool 回执 → 变成「孤儿 tool 消息」→
LLM API 直接 400 → **整条 run failed**。

真机日志证据：一致点 seq=12 的 delta 里 assistant **有** `render_video` 的 tool_calls，
而最终快照（seq=13）里那条 assistant 只剩 `content`，紧跟着一条 `tool_call_id` 指向它的
回执——正是被剥掉之后的形状。

修法：`_repair_orphans(messages, keep_ids=...)`，把待批 id 作为「必须保留」传进去；
`approve` 与 `resume` 都从 `cp.approval["pending_calls"]` 取 id 传入。
回归：`tests/test_approval_gate.py` 用例⑦（先复现旧行为再验证修好）。

### 5.2 渲染确认「只回喂一句话」会让模型再调一次渲染 → 弹第二张卡

一开始确认后的处理是「回喂一句『用户已确认』」。但模型看到这句话后会**再发起一次**
`render_video`，于是又被门拦住、弹出第二张一模一样的卡——实测就是这样循环下去的。

修法：确认类决策（`confirm_render`）**直接执行**挂起的那批调用（用户点一下，片子开始渲），
其余决策（要改 / 自定义）才回喂文字且绝不执行。另外给同一条 run 加一次性标记：
确认过之后再出现渲染调用，如实回一句「已在渲染中」，既不再弹卡也不重复提交
（重复渲染代价不对称：一次误判就是白烧几分钟，而且两次写同一个 artifact 作用域）。
回归：`tests/test_approval_gate.py` 用例⑥。

### 5.3 迁移脚本会在「曾经挂起过审批」的库上让**服务起不来**

`migrations.sql` 里放宽 `checkpoints.status` 的那份定义停留在只到 `'superseded'` 的旧版本，
而 `schema.sql` 的 `CREATE TABLE` 早已含 `'awaiting_approval'`。执行顺序是
schema.sql → migrations.sql，于是这份窄定义把全量约束**换回窄的**；只要库里存在一条
`awaiting_approval` 的挂起 run，这次加约束就因「已有行违反」失败，而它跑在启动流程里：

```
IntegrityConflict: check constraint "checkpoints_status_check" is violated by some row
ERROR:    Application startup failed. Exiting.
```

**它只在「真的挂起过一次审批」的库上复现**——也就是恰好在这一轮开始用挂起功能之后。
修法：把两份定义对齐（都含 `awaiting_approval`）。回归：`tests/test_storage.py` 新增一条
结构断言，直接比对 schema.sql 与 migrations.sql 里 `checkpoints_status_check` 的取值集合——
两份一旦漂移就报错，不必等到某个库起不来才发现。

### 5.4 主动提问续跑时给同一个 tool_call 补了第二条回执

`ask_user` 在挂起**之前**就已经执行过，它的 tool 回执已在 `messages` 里。
`_settle_pending` 收口时又给同一批补了一条同 `tool_call_id` 的结果——
变成「一个 id 两条回执」，LLM API 直接 400，整条 run failed。
真机证据（会话 `ask-*`）：一致点里消息 [8] 与 [9] 的 `tool_call_id` 完全相同。

渲染确认门那一路是**先拦后执行**，所以它确实需要补；两种情形必须区分。
修法：收口前先算出「已有回执的 id 集合」，只给还没有回执的那几条补。
回归：`tests/test_approval_gate.py` 用例⑧（含「同一 id 不得有两条回执」的断言）。

### 5.5 技能与提示词都没说「怎么问」，模型于是把问题写进正文

四个技能正文共 7 处写着「向用户提问」，却没说用哪个工具；系统提示词同样没提。
于是模型把问题写进回复正文——用户只能自己打字，这正是需求 4 要消灭的形态。

修法分三层：
1. 系统提示词（`prompts/system_prompt.md` + `DEFAULT_SYSTEM_PROMPT`）明确要求
   「一律调用 ask_user，不要把问题写在正文里」，并特意说明**连「请你发素材/贴链接」
   这类请求也要用选项**（否则模型会把「要素材」当成例外，继续在正文里索要）。
2. 四个技能的「向用户提问」全部改成「用 ask_user 弹出选项」。
3. `tests/test_prompt_library.py` 新增漂移守卫：`prompts/system_prompt.md` 与
   `DEFAULT_SYSTEM_PROMPT` 必须内容一致（只差空白）。这两处各写一份文案，
   靠人眼比对一定会漂——实测就漂过一次（少一个空格、以及文案不同步）。

**端到端验证**（`.runtime/audit/verify_ask_e2e.py`，真 WebSocket）：

```
① WS 上收到带选项的结构化提问
   title   = 这条短视频你想要多长？
   options = [('short_30','30 秒左右（快节奏）',True), ('mid_60','60 秒左右（标准）',False),
              ('long_120','2 分钟左右（完整表达）',False), ('keep_all','不截断，素材多长就多长',False)]
   → 题面 / 选项 / 推荐徽标 / 自定义项 全部就位
② run 停在 awaiting_approval（不是直接答完）
③ 用户点选 → 续跑 completed，且用户的选择进了上下文
④ 问题被消费掉，不会反复弹同一张卡
```

需要说明的**非确定性**：模型有时会先答一句再问（甚至不带素材时先要素材）。
这是模型的自由度，不是链路缺陷——机制已经保证「一旦它决定问，问就一定是弹窗」。

**（2026-10-02 更新）「正文里提问」这一半下一轮已经补做了。** 本节当时写的是「本轮没做」，
理由是它对正常答复有误伤风险而收益只是省一次打字——这个判断后来被推翻，因为误伤风险可以靠
判据做窄来控制，而「用户只能自己打字」正是需求 4 要消灭的形态。现在是硬保证：
`agent_framework/ask_gate.py` 在准备收尾那一刻判 `looks_like_asking_user`，本轮没有 `ask_user`
调用就把这一轮打回（默认只打回一次，`popup_question_nudges=1`），打回文案按轮次分执行/规划两版；
预算用尽后不再打回，改为在正文末尾附一句服务端核对到的事实（`NO_POPUP_NOTE`），如实交付。
误伤靠两级判据挡着：强索取措辞不带问号就算（「请把链接发我」本来就是祈使句），
弱索取（你想 / 要不要我 / 是否）必须配问号，「两点需要你知道的偏差」这类告知不挨打——
正反例都收在 `tests/test_ask_gate.py`（26 项）里，标定脚本 `.runtime/audit/calibrate_ask_gate.py`。
开关 `AgentConfig.require_popup_questions` 默认 **True**。
剩下的边界仍是词面判据本身：认不出一句刻意绕开措辞的自述，宁可漏纠也不误伤正常回答。

### 5.6 提问续跑把用户的回话整条丢掉 → 模型连问 6 题

§5.4 修掉「补第二条回执」之后，还漏了另一半：**回执不补了，答案也没写进去**。

`_settle_pending` 在「这批调用都已经有回执」那条分支里直接返回，什么都不追加。于是模型在
续跑那一轮看到的上下文尾部仍然是 `tool: {"asked": true, "note": "问题已发给用户…"}`，
等不到用户的回答——它只能照 §5.5 的提示词再问一遍。真机实测：同一条 run 连问 6 题，
**第 6 题还在重问第 1 题**（会话里六道「已暂停」，用户点了六次确认）。

判据不能只看界面：界面上每条答案都以用户气泡回显过（前端自己的乐观渲染），
要看的是 **checkpoint 链上的角色序列**。修前是 `assistant → tool(asked) → assistant → tool(asked)…`，
修后是 `tool(asked) → user("highlight") → assistant("你选了高光精选，方向定下来了") → tool(asked 下一题)`。

修法：`remaining` 为空时把 `note or decision_text(decision, "")` 以 `role=user` 追加。
回归：`tests/test_approval_gate.py` 用例 H（链上「答案」恰好一条 `role=user`、
`len(messages)` 只多 2、且没有第二条同 id 回执）。
用例 G（§5.4 那条）与 H 是互补的两半：G 钉「不许多写回执」，H 钉「必须写进回话」。

### 5.7 续跑那一轮 `asked_this_run` 归零 → 每一轮都吃一条假打回

§5.5 补做弹窗硬保证之后才暴露出来的：`asked_this_run` 是每次 `_drive` 的局部量，
而**续跑是一次新的 `_drive`**。那一轮的上下文里明明已经有 `ask_user` 的调用与回执，
但局部变量是 `False`，于是硬保证判「这段在提问且本轮没调 ask_user」成立，
给一条本来就正确的续跑打回——真机上续跑的**每一轮**都挨一条
「服务端核对：…但你没有调用 ask_user」。

修法：`_settle_pending` 返回「这一批里有没有 `ask_user`」，调用点把它 OR 回 `asked_this_run`。
注意区分：渲染确认门那一路也走同一分支（它带同样的 `ask` 结构），但只有 `ask_user` 那一路
才是「本轮已经问过」的证据，所以返回值取的是 `any(tc.name == "ask_user" for tc in calls)`。
回归：用例 I（脚本 `ask_user → 答案 → 收尾`，断言只多一次 LLM 调用、
链上零条含「没有调用 ask_user」的 system 消息）。

**两处判据的反向验证**：把修复回退后跑同一份测试，H/I 一起红（6 条 FAIL）；
修复后 46/46 绿。用例 ⑧ 的第一版判据太弱（`"60" in 拼接正文` 在带 bug 时也能过，
因为回执文本里就有「60 秒」），改成断言消息**角色**之后才真正 discriminate。

## 7. 仍然没做 / 已知取舍

1. **P2「拆整轮 barrier」没做**：调研给的收益 ~29.5s（占 957s 的 3%），
   但改动落在调度器核心。用户要求「首要确保任务链执行完整成功，再保证速度」，
   在 3% 收益上动调度正确性不符合这个优先级。它是可独立推进的一项，
   有复现脚本与基准，等渲染拍平落地稳定后再做更合适。
2. **ASR 分段并发没做**：实测 CPU 上 1.03×（几乎零收益），且会改段边界、
   破坏 `_filter_asr_hallucinations` 的上下文连续性抑制。真提速只能换 GPU 设备，
   但 int8→float16 会让文本可能微变。
3. **`understand_clips` 的 `Semaphore(4)` 没调大**：收益 ~13s，但有改变输出的风险
   （某批 429/超时 → 该批走「降级占位」caption → 影响选片 → 改最终成片）。
4. **规划轮段仍在 `.py` 里拼装**：**已做（2026-10-02）**——搬的是「措辞 + 哪一段出现」，
   不是「谁来算数据」：文案落进 `prompts/planning_round.md`，模板按空行分块、块首独占一行的
   `{?key}` 是守卫（没值整块不出现），`render_blocks` 只有这一条加「渲染后为空的行不留空行」，
   没有 if/for/嵌套；节点白名单与可上卡开关仍由 `gate.whitelist()` / `gate.knob_facts()` 现取后
   插进 `{nodes}` / `{knobs}`。等价性靠**动手前**逐字捕获的 9 条渲染金样钉住（内联回落与磁盘模板
   各比对一遍，要求字符串相等），另钉一条 AST 守卫：`run_server` 构造 `PlanGate` 时必须真的带
   `prompt_library`——上一轮的边界判断（「条件拼装搬进模板只会变成调试渲染」）是靠这两条才敢撤的。
   详见 `docs/audit-2026-10-01-缺陷修复记录.md`「结构性改造 4」。
5. **`plan_gate.py` / `_drive` 的拆解**：**已做（2026-10-02）**——`plan_gate.py`（拆前实测
   1526 行、6 种职责）切成 `agent_framework/plan/` 包的 12 个模块，`gate.PlanGate` 只做装配
   与 12 个公开成员转发；`_drive` 从 325 行收成 77 行骨架 + 六块具名助手（`_open_run` /
   `_tool_round` / `_suppress_repeat_render` / `_pause` / `_nudge_back` / `_deliver`），
   控制流与语义未变。两份形状由 `tests/test_plan_layout.py`（31 项）钉住，不让它长回去。
   逐模块职责表与两处坑（`_norm`→`clean` 避开局部变量同名、切片粘合错误由 pyflakes 兜出）见
   `docs/audit-2026-10-01-缺陷修复记录.md` 的「结构性改造 1+2」一节。
