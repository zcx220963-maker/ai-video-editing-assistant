## 3. 模块详解(12 个模块)

### 3.1 接入层与鉴权(`agent_framework/server.py` 1577 行)

**职责**:HTTP + WS 全部端点;鉴权;中文名换轨;凭证打码。

- FastAPI + lifespan 统一启停存储/MQ/consumer/心跳/广播。
- 鉴权:`/register` 签发 32 字节随机 token,**库里只存 sha256**;HTTP 走
  `Authorization: Bearer`,WS 浏览器不能带自定义头 → `?token=` 查询参数,
  失败 close 4401;校验失败统一 401 不区分原因(`auth.py:8-10`)。
- 跨 owner 语义:读返回"空"不返回 403(不泄露会话存在性);写 409;别人的 run 一律 404。
- **中文名换轨**(§3.14):一份词表(工具 display_name + MCP title + 技能 display)
  + 两个出口(HTTP `CatalogJSONResponse` / WS `rewrite_obj`),双轨制:
  `KEEP_KEYS` 里的机器名是键(挂 `*_display`),`OPAQUE_KEYS` 是用户内容整条不动。
- 安全细节:uvicorn 访问日志的 `token=` 打码(`_mask_credentials_in_access_logs`,
  **挂在 lifespan 而非 import 时**——uvicorn 启动会 dictConfig 清掉已有 filter,这是踩过的坑)。

**为什么**:user_id 不放请求字段,由 token 反查——模型和前端都伪造不了身份。

**自检**:① 为什么 WS 凭证走查询参数?② 为什么 403 改成"返回空"?
③ 访问日志打码为什么要装在 lifespan?

### 3.2 消息队列与会话路由(`mq.py` 206 行 + `consumer.py`)

- 接口 `MessageQueue`,`build_message_queue("memory"|"kafka")` 双实现:
  内存版**复刻 Kafka 语义**——每 (topic,group) 4 分区,`zlib.crc32(key) % 4`
  落分区(key=session_id),分区内严格 FIFO、分区之间并发,每分区一个 worker task;
  Kafka 版延迟导入 aiokafka。**不依赖外部 broker 也能跑。**
- InBound = chat topic;OutBound = 回投 topic(逐字 delta/进度/审批帧/成片卡/error/answer)。
- `SessionConsumer._handle` 按 `action.op` 分派:**plan(默认)/ execute_plan / resume /
  fork / approve / execute(定时任务,interactive=False 跳确认门)**。
- 分区 key = `f"{user_id}:{conversation_id}"`(consumer.py:20-22)→ **同一会话串行,
  不同会话并行**,这就是"第二句话不会在第一句处理完前执行"的全部机制。
- handler 异常按 `topic/group/partition/run_id` 记 `log.exception`(曾静默吞掉,
  导致 run 无声消失——靠这行日志才定位到 402 余额问题)。

**为什么 MQ 而不是直接调函数?** 削峰、执行位与请求生命周期解耦(渲染要跑几分钟)、
消费组天然支持多副本。回投走 OutBound 是为了让"谁执行"和"谁连着 WS"解耦。

**自检**:① 同会话串行靠什么保证?② 内存版怎么做到"单条消息失败不中断分区"?
③ 为什么要区分 InBound/OutBound 两个 topic?

### 3.3 Agent 主循环(`agent.py` 1931 行)

- 生命周期:`AgentOnceRun.run` = 附件校验 → ContextBuilder.build → user 消息落库 →
  `checkpoint.begin` → 绑身份 → `_drive`。
- **`_drive` 是 77 行骨架**(曾 325 行 god method,重构后六块具名):
  `_open_run`(恢复 RunState)→ while 迭代:{ `_settle_pending` 审批收口 →
  **一致点落盘** → before_iteration 钩子 → LLM → 要工具走 `_tool_round`,
  否则 `_nudge_back` 四道硬保证 → 通过则 `_deliver` }。
- **三道门**(`_tool_round`):① 通用审批门(`requires_approval`)② 渲染前确认门
  (`should_gate_render`)③ `ask_user` 主动提问——命中即 `_pause`:
  先落盘再 `await_approval` 再发审批帧。挂起态 `awaiting_approval` **刻意不在
  `_UNFINISHED` 里**(人工挂着就是等人工,崩溃恢复不该捞它重跑)。
- **渲染代查** `_follow_inflight_renders`:一轮工具跑完,结果里还有 queued/running
  的渲染视图 → 循环自己每 3s 调 render_status 到终态才拼进上下文(预算 1800s,
  每 120s 心跳续 checkpoint 租约)。**"模型会不会自己去查"不再是链路成败点。**
- 撞迭代上限 → 标 `failed`(不是 completed),这样"继续"能接上;
  续跑按"再给一轮"而不是接着数。

**为什么迭代边界才落 checkpoint?** 一致点的定义是"即将调 LLM 前"——此时上一批
工具结果已全部落链,恢复只需重发一次 LLM 调用,**绝不重放已提交的工具**(幂等关键)。

**自检**:① ReAct 循环在本项目对应哪段代码?② 为什么挂起态不算"未完成"?
③ 渲染代查为什么由循环做而不是信任模型?

### 3.4 工具系统与并发(`tool.py` 382 行 + `tools/` + `orchestration.py`)

- `Tool(ABC)`:抽象 `name/description/parameters/execute`;辅助 `_TYPE_MAP`/
  `_resolve_type`(处理 union 类型);`read_only / exclusive / concurrency_safe`
  三属性控制并发(`tool.py:84-136`)。
- `ToolRegistry`:`register/unregister/get/has/get_definitions/execute`;
  **错误是类型化 `ToolError(tool, detail)`,不再嗅探 `startswith("Error")`**
  (tool.py:13 注释明写),但保留 `_HINT` 附加语(`tool.py:32,58-59`)。
- **并发分批两条规则**:契约(读写集相交即冲突)+ read_only;
  `concurrency_safe=False` 独占一批;贪心且保持模型给出的顺序;
  **契约取不到 → 保守串行(正确性不依赖契约存在)**。
- **Interceptor**(`orchestration.py`):工具真正执行前按 `required_nodes` **递归**
  补齐未执行的前置——"LLM 无论怎么选,执行路径都满足 DAG 约束"的安全网。
- `Store` = 程序控制的节点间数据总线(写入带 reducer:last_write_wins/append/merge);
  `ArtifactStore` 把总线持久化到 artifacts 表,作用域 `(session_id, artifact_id)`。
  **Store(框架管)与 Memory(Agent 自主读写)严格区分,不能混。**
- 框架工具清单:file(Write/Read/Edit/Grep,root 收窄到会话工作区)、
  web(Fetch/Search,防 SSRF)、fetch_media(直链→页面嗅探→yt-dlp 三策略,
  JS 运行时探测)、rerun_from(跨轮回溯)、cron、memory、skill、team、MCP 外部工具。

**自检**:① 为什么错误不再用字符串前缀判定?② 拦截器递归补齐解决什么问题?
③ Store 和 Memory 的边界在哪?

### 3.5 上下文构建与压缩(`context.py` + `compress.py`)

- `ContextBuilder.build`:system = `prompts/system_prompt.md`(缺目录回落内联,
  提示词是核心资产不能因为目录没拷而变空)+ bootstrap 文件段 + `<runtime>` +
  各 ContextSource(记忆/技能)段 + `<attachments>` 素材事实段 + 本轮 extra_sections
  (如 `<approved_plan>`);消息 = [system, *Session 历史, user]。
- **三级压缩**(`compress.py:4-6` 与文档逐字对应):
  ① 折叠旧工具结果为预览(保留最近 2 条完整)→ ② 从最早开始淘汰 →
  ③ 被淘汰的消息做摘要(默认确定性摘要,可换 `make_llm_summarizer`)。
  始终保留:首条 system、最后一条当前 user。
- **`_repair_orphans`**:双向修复孤儿 tool_calls/tool 消息并重排;
  `keep_ids` 保护 HITL 待批调用不被剥掉(否则续跑直接 400)。
- token 估算:CJK 逐字计 1,西文 4 字符计 1(compress.py:48-62)。
- prompt 指纹:`{version}:{sha256[:8]}` 落进每轮 qa.parts 首条——换过文案之后
  的结果能归到具体版本(eval 用)。

### 3.8 Hook 可观测(`hooks.py` 683 行)

- `AgentHook` 生命周期节点(实现约 10 个,文档只列 5 个):
  before_iteration / on_stream / on_stream_end / after_execute_tools /
  **on_approval_required / on_llm_usage / before_tool_call / after_tool_call /

- `CompositeHook` 统一转发、**吞单 Hook 异常只记日志**——一个 Hook 挂不能拖死主循环。

### 3.9 Checkpoint / fork / 崩溃恢复 / 多副本(`checkpoint.py` 530 行 + `run_state.py`)

**★★ 本项目最硬核的模块,面试重点。**

- **指针行 + 一致点增量链**:PG `checkpoints` 一行 = 走到第几轮/状态/占哪份剪辑产物
  (刻意不存 messages);`checkpoint_entries` 每行只存自上一致点**新增**的消息
  (kind=delta),上下文压缩改写过旧消息时那一条退化为 kind=full 基准——
  重建从最近 full 往后拼 delta。
- **落盘时机只在迭代边界**(即将调 LLM 前)→ 恢复只重发 LLM 调用,
  绝不重放已提交的工具。
- 状态机:running / completed / failed / superseded / **awaiting_approval**
  (审批挂起把 pending_calls + 结构化 ask + fallback_options 全落 approval 列)。
- **fork/时间旅行**:`load(run_id, at_seq)` 重建任意一致点 → 子 run 换新
  `artifact_id` → 父产物集整份 `clone_from` 复制 → 按剪辑 DAG 契约算**下游闭包**
  逐个作废(上游切镜/ASR 逐字节复用)→ 父 run 置 superseded →
  **新诉求作为子 run 最新 user 消息接上**(否则模型原样重跑选同一首 BGM——真机踩过)。
- **跨轮回溯**:`rerun_from(node, instruction, run_id?)`——本轮链上没有该节点时,
  回绝文本列出本会话跑过它的历史执行当索引;只认同一会话、绝不猜。
- **多副本**:`claim_recoverable(instance_id)` 两步纯 AND 认领(无主 → 租约过期),
  PG `FOR UPDATE SKIP LOCKED`;租约在每次 save_progress 顺带续期(迭代边界=心跳)。
- **RunState**(`run_state.py`):跨挂起必须成立的事实收敛成字段清单对象
  (approved_plan / calls_attempted / calls_executed / plan_candidates / qa_parts…),
  随指针行落盘(写入点只有 4 处:`_drive` 开头/每个一致点/每个挂起点/异常路径,
  **与消息同批**)。收尾后只留 approved_plan("认过的承诺"),分叉时子 run 继承。

**自检**:① 一致点为什么定义在"调 LLM 前"而不是"工具执行完"?② fork 为什么
要作废下游而不是只重跑一个节点?③ RunState 解决什么问题(挂起前后对账丢失)?
④ 两个副本怎么保证同一条 run 只被一个接手?

### 3.10 计划门与 HITL(`plan/` 包 + `ask_gate.py` + `render_gate.py` + `ask_user.py`)

**计划门 = 两次 run,不造暂停态**(§3.15):
- 默认入口就是规划轮:规划注册表**物理不含**剪辑执行节点,出口只有 submit_plan
  或直接回答。Run A 正常 completed → 用户确认 → 另起 Run B(指针行记 plan_run_id 谱系)。
  **没有"等待确认"状态机、checkpoint 语义零改动。**
- **四重校验**(纯代码,一次 LLM 都不叫,`plan/validate.py`):
  ① node ∈ 注册表 ∩ 白名单 ② 步骤序与 DAG requires 拓扑相容 ③ skills_hint 存在
  ④ param_options 每个值可反查枚举源。`confirm` 的拒收**发生在跑模型之前**。
- **枚举是承诺,自定义是诉求**:卡面值必须能反查节点 schema/BGM 曲库真实标签;
  自由文本永不进节点参数,只进 `<user_custom_requests>` 段(中和+转全角防注入)。
- **两句服务端核对**(词面判据,plan/wording.py):`claims_plan_card`(没出卡不许
  声称出了)/ `claims_step_executed`(一次步骤没调不许声称渲完)→ 退回重写一次,
  预算用尽补一句事实,绝不带假称收尾。
- **PlanReconcileHook**:批准计划 vs 实际调用事后对账,**只观测不拦截**;
  `ask_user` 记在 calls_executed 但算交互不算创作步骤。
- **复盘进记忆**(`plan_retro.py`):候选卡 vs 确认帧一比出结构化差异(跳步/改参/
  换一版原话/成片退回),落带锚点短行("只落动作不落结论");调用点在 runner.run
  **之前**(确认帧是既成事实,渲染崩了偏好也不丢);一轮最多 8 行、≤160 字。

**HITL = 同一条 run 内挂起**(§3.16,与计划门的两次 run 是两回事):
- 三条触发:ask_user / 渲染前确认门(默认开)/ requires_approval。
- 作答 `POST /runs/{id}/approve` → 投 MQ action 帧 → `Agent.approve` 续跑。
- **两条硬纪律**(真机踩出来的):① 用户的回答以 `role=user` 追加,
  **不得补第二条同 call_id 回执**(打接口直接 400);② `asked_this_run` 是
  每次 `_drive` 的局部量,续跑必须由 `_settle_pending` 恢复,否则撞弹窗硬保证
  吃假打回。
- **弹窗硬保证**(ask_gate.py):准备收尾时文字在索取(两级词面判据:强索取不带
  问号也算;弱索取必须配问号)而本轮没调 ask_user → 打回一次,预算用尽附
  NO_POPUP_NOTE。

**自检**:① 为什么计划门选两次 run 而不是 interrupt 状态机?
② 卡面参数为什么要反查枚举源?③ 弹窗判据为什么"宁可漏纠不误伤"?

### 3.11 Storyline 剪辑服务(`storyline_server/`,:8001)

- FastMCP + streamable-http;每节点包一层 async handler 注册为 MCP 工具,
  会话身份从 `X-Storyline-Session-Id` 头解析;作用域 `u:{user}:c:{conv}` 与主服务共用。
- **20 个 DAG 节点**(`core_nodes.py` 2999 行),记住五段式:
  素材(search_media/load_media)→ 理解(split_shots=ffmpeg 场景检测 / asr=faster-whisper
  small 本地 / understand_clips=每镜抽帧 8 帧批打 VLM)→ 组织(filter/group/
  speech_rough_cut=间隔<0.5s 合并)→ 创作(correct_transcript 修字闸 / generate_script /
  generate_voiceover=edge-tts 坏音色落静音轨 / select_BGM 无曲库落正弦占位 /
  转场 xfade)→ 时间线与渲染(plan_timeline 三平行变体 / render_video 终点)。
- **NodeContract**(`editing_contract.py`):name/requires/reducer/params;
  writes=`store:{name}`,reads=前置键——**契约即 DAG 边,也是 fork 作废闭包的依据,
  也是并发分批的依据**(一份契约三处用)。
- **render_video**:MoviePy 2.x 主路径(多轨 CompositeVideoClip、字幕扁平化成并列
  TextClip 层——曾逐条嵌套导致 87s/1080p 跑 30 分钟)+ ffmpeg 兜底 + low_res +
  60s 分段;渲染前音画同步闸/对象键校验/覆盖层锚点换算,渲染后 ffprobe 探测 +
  抽 3 帧黑屏/定格抽检(luma<6.0)。
- **提交+轮询**(`render_jobs.py`):enqueue 落行 → asyncio.create_task 后台跑,
  Semaphore(2) 限流;grace 20s 内联等,长片回 queued+hint;**看门狗**每 30s 查,
  按"无进展时长"(非总耗时)600s 收口,`_reaped` 防止看门狗判死后 MoviePy 线程
  杀不掉导致双渲染;`_guarded` 兜底异常必落终态。
- **dry_run 出片账**:与真渲同一批判断函数,把 raise 换成记进 blocking;
  `__no_store__` 不进产物表、不落 render_jobs 行;路由层在进分发器**之前**识别
  dry_run 内联回账(真机踩过:分发器先落 queued 行把账盖掉)。
- **证据分级**(evidence_ledger):每条 = 主张 + 证据等级 + verified 与否;
  五级 machine/byte/frame/listening/eyeball;规则一条:**没做的那一步不许出现在
  verified 里**。机器没有听觉和内容判据 → 后两级永远 UNVERIFIED 且写明为什么。

**为什么剪辑放独立 MCP 服务?** 分工(音视频团队实现节点,Agent 团队规范调用)、
技术栈隔离(ffmpeg/MoviePy 重依赖)、故障隔离(连不上就真没剪辑能力,不假装)。

### 3.12 存储层与产物引用(`agent_framework/storage/`)

- PG:SQLAlchemy 2.0 async + asyncpg;调用方不写 SQL,走 `Cond` DSL +
  schema.sql 白名列名(db.py);15 个 repo 挂 Storage 上。
- MinIO:官方 SDK(同步),每个调用包 `asyncio.to_thread`;七方法接口
  (put/get_stream/head/delete/list_prefix/presign_get/localize)+ sha256 内容寻址缓存。
- **双后端**:`build_storage("pg_minio"|"memory")`,同一套仓储接口——
  离线测试用内存替身秒级跑;`test_storage_contract.py` 同一套用例双引擎各跑一遍。
- **产物引用契约(§3.12)**:payload 里只存 `obj:` 对象键(跨进程/机器/重启),
  读侧唯一入口 `Workspace.localize_ref`(sha1 槽位同名不互盖、命中直返、并发锁);
  三种键布局:users/{owner}/convs/{conv}/{material_id}、renders/{safe_sess}/{artifact}.mp4、
  derived/{sess}/…;**会过期的 presigned 直链不当持久引用**(media_url 只回给调用方,
  BaseNode.ephemeral 不落库);引用取不到字节=产物失效,当场报"请重跑产出它的节点",
  **绝不产出引用死链的"成功"**。
- **分片上传**:进度在桶里不在内存(list_prefix 就是账本,片号定宽补零字典序即拼装序);
  三道 sha256(逐片/按序清单/整文件);代价=拼装期 2× 桶占用峰值(刻意取舍)。

## 4. 四条关键流程(白板能画出来才算过)

### 4.1 一条消息的完整生命周期

```
浏览器 POST /chat (Bearer) → 鉴权(token→sha256→user_id)
→ InBound MQ, key=user:conv → 分区 worker → SessionConsumer(op=plan)
→ Agent.plan(): ContextBuilder(系统提示+记忆+技能清单+素材事实)
→ LLM(流式, delta 经 OutboundStreamHook→OutBound→WS)
→ submit_plan 出卡(四重校验)→ 计划卡帧 → 前端
用户点确认 → POST /plans/{id}/confirm(跑模型前校验)
→ 新 Run B: 注入<approved_plan> → 迭代循环(三道门/工具/Interceptor 补齐/一致点落盘)
→ render_video 提交(grace 20s)→ 循环代查到 done
→ MediaCardHook 成片卡 + qa.parts 持久链接 → answer 帧收尾
```

### 4.2 崩溃恢复

```
进程重启 → storage 连通建表 → claim_recoverable(instance_id)
   FOR UPDATE SKIP LOCKED 认领无主/租约过期的 running|failed
→ load 最近一致点(最近 full + 重组 delta)→ hydrate RunState
→ 续 _drive:重发 LLM 调用(已提交的工具绝不重放)
   每轮心跳续租(120s 渲染代查循环也续)
→ 终态 complete/mark_failed 归还认领
```

### 4.3 fork / 时间旅行

```
rerun_from(node, instruction) 或 POST /runs/{id}/fork(at_seq)
→ 在链上找"该工具结果出现之前"的一致点(找不到如实回绝,列出历史执行当索引)
→ load(at_seq) 截断重建 → 子 run 新 artifact_id
→ 父产物集 clone_from 整份复制 → DAG 契约算下游闭包,作废 rerun 点及下游
→ 父 run 置 superseded → instruction 作为最新 user 消息接上
→ 子 run 重跑:上游节点逐字节复用,只重做点名节点及其下游
```

### 4.4 渲染:提交 + 轮询 + 三处收口

```
render_video 调用 → MCP handler → RenderDispatcher.submit
→ render_jobs 落 queued 行 → 后台 task(Semaphore 2)
→ 20s grace 内等到终态?短片一次调用拿 done
→ 否则回 {status:queued, hint} → 模型可自己查 render_status(提示词三处指向)
   也可直接收尾 → _follow_inflight_renders 循环代查(3s 间隔,1800s 预算)
→ 编码进度:MoviePy logger= 挂 proglog,percent 70→98 真报
→ 终态 done/failed 写 render_jobs.result(证据账本随行)
→ 三处出口同账:WS media 帧 / qa.parts 持久链接 / render_status 查询口
→ 看门狗 600s 无进展收口;崩溃遗留由启动 reap_hanging 收
```

## 5. "为什么"系列(设计权衡,面试金矿)

1. **为什么两层服务(MCP)而不是把剪辑做成框架内工具?** 分工/依赖隔离/故障隔离;
   且"连不上就没有剪辑能力"避免了第二套 DAG 两个真相(mock 兜底因此被删)。
2. **为什么 MQ?** 执行位与请求解耦(渲染分钟级)、削峰、多副本消费组。
3. **为什么同会话串行靠分区 key 而不是分布式锁?** crc32 路由天然保证,
   零额外协调;Kafka 语义即如此。
4. **为什么 checkpoint 存增量链而不是每轮全量?** 长会话全量会爆存储;
   full 基准只在压缩改写时出现,读路径 O(1 定位)+线性重放。
5. **为什么一致点在 LLM 调用前?** 工具结果已落链=可恢复;重放 LLM 无副作用,
   重放工具有(渲染/上传都贵)。
6. **为什么计划门用两次 run?** 不新增状态机、不碰 checkpoint 语义、
   崩溃恢复/续跑免费继承;取消=不 confirm 即可。
7. **为什么卡面参数必须反查枚举源?** 枚举是"承诺"——会直接拼进节点调用;
   自由文本进参数=把自然语言当 API。
8. **为什么防假称靠服务端词面判据而不是提示词?** 提示词是概率性的;
   服务端核对是确定性的兜底。代价:词面认不出绕开措辞——"宁可漏纠不误伤"。
9. **为什么渲染提交+轮询?** MCP 是阻塞 JSON-RPC,一次调用等一部片子
   客户端必超时;抬 timeout 不改形状,挪执行位才改。
10. **为什么进度条要用 proglog?** MoviePy 2.1.2 没有 progress_callback,
    logger= 是唯一逐帧入口;否则几分钟不动像卡死。
11. **为什么看门狗按"无进展时长"?** 慢渲染每 1% 写行,总耗时判会误杀;
    真挂了的表现是 updated_at 不动。
12. **为什么证据分级?** "渲染完成"曾把机器验不了的(听感/对题)和量过字节的
    混为一谈;分级后未验的必须写明为什么拿不到。
13. **为什么 app_secrets 存明文?** 两个进程都要拿它真签发请求;
    表按 user_id 外键归属,删用户 CASCADE;对外一律掩码。
14. **为什么密钥热读而不是启动读?** 页面填 key 不用重启;5s TTL 两进程跟上。
15. **为什么 thinking 默认关?** 成百次小请求(understand_clips 逐镜一次),
    2.1×/1.7× 的实测收益;开关留两条通道。
16. **为什么对象键只有 obj: 一种?** 工作区路径有三个死法(清扫收走/换实例没有/
    分叉跨机器读不到);presigned 会过期。
17. **为什么 mock 节点被摘除?** 两套 DAG=依赖补齐只在 mock 侧生效=
    同一件事两个真相;宁可"没有剪辑能力"也不假连。
18. **为什么中文名做双轨而不是替换?** 机器名是键(复用/作废/排序都比对它),
    换成中文会打断机制。
19. **为什么记忆只落动作不落结论?** 一次勾选是一个数据点,写成结论
    下轮就把偶然当偏好。
20. **为什么 quota 默认 0?** 上线先观察一周用量再定阈值——limit=0 仍记录。

## 6. 易混淆概念对比

| 概念对 | 区别一句话 |
|---|---|
| InBound vs OutBound | 入站收用户消息(chat topic);出站回投一切帧(delta/卡/审批/answer) |
| MQ 路由 vs Session Manager | 路由解决"这条消息由哪个通道处理";Session 解决"这个会话之前聊了什么" |
| Store vs Memory | Store=编排引擎数据总线,框架管读写;Memory=Agent 长期记忆,Agent 自主读写 |
| 计划门 vs HITL | 计划门=两条 run(规划 run 出卡+执行 run);HITL=同一条 run 挂起等人工 |
| fork vs resume | fork=回到历史一致点换分支(父 run 让位);resume=从最新一致点续跑(崩溃恢复同入口) |
| checkpoint 指针行 vs 增量链 | 指针行=run 元状态;增量链=消息本体(full 基准+delta) |
| dag_contract vs required_nodes | 契约是服务端下发的机器可读边(供并发/作废);required_nodes 是拦截器补齐的声明 |
| awaiting_approval vs failed | 前者=等人工,崩溃恢复**不**捞;后者=异常,启动时会被认领重试 |
| read_only vs concurrency_safe | read_only=无副作用;concurrency_safe=read_only 且不 exclusive |
| dry_run vs render | dry_run=同一批判断函数只记账不烧像素,零留痕;render=真渲,落任务行与产物 |
| superseded vs completed | 让位(被 fork/跨轮回溯替代,退出恢复候选)vs 正常完成 |
| plan_run_id vs forked_from | 前者=执行 run 指回规划 run(谱系);后者=子 run 指回被回溯的 run |
