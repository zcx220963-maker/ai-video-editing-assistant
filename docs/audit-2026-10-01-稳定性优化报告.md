## 1. 这一轮修了什么

### R2 音画不同步 —— 两个叠加的 bug（最严重）

**bug A：画面没铺满配音时长。**
`_build_timeline` 里配音比画面长时，只把时间指针推到配音末尾、**不给画面补事件**：

```python
t = max(t, g_start + vo["duration"])   # 指针走了，画面轨道还是短的
```

渲染侧再用 `-shortest` 收尾 → 成片尾段画面定格在最后一帧、音轨被截断。
实测：画面 1.5s / 配音 6.0s → 成片 format 6.000s，但**音轨只有 1.499s**。
真实场景几乎必触发（60~120 字旁白 ≈15-30s，而模型常只分到两三个短镜头）。

**修法**：配音更长时用空镜池继续铺满，源区间在素材内部循环取（不能顺着往后读，
否则源片只有 3s 时读到 3s 之后会切出空片段、整条画面轨塌掉）。

**bug B（隐藏更深）：ffmpeg 兜底路径的配音时长恒为 0.04 秒。**

```python
se = float(ae.get("src_end", ae.get("end", 0.0)))   # 事件里两个键都没有 → 0
dur = max(0.04, se - ss)                            # 恒等于 0.04
```

`_build_timeline` 写出的 `audio_events` 只有 `path/start/group_id`——既没有 `src_end`
也没有 `end`。于是每次抽取配音都是一段 0.04 秒的静音，**整条 ffmpeg 兜底路径始终出无声片**，
而且不报错、format 时长还被 `-shortest` 掩盖着。

**修法**：事件自带 `duration`，渲染侧按 `src_end → end → src_start+duration` 次序回退。

**实测（修复前后对照）**：

| | 视频流 | 音轨 | format |
|---|---|---|---|
| 修复前 | 6.000s | **1.499s** | 6.000s |
| 修复后 | 6.000s | **6.000s** | 6.000s |

真机最终产物（20 秒成片）：`v:0 h264 20.000` / `a:0 aac 20.000` / `format 20.000`。

### R3 渲染看门狗误杀长渲染 + 判死后并发重渲

三个叠加的问题：

1. **兜底路径几乎不报进度**：ffmpeg 路径只在开头报 1 次（60%），分段路径**全程 0 次**。
   而看门狗按「多久没进度」判死（`render_stall_sec=600`）——一次都不报的表等于「立刻停滞」。
2. **判死后重试会起第二份渲染**：`reap_stalled` 取消 asyncio 任务（但 MoviePy 那个**线程杀不掉**），
   `_guarded` 的 `finally` 又把 `_tasks` 的 key 弹掉 → 下一次 `submit` 认为「没人在跑」，
   于是第二份渲染开始写**同一个产物路径**。现场残留印证过：69 个分段时间戳分两波、互相覆盖。
3. **迟到写会翻转状态**：旧线程跑完把自己的结果写成 `done`，把「已判死」翻回去，
   或覆盖新一次尝试的结果。

**修法**：
- 两条兜底路径全程按事件/分段上报进度（实测 ffmpeg 报 5 次、segmented 报 8 次）；
- 判死后把 key 记进 `_reaped`，旧渲染真正结束前**拒绝**为同一产物起第二份；
- 新增 **attempt 令牌围栏**：每次 open/重开/判死都换令牌，渲染体写进度与终态时带上它，
  令牌不符的写一律丢弃。`fail()` 也支持带 `result`（给下面的 S4 用）。

**实测**：判死后重试累计只启动 1 份；旧线程迟到的 `done` 与进度都被丢弃；
旧渲染真正跑完后占位锁自动释放、允许重来。

### R5 终答在断连瞬间永久丢失

`answer` 帧原先**故意不进环形缓冲**（理由是「REST 历史里有一份，留着会重复」），
而前端重连只重开 socket、不重拉历史（`loadHistory` 被 `if (histories[cid]) return` 挡住）。
于是断连恰好落在收尾那几秒 → 答复哪儿都拿不到，**必须整页刷新**。

**修法（两侧一起）**：
- 服务端：缓冲**保留终答**（只清中间进度帧），重放统一打 `replayed: true`；
- 前端：重连后**强制重拉历史**并在途 run 状态校准回来，`replayed` 帧按内容去重。

顺带修掉一个更隐蔽的错杀：原先的清理按「这条 run 的第一帧位置往后清」，
只要缓冲区里夹着**别条 run 的在途进度**就会被一起清掉（实测 r-3 的在途 delta 被误删）。
改成用独立的「已落定 run」集合判定，不再依赖帧还在不在缓冲里。

---

### R4 自动续跑吞掉用户的新指令

`consumer` 无条件 `agent.resume(cp.run_id, ...)`（**不带 message**），
而 `/chat` 回的是**新 uuid**，前端 `p.run_id !== busy[cid]` 的守卫把每一帧都丢掉。

真机后果：同一会话里用户的新指令**既没被执行、也没落库**，气泡永远等不到回复。

**修法**：
- 判定「消息与被打断那次是否同源」——同一句重发/点「继续」才续跑，换了内容走新诉求。
  实测 6 个用例全对（含真机那条「把它改成竖屏，重做时间线」→ 不续跑）；
- 续跑时投一帧 `run_adopted` 告诉前端**真正在跑的 run_id**，前端认下它，帧不再被丢；
- 终答与错误帧统一挂 **effective_run_id**。

---

### S4 渲染失败的回退选项到不了模型

节点确实返回了 `__fallback_options__` + 3 个方案，但渲染走「提交 + 轮询」，
模型看到的是从 `render_jobs` 行拼出来的视图，而 `fail()` **只写 error**。

**修法**：`fail()` 支持写 `result`；`render_view` 在 failed 时把 result 合进视图。
实测模型侧能看到 `output.__fallback_options__=True` 与 3 个方案。

---

### S5/S6 超时被当断线，整段活重跑一遍

- **S5**：MCP 客户端 `except Exception` 就把「超时」当断线——重新 initialize 再原样重发
  `tools/call`。asr / 画面理解一超时，服务端就把同一段长活**整段再跑一遍**，
  时间与 API 费用翻倍。修法：超时**不重发**，如实上报「服务端仍在处理」。
- **S6**：asr 单次预算 `60 + 1.5×音频秒` **无上界**，而传输超时是 600s：
  音频 400s → 660s、600s → 960s、900s → 1410s，**必然**客户端超时。修法：夹到
  `tool_timeout - 30s` 以内并给 warnings。

实测：3600s 音频的原始预算 5460s 被夹到 570s；模拟超时只发出 1 次 `tools/call`。

---

### 记忆上限与中文 token 估算

- **中文估算偏低 4 倍**：`len(text)//4` 把 1360 个中文字算成 344 token（实际 ≈1360）。
  后果是整个压缩闸门形同虚设——「超预算就压缩」永不触发，直到模型报上下文超限。
  修法：CJK 逐字计 1、其余每 4 字符计 1（英文不变）。
- **记忆无上限**：Agent 自己 append，schema 无约束，每轮**整段**注入 system，
  而压缩器不看 system 段。修法：单类 2000 字 / 合计 4000 字上限，
  超出时保留最近写的并**明确写出省略了多少字**（不静默丢）。

实测：11869 字记忆 → 注入 2055 字且带省略说明；两类合计仍被夹在 4094 字。

### 装配期一致性检查（这一轮最值钱的结构性改动）

**在防什么**：这个项目的 LLM 面向层有**四份互不校验的清单**——生产提示词里的工具名、
真实注册的工具名、计划门白名单、技能正文里让模型调的工具名。漂移了没人知道。
真机就是被它坑的：提示词写 `read_node_artifact`、真实工具叫 `read_node_history`。

**为什么不做「扫出所有像工具名的 token 求差集」**：试过，不可用。提示段里同时有
工具名、参数键、字段名、枚举值、以及**代码标识符**（`read_node_history` 自己就是函数名）。
想靠黑名单分开就会把真名一起豁免——正好放过要抓的那一类。形态上分辨不了语义。

**最终判据（两个方向）**：
- **方向 A（精确、零假阳性）**：维护 `WATCHED` 清单（15 个高危/历史误名），
  哪个「不在真实工具集里、却在待注入文本里出现」就报警。扫到就是真错。
- **方向 B（跨来源）**：技能正文是自然语言文档，里面的 `xxx_yyy` 基本就是工具名，
  与真实工具集求差集；参数键 / 技能名 / 模板 id / 样例 id / 产物字段名按形态或 schema 排除。

**实测（召回与精确都验过）**：

```
① 召回：提示词写 read_node_artifact          -> 抓到
② 召回：技能里臆造 analyze_shots / summarize -> 两个都抓到
③ 精确：真实 4 份技能正文 + 真实 46 个工具   -> 0 误报
```

启动期实际输出：

```
[startup] 一致性检查通过：提示面与 4 份技能正文点名的工具都在真实的 46 个工具里
```

**过程中被它自己抓出的两个误报，也已修正**：`submit_plan` 只活在**规划注册表**里，
不在主注册表（漏了它会把正确的提示词误报成假工具）；`asr_segments`/`material_id`
是技能里描述的**产物字段**，不是工具。

## 4. 还没做的（诚实清单）

按值得做的顺序：

1. **渲染代查最长 1800s 不落 checkpoint / 不续租 / 占死一个 MQ 分区**。
   现在有进度上报了，但代查期间仍不写 checkpoint，同分区其它会话会被一起阻塞。
   修法：轮询后顺带 `save_progress` 续租；代查改成后台任务而非分区协程。
2. **多副本广播时，没挂 WS 的会话帧既不投递也不入缓冲**（`broadcast.py`）。单副本无碍。
   ——**已做**（2026-10-02）：不投递不变，改为攒进**有界**影子预算（会话条数 + 合计帧数两条常数
   上界），接管后重连补得回接管前的进度；见 `audit-2026-10-01-缺陷修复记录.md`「结构性改造 5」。
3. **`/timelines*` 在 `memory` 存储后端会 500**（用了 PgDatastore 私有 `_run`）。
   生产是 pg_minio，不受影响。
4. **素材可见性查询是全表扫 + N+1**（`list_visible` 无 owner 过滤、逐行再查会话）。
   数据量上来会拖慢剪辑开局。
5. **`checkpoint_entries.seq` 用 max+1 分配**，同 run 被两条路径同时驱动会撞主键。
6. **提示词仍 100% 静态**硬编码在 5 个 .py 里；Bootstrap 机制（`context.py` 已实现）
   **仍未接线**。这是「动态加载」缺的那一半，也是 R11。
7. **`plan_gate.py` 1356 行 6 种职责、`_drive` 169 行 god method**（R13）。
   ——**已于 2026-10-02 拆完**，见 `audit-2026-10-01-缺陷修复记录.md`「结构性改造 1+2」一节。
8. **`start.bat` 仍带 `--no-resume`**：我是用 `python run_server.py` 起的服务，
   所以崩溃恢复生效；但双击 `start.bat` 会把 running 全标 failed。建议去掉这个参数。
