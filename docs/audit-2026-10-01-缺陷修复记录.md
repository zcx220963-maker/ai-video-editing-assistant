## 已修（A–F，均已提交并回归）

### A. 刷新后挂起的弹窗不会重新弹 ✅
**核实**：`server.py` 一直在回 `run.approval`（含结构化 `ask`），但
`App.vue` 的 `checkActiveRun` 只判 `status === "running"`，`approval` 一个字没读。
用户在等确认时刷新 → 后端永久挂起、界面无可点，只能整页重开。

**修法**：`checkActiveRun` 增加 `awaiting_approval` 分支，把服务端那份 `approval`
还原成 WS 帧的同一形状，复用 `approvalBubble`（同一条渲染路径）。
**实测**：`GET /convs/{id}/runs/active` 在挂起时回 `approval`，含题面 + 4 个选项 + run_id。

### B. 定时任务跑到渲染会永久死锁 ✅
**核实**：cron 投递（`run_server.py` `action.op="execute"`）已显式跳过计划门，
但渲染门只认**进程级** `AgentConfig.gate_render`，照样拦。挂起后
`awaiting_approval` 刻意不在 `_UNFINISHED` 里、自动续跑捞不到，而审批端点要
`_owned_run_row`（那条 run 的 `user_id="cron"`）——浏览器永远过不了归属校验。

**修法**：把「有没有活人在等」变成 **per-run 事实**而不是进程常量：
`handle/run/_drive` 加 `interactive`，consumer 收到 `op="execute"` 传 `False`，
两道确认门据此放行。单副本定时任务不再可能卡死在等确认上。

### C. 非 WS 客户端拿不到弹窗 ✅
**核实**：`/chat/sync` 只回 `answer`（一句「已暂停」），`ChatSyncResponse` 没有
`approval`/`ask`；`scripts/run_live.py` 里 `approve|approval|ask` 零命中——
真机验证弹窗只能走浏览器。

**修法**：`ChatSyncResponse` 加 `status` + `approval`（`answer` 保留，旧客户端不受影响）。
并把 approval 视图抽成 `_approval_payload` **一处拼装**，`/chat/sync` 与
`/convs/{id}/runs/active` 共用，形状不会漂。
**实测**：`/chat/sync` 返回 `['answer','approval','run_id','status']`，
`approval.ask` 带题面与 4 个选项。

### D. fork 之后编排预览读的是错作用域 ✅
**核实**：`_load_preview` 写死 `_default`，而 `rerun_from` 分叉给子 run 生成
`art-xxxx` 作用域（`checkpoint.fork`），子 run 产物写在自己那份里。

**修法**：两处
1. `_load_preview` 取**当前生效作用域**（`identity.artifact_id`）而不是固定 `_default`；
2. `GET /preview/{conv}` 的 `artifact_id` 留空时不再盲取 `_default`，而是回退到
   「本会话**最近写过产物**的那个作用域」——分叉后预览显示的是这一次的编排，不是父 run 的旧编排。

### E. 多题弹窗的答案数组被静默丢掉 ✅
**核实**：前端发 `{decision, message, answers}`，`RunApproveRequest` 只有
`decision`/`message`，pydantic 默认忽略多余键——靠前端把 answers 拼成中文句子
塞进 `message` 才没丢信息。

**修法**：`RunApproveRequest` 补 `answers` 字段 → 审批帧带上 → `Agent.approve`
→ `_settle_pending`；新增 `_answers_text()` **优先用结构化答案**（带选项 key），
单题时回退 `note`（保持原行为）。
**实测**：带 `answers` 的 approve 被接受（200，未被 422 拒）。

### F. 两道门的先后顺序 ✅
**核实**：通用审批门（`reg.needs_approval`）与渲染确认门的相对顺序决定了
「谁显式配了审批 render_video 时用户看到哪张卡」。

**修法**：通用门**命中即返回**，天然优先——显式配置的人拿到那道门的语义
（逐条列出待批工具、批准/拒绝）；默认配置下没有工具需审批，渲染一律走带
**编排预览**的门，需求 2 不受影响。

## 结构性改造 5：没挂 WS 的副本也攒一份（2026-10-02 已做）

### 判断的翻转

`broadcast.py._listen` 原来对「本地查无这条 session 的连接」的帧**整条跳过**，理由写在
docstring 里：不想按「会话数 × 副本数」吃内存。代价是同一段 docstring 承认的那条边界——
浏览器被别的副本接走时，新副本本地没攒过，重连补不回**接管之前**的进度。

这一轮把「不投递」留下、把「不攒」翻掉：新增 `ConnectionManager.buffer_only(payload)`，
只写环形缓冲、一个字节都不投（投递仍只走 `route`，直播路径一字未改）。

顺带同一处也修掉一个更早存在的洞：**单副本开了广播**时，WS 恰好不在本实例上（用户关了标签页、
纯 REST 驱动的 run）的帧以前被直接丢弃，现在留在预算里等重连。

### 内存怎么封住（这是这条判断当初的全部理由）

| 上界 | 默认 | 语义 |
|---|---|---|
| `shadow_sessions` | 64 | 占预算的会话条数（LRU） |
| `shadow_frames` | 2000 | 这些会话合计帧数 |

超了**整条**丢掉最久没人碰的那条会话，不按帧截断——留下半截进度比什么都不留更容易被误当成全部。
本地挂上连接 → 退出预算（改由每会话 `buffer_size` 那条 deque 兜底）；最后一条本地连接断开 →
并入预算。`route` 里退回本地投递的那一支（broker 不可达）同样记账，不然那份缓冲没有任何淘汰机会。

两处顺带堵掉的无界增长：`ConnectionManager.sent` 与 `OutboundBroadcaster.published` 是观测计数，
以前**每帧永久追加一份**（帧里带整段工具结果与媒体载荷），长跑必漏；现在是有界 deque（`obs_limit`，
默认 500）。

### 一条必须写下的测试坑

`sent` 从 `list` 换成 `deque` 之后，既有断言 `cm_a.sent == []` **静默恒为 False**
（`deque([]) == []` 不成立）。它是这次改完跑测试才炸出来的，不是先想到的——凡是把观测容器
换成有界类型的改动，先 grep 一遍对它做等值比较的断言。

验证：`tests/test_outbound_broadcast.py` **37 项**（新增 ⑤「跨副本影子预算的有界性」13 项：

`shadow_sessions=0` 退回老口径、无 `session_id` 不攒、两个观测计数有界；② 里那条

## 结构性改造 6+7：连接池参数与环境变量名（2026-10-02 已做）

### 7. `.env.example` 里那两把没人读的 key

审计的原话是「要么支持、要么删掉」。选了支持，因为**删掉才是说谎**：填了
`DEEPSEEK_API_KEY` 的人期望它能用，而它确实只是一个环境变量名的差别。

现在优先级链只有一层「环境」，但一层里有三个名字（`secrets.ENV_KEY_NAMES`，按此顺序取第一个非空）：

1. 页面「设置」里按用户存在 PG 的 key（`app_secrets`，最高，不变）；
2. `OPENAI_API_KEY` → `DEEPSEEK_API_KEY` → `SILICONFLOW_API_KEY`（同一层，**不是三把 key
   叠三层**：它们是同一家兼容网关的不同叫法，同时填时先到先得）；
3. 进程内回落常量（只在两者都没有时才用）。

空白串算「没填」而不是「填了个空」——`.env.example` 里那三行都是 `KEY=`，被 `.env` 原样
复制过来时会把空值塞进环境，旧代码用 `os.environ.get(...) or` 恰好躲过了这一点，
新代码要显式 `.strip()` 才不后退成 bug。

改动点：`secrets.py`（`ENV_KEY_NAMES` + `env_api_key()`，`resolve_api_key` 复用它）、
`llm_openai.py`（构造时的 fallback 与「没配 key」那条 RuntimeError 都走同一条链，
不再各写各的名字）。**回传的 source 只有变量名，值全程不进日志、不进返回值**；
展示仍必须先过 `mask()`。

### 6. PG 连接池

`PgDatastore.__init__` 以前只接 `pool_size`（默认 5），现在多三条并全部由 `build_storage`
从环境读（都有默认值，不配也跑；**没加进 `ENV_KEYS` 必填清单**，缺了不该拒绝启动）：

| 环境名 | 默认 | 为什么要 |
|---|---|---|
| `PG_POOL_SIZE` | 5 | 原有 |
| `PG_POOL_MAX_OVERFLOW` | 10 | 长任务与 HTTP handler 共用这一池，池满时溢出几条比排队等超时好 |
| `PG_POOL_PRE_PING` | 1（开） | 容器重启或 PG 掐掉空闲连接后池里那条是死的，不 ping 就是一次 `StorageUnavailable` |
| `PG_POOL_RECYCLE_SEC` | 1800 | 比 pre_ping 更便宜的兜底，连接活够久就换新 |

三条都写进 `.env.example` 并带上原因注释。断言打在**真池对象**上
（`engine.pool._max_overflow/_pre_ping/_recycle`），不是打在构造函数参数上——参数传对了
但 SQLAlchemy 没吃进去，这一样测不出来。

验证：`tests/test_model_settings.py` **69/69**（新增 `case_env_alias_names` 8 项：名字与顺序、
只填 DEEPSEEK 能用、OPENAI 优先、空串跳过、SILICONFLOW 兜底、构造器走同一条链、source 不带值、
`mask` 仍是必需步骤；另外把 6 处只 pop `OPENAI_API_KEY` 的存/取现场换成
`clear_env_keys()`/`restore_env_keys()`——环境层开始读三个名字之后，只清一个会让用例结果
取决于本机恰好填了什么）；`tests/test_storage.py` **125/125**；`python -m pytest` **58/58**；
`python scripts/run_eval.py` **4/4**，指纹 `2026-10-01.v2:cbf36a96` 不变。

## 结构性改造 4：规划轮整段落进提示词库（2026-10-02 已做）

清单里最后一条「文案硬编码在 .py」的口子。`prompts/` 早就在跑（系统提示 + 5 类纠错说明），
但**规划轮那一段**——模型每轮规划收到的那段最长、最能决定行为的 system 文案——仍然由
`plan/prompt.py` 的代码拼接：改一句话要动代码、过评审、重新发布。

### 搬什么、不搬什么（这一条决定成败）

搬过去的只能是**措辞**与**哪一段出现**；**数据仍然由代码算**。段里两处插的是
`gate.whitelist()` 的节点名单和 `gate.knob_facts()` 的可上卡开关，这两份和服务端卡面校验
是同一份判据——一旦让模板自己去拿，就变成「提示词里写的开关和真校验的开关各说各话」。

于是渲染器只加了两条规则（`prompts.render_blocks`），没有第三条：

1. 模板按**空行分块**；块首独占一行的 `{?key}` 是守卫，这个键没值就整块不出现；
2. 块内某行渲染后为空（它本来只有 `{data}` 而这次没数据）→ 丢掉这一行，不留空行。

刻意不做 if / for / 嵌套 / 子模板。真加了那些，这一步就不是「改文案不必改代码」，
而是往仓库里塞一门模板语言，把评审成本换成调试成本。**判定标准是能不能一眼看出
「这条消息进来会出现哪几段」**——现在能。

### 先捕获金样，再动刀（唯一可信的等价判据）

迁移前先从**旧代码**逐字捕获 9 条渲染结果落进 `tests/data/planning_round_golden.json`
（最小 / 待确认卡开关 / 换一版旧卡 / 反馈原话 / 待续跑 / 同会话历史 / 全开 / 无节点无开关 /
有节点无开关，最长一条 1897 字符）。改完之后拿这九条比对，**要求字符串相等**，
不比「意思差不多」：多一个空格少一个换行，模型的行事方式都可能漂。

`tests/test_planning_prompt_golden.py` 拿同一批输入跑两遍——一遍 `prompt_library=None`
（内联回落，即提示词目录没拷过去的环境），一遍仓库自带的 `prompts/planning_round.md`
（生产默认读的那份）——两条路径都必须逐字等于金样。

### 写渲染器时踩到的四条（都有用例钉住）

- **块之间收成一个换行**：`render_blocks` 用 `"\n"` 重新拼接幸存的块，不保留原文的空行。
  金样能对上正是因为旧代码也是逐段 `"\n".join`。第一次写测试时以为会留空行，红了。
- **先切块再替换**：值本身可以带空行（`{knobs}` 是多行清单）。若先替换再切块，
  值里的空行会被当成块边界、里面的行首 `{?…}` 会被误当守卫。所以切块必须在替换之前。
- **守卫必须独占一行**：`写在行中 {?has} 不算守卫` 原样输出。宽松匹配会吃掉正文。
- **只含空白的值算没值**：`"   "` 若当真存在，会留下一段只有标题没有内容的空壳文案。

### 内联回落留着，所以 `prompt.py` 反而长了

`_PLANNING_TEMPLATE` 与磁盘那份**逐字相同**，两边各留一份是设计（目录没拷过去也要能跑），
代价是 `plan/prompt.py` 从 255 行涨到 269 行、`prompts.py` 从 139 涨到 199 行。
这一轮省的不是行数，是「改文案要不要动代码」。两份的漂移由 `test_prompt_library.py`
的守卫钉住（模板那份只允许行尾空白差，比 `system_prompt` 那条「空白归一」更严——
块结构本身是语义）。

### 接线：差点又是一个「写了但没人接」

`run_server.build_runtime` 里 `prompt_library` 原本构造在 `PlanGate(...)` **之后**，
直接传会变成传 `None`——模板写了、金样全绿、生产从来没读过它。把库的构造挪到计划门之前，
并给 `PlanGate` 加 `prompt_library` 形参（只有一个消费者：`prompt.planning_section`）。

这条不是靠人记住的：`test_planning_prompt_golden.py` 的第 ⑥ 组用 AST 读出
`run_server.py` 里 `PlanGate(...)` 调用的关键字实参，缺 `prompt_library` 就红，
顺带用文本序断言库构造在门之前。**Bootstrap 机制当年就是死在「实现了但装配里没传」**
（`bootstrap_dir` 一直没传），同一个失败模式不允许再犯第二次。

### 顺手补完 R11 的最后一块：子 Agent 的 system 提示词

根因报告的 R11 要的是四份东西落盘：系统提示 / 规划轮段 / 5 类 nudge / **子 Agent 提示词**。
前三份上一轮就接了，第四份一直硬编码在 `subagent.py`。既然都在改同一套机制，一并搬进
`prompts/subagent_system.md`（内联那份仍是逐字回落）。

搬的时候踩到一个和上一段同族的坑：`SubAgentRunner.__init__` 的形参默认值写的是
`child_system_prompt: str = CHILD_SYSTEM_PROMPT`——**默认参数在 import 时就定格了**，
