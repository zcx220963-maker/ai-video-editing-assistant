## 已修（A–F，均已提交并回归）

### A. 刷新后挂起的弹窗不会重新弹 ✅
**核实**：`server.py` 一直在回 `run.approval`（含结构化 `ask`），但
`App.vue` 的 `checkActiveRun` 只判 `status === "running"`，`approval` 一个字没读。
用户在等确认时刷新 → 后端永久挂起、界面无可点，只能整页重开。

**修法**：`checkActiveRun` 增加 `awaiting_approval` 分支，把服务端那份 `approval`
还原成 WS 帧的同一形状，复用 `approvalBubble`（同一条渲染路径）。
**实测**：`GET /convs/{id}/runs/active` 在挂起时回 `approval`，含题面 + 4 个选项 + run_id。

### B. 定时任务跑到渲染会永久死锁 ✅
**核实**：cron 投递（`run_server.py` `action.op="execute"`）已显式跳过计划门，
但渲染门只认**进程级** `AgentConfig.gate_render`，照样拦。挂起后
`awaiting_approval` 刻意不在 `_UNFINISHED` 里、自动续跑捞不到，而审批端点要
`_owned_run_row`（那条 run 的 `user_id="cron"`）——浏览器永远过不了归属校验。

**修法**：把「有没有活人在等」变成 **per-run 事实**而不是进程常量：
`handle/run/_drive` 加 `interactive`，consumer 收到 `op="execute"` 传 `False`，
两道确认门据此放行。单副本定时任务不再可能卡死在等确认上。

### C. 非 WS 客户端拿不到弹窗 ✅
**核实**：`/chat/sync` 只回 `answer`（一句「已暂停」），`ChatSyncResponse` 没有
`approval`/`ask`；`scripts/run_live.py` 里 `approve|approval|ask` 零命中——
真机验证弹窗只能走浏览器。

**修法**：`ChatSyncResponse` 加 `status` + `approval`（`answer` 保留，旧客户端不受影响）。
并把 approval 视图抽成 `_approval_payload` **一处拼装**，`/chat/sync` 与
`/convs/{id}/runs/active` 共用，形状不会漂。
**实测**：`/chat/sync` 返回 `['answer','approval','run_id','status']`，
`approval.ask` 带题面与 4 个选项。

### D. fork 之后编排预览读的是错作用域 ✅
**核实**：`_load_preview` 写死 `_default`，而 `rerun_from` 分叉给子 run 生成
`art-xxxx` 作用域（`checkpoint.fork`），子 run 产物写在自己那份里。

**修法**：两处
1. `_load_preview` 取**当前生效作用域**（`identity.artifact_id`）而不是固定 `_default`；
2. `GET /preview/{conv}` 的 `artifact_id` 留空时不再盲取 `_default`，而是回退到
   「本会话**最近写过产物**的那个作用域」——分叉后预览显示的是这一次的编排，不是父 run 的旧编排。

### E. 多题弹窗的答案数组被静默丢掉 ✅
**核实**：前端发 `{decision, message, answers}`，`RunApproveRequest` 只有
`decision`/`message`，pydantic 默认忽略多余键——靠前端把 answers 拼成中文句子
塞进 `message` 才没丢信息。

**修法**：`RunApproveRequest` 补 `answers` 字段 → 审批帧带上 → `Agent.approve`
→ `_settle_pending`；新增 `_answers_text()` **优先用结构化答案**（带选项 key），
单题时回退 `note`（保持原行为）。
**实测**：带 `answers` 的 approve 被接受（200，未被 422 拒）。

### F. 两道门的先后顺序 ✅
**核实**：通用审批门（`reg.needs_approval`）与渲染确认门的相对顺序决定了
「谁显式配了审批 render_video 时用户看到哪张卡」。

**修法**：通用门**命中即返回**，天然优先——显式配置的人拿到那道门的语义
（逐条列出待批工具、批准/拒绝）；默认配置下没有工具需审批，渲染一律走带
**编排预览**的门，需求 2 不受影响。

## 结构性改造 3：临时键收敛为显式状态（2026-10-02 已做）

新增 `agent_framework/run_state.py`：`RunState`（dataclass）+ `tool_names_in()`。
原先挂在 `ctx.extras` 上、**不进 checkpoint** 的 7 个键全部收进这一份显式状态，
落在 `cp.plan["state"]`（JSON 列，无迁移），在每次一致点 / 挂起点 / 失败路径随 checkpoint 落盘，
`_drive` 入口 `RunState.restore(cp)` 还原：

| 键 | 收敛后 |
|---|---|
| `approved_plan` | `RunState.approved_plan` |
| `tool_calls_seen` | `RunState.calls_executed`（对账口径：真打到注册表的） |
| （新增硬保证口径） | `RunState.calls_attempted`（含失败，执行轮「一次步骤都没调用」判据用） |
| `plan_candidates` / `plan_warnings` | 同名，随指针行 `plan.candidates/warnings` 一起还原，不重复落 JSON |
| 计划卡是否已推 | `RunState.plan_card_pushed`（续跑不再推第二张一样的卡） |
| 对账帧是否已推 | `RunState.audit_pushed`（挂起前后跨 `_drive` 去重，原来只在当轮去重） |
| `plan_audit` / `qa_parts` | 同名；`qa_parts` 落盘 → 续跑不再丢半截转写、`prompt_fingerprint` 不再重复 |

`ctx.extras` 只留真正的每轮注入：`run_id`、`checkpoint`、`checkpoint_manager`、`handover`、
`confirm_plan_requested`、`_fail_counts`、`_media_urls_pushed`。

顺带修掉两个做这一项时撞出来的真缺陷：

* `ask_user` 被对账当成「计划外一步」（角标显示计划外 1 步 · 向用户提问）——提问是交互动作，
  不是多做出来的一步创作，已并入 `NON_STEP_TOOLS`。
* 批准后的编译计划原先**没有任何持久落点**（只在 `ctx.extras` 活一轮）：外部驱动的 fork
  因此丢掉执行轮硬保证。现在 `retain_residue` 在收尾时只留 `approved_plan` 这一份残值，
  `CheckpointManager.fork` 把父 run 的这份继承进子 run。

验证：`tests/test_run_state.py` 34 项（往返 / 指针行还原 / 挂起→续跑端到端：对账帧在续跑后
仍出现且跨挂起恰好 2 帧、assistant 行 `qa.parts` 含三个节点、恰好一条 `prompt_fingerprint`、
残值只留 `approved_plan` / fork 继承承诺但不继承转写与父结论）；
`tests/test_plan_gate.py` 145 项、`python -m pytest -q` 全量 57/57 绿。
