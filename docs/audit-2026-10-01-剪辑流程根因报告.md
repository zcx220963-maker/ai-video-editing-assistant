## 1. 为什么"任务总是断" —— 四个断点，全部复现

### 断点 1（最致命）：MoviePy 打不开带章节的素材 → 永远出不了成片

```
moviepy/video/io/ffmpeg_reader.py:414   input_chapters = []          ← 只建了空表
                          :499   input_chapters[input_number].append(..)  ← 直接下标
```

章节在 ffmpeg 输出里排在流信息**之前**，所以第一次碰到 `Stream #` 行、走"退出章节"分支时
`input_chapters` 还是空表 → `IndexError: list index out of range`
→ 被包装成 `OSError: Error passing 'ffmpeg -i' command output`。

同一个函数里处理章节的另一个分支（:229）**是有边界检查的**，只有这处漏了。上游疏漏。

**为什么这个 bug 特别坑**：

- 触发条件极常见：HandBrake 转码、蓝光/DVD 抓取、B站等站点下载、带章节的录屏——都有章节块。
  我用的测试素材（788KB 小视频）就带 `Chapters:`。
- 报错文本被视图截断（真机上 render_jobs 只存了一段开头），表现是
  「render_video 卡在 video_track 10%」「ffmpeg 读源文件中断」，
  排查方向会被带偏到路径、编码、并发上。
- 它同时让 MoviePy 主路径**和**两条兜底路径的定位变得不可能（见断点 4）。

**现场证据**：修复前，执行轮跑到 14 轮、切镜头/理解/筛选/分组/文案/配音/时间线全部正常，
卡在最后一步：

```json
{"render": {"status": "failed", "stage": "video_track", "percent": 10,
  "error": "MoviePy 失败: Error passing `ffmpeg -i` command output: ..."}}
```

**修复后实测**（同一份素材，走真 MoviePy 合成 → 出文件 → ffprobe 校验）：

```
源素材: mat-809a7b.mp4 (788493 B, 带 Chapters)
成片已生成: .runtime/audit/render_proof.mp4 (131310 B)
  ffprobe: duration=3.0 size=320x176 fps=25.0 has_audio=True
结论: 成片可用（媒体链路已通）
```

### 断点 2：规划轮"用嘴交了计划卡" → 界面上永远没有卡，用户点不了确认

规划轮的硬保证是"必须 `submit_plan` 出一张卡"。原来靠**文本措辞**判断模型有没有假称：

```python
_CARD_NOUN = re.compile(r"(计划卡|续跑卡|候选计划)")
_CARD_DONE = re.compile(r"(已(?:经)?(提交|生成|出卡|发出|回投|给出|送到|挂上)|提交成功|等你确认|请确认)")
```

真机原文（我复现到的两版）：

> 「已为你准备好 3 个**候选方案**（都基于素材 mat-e2c888，目标成片约 20 秒）……
>  **p1 · 标准流程** … **p2 · 高光精选** … **p3 · AI 转场版** …
>  你在**计划卡上选一版确认即可**。」

实测两版都判不中（`claims_plan_card=False`）：它写"候选**方案**"而不是"候选计**划**"，
写"选一版确认即可"而不是"请确认"。于是：

1. 守卫不触发 → 模型不重试 `submit_plan`；
2. 规划轮以一句口头方案收尾，`/plans/{id}` 回**零张卡**；
3. 用户看到一段像是"已经给了方案"的话，但界面上没有任何可点的东西 → 流程死在这里。

**这是"剪辑流程跑不起来"最直接的那个断点**，因为它发生在第 1 步：卡都没有，后面全不用谈。

### 断点 3：撞迭代上限被判成"成功结束"，半成品再也接不回来

```python
iteration = 40 的时候跳出循环
final = f"[已达最大迭代次数 {N}，提前结束]"
await self.checkpoint.complete(cp, ...)      # ← 标成 completed
```

`_UNFINISHED = {running, failed}` 不含 `completed`，于是：

- `/convs/{id}/runs/active` 查不到这条 run；
- `consumer` 的自动续跑也捞不回来；
- 用户刷新后接不上，只能重开。

真机会话里已经有一批以 `[已达最大迭代次数 N，提前结束]` 收尾的记录。

更糟的是预算三处不一致：`AgentConfig` 默认 10、`build_runtime` 默认 40、
**CLI 默认 20 且会覆盖前两者** → 实跑 20。整链剪辑十几步工具调用 + 每步一轮 LLM，
20 轮**必然**在半路耗尽。这是确定性的，不是偶发。

### 断点 4：三条渲染兜底路径里，两条在这台机器上 100% 失败

```python
list_file.write_text("\n".join(f"file '{p.absolute()}'" for p in parts))
#                                       ↑ Windows 反斜杠
```

ffmpeg 的 concat 解复用器把 `file '...'` 里的反斜杠当**转义字符**：
`C:\Users\xu'zhi'cheng\Desktop\智能创作助手\...\000.mp4`
→ 被吞成 `C:UsersxuzhichengDesktop智能创作助手...000.mp4`。

实测（我用真 ffmpeg + 同形状路径做的对照实验）：

```
测试目录: ...\xu'zhi'cheng\智能创作助手\render
旧写法（不转义）：失败  rc=4294967294  Impossible to open 'C:Users...000.mp4'
新写法（转义）：  成功  duration=2.00s
```

**后果**：MoviePy 主路径一失败，节点就提示用户"改用简化渲染 / 分段渲染"——
这两条在这台机器上**永远失败**，等于把人引到两条死路，而报错是天书。

## 2. 乱在哪 —— "同一份事实存在多份副本"

这是**所有断点的共同根因**。举最有代表性的一例，同一个工具在四处有四个名字/四种说法：

| 来源 | 它认为这个工具叫什么 |
|---|---|
| 生产提示词（`plan_gate.py` 每轮注入） | `read_node_artifact` ← **这个名字根本不存在** |
| 真实工具表（`video_editing.py`） | `read_node_history` |
| 计划门白名单 | 两个都不在（它本来就不是剪辑节点） |
| 服务端 DAG 契约 | 它不是一个节点 |

模型没有"猜对"的义务，所以整条链以"莫名其妙的失败"反复断掉，
**每次断的口子不同**（有时是假工具名、有时是缺 `keep_clips`、有时是超上下文），
但根因是同一个。

同类副本清单：

- 节点中文名：`plan_gate._hints`（只覆盖 10/19）、`catalog.PARAM_LABELS`、前端打包产物里的 40 项 map —— 三份。
- `max_iterations`：10 / 40 / 20 —— 三处，且 CLI 覆盖生效。
- "最近一条被打断的执行轮"：`repositories.py` / `checkpoint.py` / `plan_gate.py` —— 四处各自线性扫，定义互不一致。
- 节点必填参数：`_obj()` 恒 `required: []`，而 `process()` 里 6 个节点硬报错。

**关于"是不是真的动态加载"**：我实测了每一条注入路径：

| 层 | 真的动态吗 |
|---|---|
| 工具 schema | ✅ 真动态（MCP `tools/list` 自动来，含 title/inputSchema） |
| 工具中文名 | ✅ 真动态（MCP title → catalog） |
| 技能清单/正文 | ✅ 真动态（SKILL.md 扫盘 → PG + MinIO） |
| 节点依赖/读写集 | ✅ 真动态（`dag_contract` 结构化取回） |
| **系统提示词** | ❌ 100% 静态，硬编码在 `context.py` |
| **规划轮整段提示词** | ❌ 100% 静态，硬编码在 `plan_gate.py`（1356 行的文件里） |
| **5 类纠错 nudge** | ❌ 100% 静态，硬编码在 `agent.py` |
| **子 Agent / 剪辑 Agent 提示词** | ❌ 静态，散在 `subagent.py` / `team_tools.py` / `editing_agent.py` |
| **Bootstrap 提示词文件机制** | ❌ 代码写了（`context.py:129-144`），**生产从未接线**（`bootstrap_dir` 恒 None） |

所以你的设计意图是"提示词和 skill 动态加载"，实际只实现了工具和 skill 那一半；
本该承担"提示词从磁盘加载"的那个口子（Bootstrap）**根本没接上**，
只有测试文件用过它。这就是"明明是按动态加载设计的"却名不副实的直接证据。

## 4. 还没修的（按性价比排序，都有复现证据）

### 应该马上修 —— 影响成功率

**R2. 画面时长与配音时长不对齐 → 成片尾部定格 + 音轨被截断**
`_build_timeline` 里 `t = max(t, g_start + vo["duration"])` 只推进时间指针、不给画面补事件。
实测：画面 1.5s / 配音 6.0s → 计划 6.00s、成片 format 6.000s 但**音轨只有 1.499s**，
后半段画面卡在最后一帧、字幕还在滚。真实场景（60~120 字旁白 ≈15-30s vs 2 个短镜头 ≈7s）
**几乎必然触发**。这次真机跑通的那条恰好时长对得上，所以没暴露。
**修法**：vo 比画面长时用空镜池继续铺满到 vo 时长；`duration` 以 `timeline.duration` 为准。

**R3. 渲染看门狗把自己正在跑的长渲染判死**
ffmpeg 路径只在开头写 1 次进度（60%）、分段路径全程 0 进度，而 `render_stall_sec=600`
会把"没进度"判死并 `task.cancel()`；`finally` 里又把 `_tasks` 的 key pop 掉 → 重试会
**并发开第二份渲染写同一个固定名目录**（现场有 69 个分段分两波时间戳，互相覆盖）。
**修法**：每切一段就 notify 写进度；`_fb_*`/`_seg_*` 目录名带 attempt id；reap 后到旧任务真正结束前禁止重投。

**R4. 自动续跑吞掉用户新指令 + 所有帧挂在前端不认的 run_id 上**
`consumer` 无条件 `agent.resume(cp.run_id, ...)`（**不带 message**），而 `/chat` 回的是**新 uuid**，
前端 `p.run_id !== busy[cid]` 的守卫把每一帧都丢掉。
用户看到：发一条消息后气泡永不回复，刷新后消息连同回复一起消失。
**修法**：message 与 `cp.message` 不同就按新消息走 `plan()`；续跑必须回投一帧真实 run_id。

**R5. `answer` 帧不入环形缓冲 + 前端重连不复读历史**
`connection_manager.py` 对 answer 直接 return，还清掉该 run 的进度帧；
前端 `ws.onopen` 只重开 socket，而 `loadHistory` 被 `if (histories[cid]) return` 挡住。
断连恰好落在收尾那几秒 → 答复永久不显示（要整页刷新）。

**R6. 计划卡上的"自动补齐"提示与实际契约不一致**
`_check_topology` 的注释仍写着"前置没上卡是允许的（拦截器会补齐）"，
但 `require_explicit_call` 那几个不会。注释已过期，读代码的人会被误导。
（行为本身已由新增的 `_check_explicit_deps` 兜住，只差把这句注释改对。）

### 应尽快修 —— 影响成本与稳定性

**R6. MCP 客户端把"超时"当可重试异常** → `asr`/`understand_clips` 超时后整段重跑一遍，双倍时间与 API 费用。
**R7. `asr` 单次调用上限可超过传输超时**：音频 >6分40秒 时 `timeout = 60+1.5×秒` 必然 > `tool_timeout=600`，随即被 R6 再跑一遍。
**R8. 记忆无上限**：append 200 次 → 30489 字符，每轮**全量**注入 system，而压缩器不看 system 段。配合下一条会打爆上下文。
**R9. token 估算偏 4~6 倍**（`len(text)//4`）且装配段（memory/skills/工具 schema/planning 段）不参与压缩。工具 schema 一项就 ≈6983 token，而预算 `DEFAULT_MAX_CONTEXT_TOKENS=8000`。
**R10. 渲染代查最长 1800s 不落 checkpoint、不续租、占死一个 MQ 分区**（4 个分区，同分区其它会话一起被阻塞）。

**R11. 把提示词从 .py 里搬出来。** Bootstrap 机制已经写好但没接线。接上它，
