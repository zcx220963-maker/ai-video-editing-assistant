# 整体流程全览

## 1. 整体数据流

---

## 2. 不同用户是怎么区分的？

假设有三个用户：用户 A、用户 B、用户 C。
他们发送消息后，系统不会只用"用户 A"来标识请求，而是进一步区分具体会话。

```text
A + 对话1 → Session A1
A + 对话2 → Session A2

B + 对话1 → Session B1

C + 对话1 → Session C1
```

所以：

```text
user_id + conversation_id
             ↓
        唯一 Session ID
```

这就解决了一个关键问题：**同一个用户可以同时拥有多个独立会话。**

---

## 3. 不同 Session 怎么进入 Agent？

Session ID 会作为消息路由依据。例如假设有 3 个 Partition：

```text
Session A1 ─────→ Partition 0
Session A2 ─────→ Partition 1
Session B1 ─────→ Partition 2
Session C1 ─────→ Partition 0
```

注意：**不是一个 Session 一个 Partition**，而是：

```text
很多 Session
    ↓
按照 session_id 做路由 / hash
    ↓
有限数量的 Partition
```

所以：

```text
Partition 0
├── A1
└── C1

Partition 1
└── A2

Partition 2
└── B1
```

---

## 4. 为什么这样可以支持并发？

核心是：**同一个 Session 串行，不同 Session 可以并行。**

例如：A1 是"我的订单"，A2 是"那什么时候发货？"（同一个用户接着说）；
B1 是另一个用户"帮我查一下课程"；C1 是"今天天气怎么样"。

A1、A2 不能乱序，否则第二句话可能在第一句话处理完之前就执行。
但 B 和 C 没必要等待 A：

```text
Session A ──→ Agent Worker 1
                  │
                  └── A1 → A2 → A3

Session B ──→ Agent Worker 2
                  │
                  └── B1 → B2

Session C ──→ Agent Worker 3
                  │
                  └── C1 → C2
```

因此：**同 Session：串行；不同 Session：并行。**

---

## 5. Agent 拿到消息之后做什么？

Agent 收到消息以后，并不是直接把消息扔给 LLM。大致是：

```text
收到 Session A1
      ↓
Session Manager
      ↓
找到 Session A 的历史记录
      ↓
Context Builder
      ↓
构造完整上下文
      ↓
AgentOnceRun
      ↓
LLM
      ↓
需要工具？
   ┌──┴──┐
   │     │
  否     是
   │     │
   │   Tool Registry
   │     ↓
   │   Tool Execute
   │     ↓
   └─────┘
      ↓
生成最终结果
```

所以 Session Manager 解决的是**"这个会话之前聊了什么"**，
而 MQ 的 Session 路由解决的是**"这个请求属于哪个会话、应该由哪个处理通道处理"**。
这是两个不同的问题。

---

## 6. Agent 返回结果以后怎么找到正确用户？

```text
Agent
 ↓
MQ OutBound
 ↓
MQ Consumer
 ↓
Connection Manager
```

Connection Manager 根据 `session_id` 找到对应的 Web 连接：

```text
Session A1 → WebSocket 连接 A1
Session A2 → WebSocket 连接 A2
Session B1 → WebSocket 连接 B1
```

于是：

```text
Agent 处理 A1
      ↓
结果携带 session_id = A1
      ↓
Connection Manager
      ↓
找到 A1 对应连接
      ↓
发给用户 A 的"对话1"
```

这样即使用户 A 同时开着对话 1 和对话 2、用户 B 也有会话，同时都有请求，
结果也不会串到别人的窗口。

---

## 最终可以记成 4 个核心问题

```text
① 谁发的？        → user_id
② 哪个会话？      → conversation_id
③ 怎么处理？      → session_id → MQ Partition → Agent
④ 结果发给谁？    → session_id → Connection Manager → 对应 Web 连接
```

整个系统本质上就是：

```text
                 ┌──── Session A1 ────┐
用户 A ──→ Web ──┤                     ├──→ Agent ──→ Web
                 └──── Session A2 ────┘       ↑
                                               │
                 ┌──── Session B1 ─────────────┤
用户 B ──→ Web ──┤                             │
                 └──── Session B2 ─────────────┘
                                               │
                 ┌──── Session C1 ─────────────┘
用户 C ──→ Web ──┘
```

**一句话概括：**
系统先用 `user_id + conversation_id` 唯一确定 Session，再用 Session 做 MQ 路由，
让同一 Session 保持有序处理、不同 Session 能并行处理；Agent 处理时通过
Session Manager 恢复上下文，处理完成后再通过 Session ID 找回对应 Web 连接，
把结果准确返回给对应会话。

# Agent Loop

## Agent Loop 和 Harness 的区别

- **Agent Loop** 解决"智能体怎么循环思考和行动"；
- **Harness** 解决"这个循环怎么被工程化地约束、管理和稳定运行"。

```text
（原稿此处为站内图，按文字重绘）

Main Loop（常驻，while True）—— 不断响应用户请求
  └─ 每来一次用户请求
       └─ Agent Once Loop（存在最大迭代次数）
            └─ LLM ⇄ Tool Call / Tool Result 循环，直到产出最终答案
```

外面的 Main Loop 是一个 while True，用来不断响应用户的请求；
内层的 Agent Once Loop 是一个存在最大迭代次数的循环，**防止单次请求陷入无限循环**；
内层的 Agent Once Loop 符合 **ReAct 范式**。

# 工具注册和执行

## 一. 子工具类继承父 Tool 类

Tool 是所有工具的抽象父类，统一规定工具必须提供的属性和执行入口，
具体业务由子工具实现。

Tool 类继承 `ABC` 声明为抽象类，定义了子工具类的内部方法。

### 1. 必须重写的方法（注册工具：名称、描述、参数、方法逻辑）

```python
@property
@abstractmethod
def name(self) -> str:
    """工具名称 used in function calls."""
    pass

@property
@abstractmethod
def description(self) -> str:
    """工具描述 of what the tool does."""
    pass

@property
@abstractmethod
def parameters(self) -> dict[str, Any]:
    """工具参数 JSON Schema for tool parameters."""
    pass

@abstractmethod
async def execute(self, **kwargs: Any) -> Any:
    """
    Execute the tool with given parameters.
    Args:
        **kwargs: Tool-specific parameters.
    Returns:
        Result of the tool execution (string or list of content blocks).
    """
    pass
```

### 2. 非必须重写的方法

**（1）辅助解析 Tool 参数的 JSON Schema 类型**

```python
_TYPE_MAP = {
    "string": str,
    "integer": int,
    "number": (int, float),
    "boolean": bool,
    "array": list,
    "object": dict,
}

@staticmethod
def _resolve_type(t: Any) -> str | None:
    """
    Resolve JSON Schema type to a simple string.
    JSON Schema allows ``"type": ["string", "null"]`` (union types).
    We extract the first non-null type so validation/casting works.
    """
    if isinstance(t, list):
        for item in t:
            if item != "null":
                return item
        return None
    return t
```

**（2）判断 Tool 是否支持并发（目的是提高工具执行速度）**

```python
@property
def read_only(self) -> bool:
    """判断工具是否只读、无副作用（Whether this tool is side-effect free
    and safe to parallelize.）"""
    return False

@property
def concurrency_safe(self) -> bool:
    """判断工具是否可以与其他可并发工具同时执行（Whether this tool can run
    alongside other concurrency-safe tools.）"""
    return self.read_only and not self.exclusive

@property
def exclusive(self) -> bool:
    """判断工具是否需要独占执行（Whether this tool should run alone even
    if concurrency is enabled.）"""
    return False
```

## 二. 创建子工具类对象

创建子工具类对象，然后后续需要将该工具类对象作为参数传入 `ToolRegistry`
对象的 `register()` 方法，注册到 Registry 中。

## 三. 创建 ToolRegistry 类对象

```python
class ToolRegistry:
    """
    Registry for agent tools.

    Allows dynamic registration and execution of tools.
    """

    def __init__(self):
        self._tools: dict[str, Tool] = {}

    def register(self, tool: Tool) -> None:
        """注册一个工具 Register a tool."""
        self._tools[tool.name] = tool

    def unregister(self, name: str) -> None:
        """删除一个工具 Unregister a tool by name."""
        self._tools.pop(name, None)

    def get(self, name: str) -> Tool | None:
        """通过名字找工具 Get a tool by name."""
        return self._tools.get(name)

    def has(self, name: str) -> bool:
        """查看工具是否已注册 Check if a tool is registered."""
        return name in self._tools

    def get_definitions(self) -> list[dict[str, Any]]:
        """获取所有注册工具的 schema Get all tool definitions in OpenAI format."""
        return [tool.to_schema() for tool in self._tools.values()]

    async def execute(self, name: str, params: dict[str, Any]) -> Any:
        """调用 Execute a tool by name with given parameters."""
        _HINT = "\n\n[Analyze the error above and try a different approach.]"
        tool, params, error = self.prepare_call(name, params)
        if error:
            return error + _HINT

        try:
            assert tool is not None  # guarded by prepare_call()
            result = await tool.execute(**params)
            if isinstance(result, str) and result.startswith("Error"):
                return result + _HINT
            return result
        except Exception as e:
            return f"Error executing {name}: {str(e)}" + _HINT

    @property
    def tool_names(self) -> list[str]:
        """Get list of registered tool names."""
        return list(self._tools.keys())

    def __len__(self) -> int:
        return len(self._tools)

    def __contains__(self, name: str) -> bool:
        return name in self._tools
```

创建 ToolRegistry 类对象，调用其内部方法实现工具注册和调用：

```python
registry = ToolRegistry()
```

# Hook 可观测机制

## 什么是 Hook

Hook ≈ Agent 生命周期版的 Spring AOP =
在 Agent 执行链路的特定生命周期节点"插入/拦截"一段额外逻辑。

## 1. AgentHook：定义 Agent 生命周期中的 Hook 节点

```python
class AgentHook:

    async def before_iteration(
        self,
        context: AgentHookContext
    ) -> None:
        """
        LLM 调用之前执行。

        Agent 每开始一轮新的执行时，会先进入这里，
        然后才继续调用 LLM。

        这里本身只是定义一个 Hook 节点，
        pass 表示默认不执行任何操作。

        执行顺序：
            Agent 新一轮执行
                ↓
            before_iteration()
                ↓
            LLM
        """
        pass

    async def on_stream(
        self,
        context: AgentHookContext,
        delta: str
    ) -> None:
        """
        LLM 流式输出过程中执行。

        LLM 每产生一段流式内容，就可以触发一次这个方法。

        delta：当前这一段流式输出的内容。

        执行顺序：
            LLM 开始流式输出
                ↓
            on_stream()
                ↓
            继续输出
                ↓
            on_stream()
                ↓
            ...
        """
        pass

    async def on_stream_end(
        self,
        context: AgentHookContext,
        *,
        resuming: bool
    ) -> None:
        """
        LLM 本次流式输出结束后执行。

        它和 on_stream() 的区别：

            on_stream()      → 流式输出过程中执行
            on_stream_end()  → 整次流式输出结束后执行

        resuming：表示当前执行是否属于恢复/继续执行状态。
        """
        pass

    async def after_execute_tools(
        self,
        context: AgentHookContext
    ) -> None:
        """
        Tool 执行完成后执行。

        Agent 调用 Tool 的流程：

            LLM
              ↓
            Tool Call
              ↓
            Tool Registry
              ↓
            Tool Execute
              ↓
            Tool Result
              ↓
            after_execute_tools()

        所以这个 Hook 的执行时机是：Tool 执行完成之后。
        """
        pass

    def finalize_content(
        self,
        context: AgentHookContext,
        content: str | None
    ) -> str | None:
        """
        最终内容生成后执行。

        content：当前准备返回给用户的最终内容。

        与前面的 Hook 不同：这个方法可以修改 content。

        返回值：返回处理后的最终内容。

        默认情况下不修改内容，所以直接返回原来的 content。
        """
        return content
```

**AgentHook 五个方法小结**（原稿此处为飞书站内卡片，按语义重绘）：

| 方法 | 触发时机 | 能否修改内容 |
|---|---|---|
| before_iteration | 每轮迭代开始、LLM 调用之前 | 否 |
| on_stream | LLM 流式输出的每个 delta | 否 |
| on_stream_end | 整次流式输出结束 | 否 |
| after_execute_tools | 本批 Tool 执行完成之后 | 否 |
| finalize_content | 最终内容生成后 | **是（唯一）** |

## 2. CompositeHook：组合和统一调用多个 Hook

```python
class CompositeHook(AgentHook):

    def __init__(self, hooks: list[AgentHook]) -> None:
        """
        接收多个 Hook，并保存起来。

        hooks：一个 AgentHook 对象列表。
        self._hooks：CompositeHook 内部保存的所有 Hook。

        后面的各个方法都会遍历 self._hooks，
        依次调用每个 Hook 对应的方法。
        """
        self._hooks = list(hooks)

    async def before_iteration(
        self,
        context: AgentHookContext
    ) -> None:
        """
        调用所有 Hook 的 before_iteration()。

        for h in self._hooks：依次取出一个 Hook。
        await h.before_iteration(context)：调用当前 Hook 的 before_iteration()。

        所以 CompositeHook 本身不负责具体业务，
        它只是负责把调用转发给内部的每一个 Hook。
        """
        for h in self._hooks:
            try:
                await h.before_iteration(context)
            except Exception:
                # 当前 Hook 出错时记录异常。
                # 不让这个 Hook 的异常影响其他 Hook。
                logger.exception(
                    "AgentHook.before_iteration error in {}",
                    type(h).__name__
                )

    async def on_stream(
        self,
        context: AgentHookContext,
        delta: str
    ) -> None:
        """
        调用所有 Hook 的 on_stream()。

        delta 会继续传给每一个 Hook，
        因为每个 Hook 都需要知道当前的流式内容。

        执行逻辑：
            CompositeHook.on_stream()
                    ↓
            Hook1.on_stream()
                    ↓
            Hook2.on_stream()
                    ↓
            Hook3.on_stream()
        """
        for h in self._hooks:
            try:
                await h.on_stream(context, delta)
            except Exception:
                # 当前 Hook 出错，只记录异常，然后继续执行下一个 Hook。
                logger.exception(
                    "AgentHook.on_stream error in {}",
                    type(h).__name__
                )

    async def on_stream_end(
        self,
        context: AgentHookContext,
        *,
        resuming: bool
    ) -> None:
        """
        调用所有 Hook 的 on_stream_end()。

        resuming 会传递给每一个 Hook。

        作用：统一通知所有 Hook："本次流式输出已经结束。"
        """
        for h in self._hooks:
            try:
                await h.on_stream_end(context, resuming=resuming)
            except Exception:
                # 当前 Hook 出错，不影响后面的 Hook。
                logger.exception(
                    "AgentHook.on_stream_end error in {}",
                    type(h).__name__
                )

    async def after_execute_tools(
        self,
        context: AgentHookContext
    ) -> None:
        """
        Tool 执行完成后，统一调用所有 Hook 的 after_execute_tools()。

        执行逻辑：
            Tool 执行完成
                  ↓
            CompositeHook
                  ↓
            Hook1.after_execute_tools()
                  ↓
            Hook2.after_execute_tools()
                  ↓
            Hook3.after_execute_tools()
        """
        for h in self._hooks:
            try:
                await h.after_execute_tools(context)
            except Exception:
                # 当前 Hook 出错，只记录异常。
                logger.exception(
                    "AgentHook.after_execute_tools error in {}",
                    type(h).__name__
                )

    def finalize_content(
        self,
        context: AgentHookContext,
        content: str | None
    ) -> str | None:
        """
        依次调用所有 Hook 的 finalize_content()。

        这个方法和前面的几个方法不同：

            前面的 Hook：主要是触发某个生命周期节点。
            finalize_content：每个 Hook 都可以修改 content。

        所以这里需要接收上一个 Hook 返回的 content，
        再把它传给下一个 Hook。

        最终返回经过所有 Hook 处理后的 content。
        """
        for h in self._hooks:
            content = h.finalize_content(context, content)
        return content
```

**CompositeHook 的两条铁律**：

1. 转发：所有生命周期方法遍历 `_hooks` 依次调用（delta / resuming / content
   一路透传）；
2. 隔离：单个 Hook 抛异常只记 `logger.exception`，**不影响其他 Hook、更不拖垮主循环**
   ——唯独 `finalize_content` 是链式的：上一个 Hook 的返回值是下一个的入参，
   最终返回经过所有 Hook 处理后的 content。

# CronTool 设计

CronTool = 给 Agent 增加"定时执行任务"的能力。

## 1. 整体架构

```text
LLM
 ↓
CronTool
 ↓ CRUD 操作
FileSystem（保存 CronJob）
 ↓
定时调度器
 ↓
找到到期 Job
 ↓
执行 Job
 ↓
更新 Job 状态
 ↓
重新设置下一次定时器
```

**核心思想**：用文件系统持久化定时任务，用定时器负责唤醒和执行。

## 2. CronJob

每个定时任务保存类似：

```text
Job
├── id
├── enabled
├── schedule      # 定时规则
├── delete_after_run
└── state
     └── next_run_at_ms  # 下一次执行时间
```

## 3. 核心方法

| 方法 | 职责 |
|---|---|
| `_get_next_wake_ms()` | 找到所有 Job 里最近的 `next_run_at_ms` |
| `_arm_timer()` | 取消旧定时器，按最近到期时间重新 `asyncio.sleep` 布防 |
| `_on_timer()` | 到点：筛出 due_jobs 逐个执行，保存状态，重新 arm |
| `_execute_job(job)` | 执行单个 Job：单次任务删/禁，周期任务计算下次时间 |
| `_compute_next_run(schedule, now)` | 周期任务的下次执行时间 |

## 4. 调度流程

```text
_get_next_wake_ms()
        ↓
找到最近的 next_run_at_ms
        ↓
_arm_timer()
        ↓
asyncio.sleep()
        ↓
_on_timer()
        ↓
找到 due_jobs（已经到执行时间的任务）
        ↓
_execute_job()
        ↓
_save_store()
        ↓
_arm_timer()
        ↓
等待下一次任务
```

## 5. 单次任务 vs 周期任务

`schedule.kind == "at"` 表示只执行一次：

```text
执行
 ↓
delete_after_run = true  → 删除 Job
delete_after_run = false → 禁用 Job
```

周期任务：

```text
执行
 ↓
_compute_next_run()
 ↓
计算下一次执行时间
 ↓
继续等待
```

## 6. 最核心的三个动作

```text
① 保存任务
② 找最近任务并等待
③ 到时间执行并重新调度
```

## 完整代码

```python
def _get_next_wake_ms(self) -> int | None:
    # 获得每个定时任务的下次执行时间。
    """Get the earliest next run time across all jobs."""
    if not self._store:
        return None
    times = [j.state.next_run_at_ms for j in self._store.jobs
             if j.enabled and j.state.next_run_at_ms]
    return min(times) if times else None
    # 获取最近将要执行的 Job 的时间。

def _arm_timer(self) -> None:
    """Schedule the next timer tick."""
    if self._timer_task:
        self._timer_task.cancel()

    next_wake = self._get_next_wake_ms()
    if not next_wake or not self._running:
        return

    # 睡眠时间。
    delay_ms = max(0, next_wake - _now_ms())
    delay_s = delay_ms / 1000

    async def tick():
        # 睡眠。
        await asyncio.sleep(delay_s)
        if self._running:
            # 进入执行阶段。
            await self._on_timer()
    # 执行所有的 Job。
    self._timer_task = asyncio.create_task(tick())

async def _on_timer(self) -> None:
    """Handle timer tick - run due jobs."""
    self._load_store()
    if not self._store:
        return

    now = _now_ms()
    due_jobs = [
        j for j in self._store.jobs
        if j.enabled and j.state.next_run_at_ms and now >= j.state.next_run_at_ms
    ]
    # due_jobs 就是将要执行的任务。
    for job in due_jobs:
        await self._execute_job(job)

    self._save_store()
    self._arm_timer()

async def _execute_job(self, job: CronJob) -> None:
    """Execute a single job."""
    # ...
    # 只执行了一次，删除。
    if job.schedule.kind == "at":
        if job.delete_after_run:
            self._store.jobs = [j for j in self._store.jobs if j.id != job.id]
        else:
            job.enabled = False
            job.state.next_run_at_ms = None
    else:
        # ⭐️⭐️⭐️⭐️ 计算该定时任务下次的执行时间。
        job.state.next_run_at_ms = _compute_next_run(job.schedule, _now_ms())
```

## 总结

CronTool 通过文件系统保存定时 Job，调度器不断找到最近要执行的任务并等待，
到时间后执行任务、更新下一次执行时间，再重新设置定时器，
从而让 Agent 具备定时任务能力。

# 基于现有服务的扩展——MCP（CLI）

MCP（Model Context Protocol）Tool 是智能创作助手接入存量服务的关键桥梁。
存量代码中有大量社区 API 接口（定时发布、模板列表等），MCP Tool 可以非常快捷地
将这些已有服务接入，并提供给 Agent 使用。

本节三个关键认知：

1. MCP Tool 只提供 MCP **客户端**，需要配合实现了 MCP 协议的**服务端**才能工作。
2. 需要事先将 MCP 的配置写入相关文件，供 Agent 读取。
3. MCP Config 只给出 MCP Server，而 Server 提供的功能（包括 inputSchema）
   需要 MCP Client 访问 MCP Server 才能获取。

## 代码块 1：MCPServerConfig 配置模型（Python）

```python
class MCPServerConfig(BaseModel):
    type: Literal["stdio", "sse", "streamableHttp"] | None = None  # 传输类型
    command: str = ""                                                # stdio 模式：执行的命令，如 "npx"
    args: list[str] = Field(default_factory=list)                   # stdio 模式：命令参数
    env: dict[str, str] = Field(default_factory=dict)               # stdio 模式：环境变量
    url: str = ""                                                    # HTTP/SSE 模式：服务端 URL
    headers: dict[str, str] = Field(default_factory=dict)           # HTTP 模式：自定义请求头
    tool_timeout: int = 30                                           # 工具调用超时时间（秒）
    enabled_tools: list[str] = Field(default_factory=lambda: ["*"]) # 白名单：只接入这些工具
```

该模型用 Pydantic 定义每个 MCP Server 的连接与筛选信息，字段含义如下：

| 字段 | 类型 | 默认值 | 说明 |
|---|---|---|---|
| type | `Literal["stdio","sse","streamableHttp"] \| None` | None | 传输类型，决定客户端如何连接服务端 |
| command | str | `""` | stdio 模式：要执行的本地命令，如 npx |
| args | list[str] | `[]` | stdio 模式：传给命令的参数 |
| env | dict[str, str] | `{}` | stdio 模式：进程环境变量（如 API Token） |
| url | str | `""` | HTTP/SSE 模式：服务端 URL |
| headers | dict[str, str] | `{}` | HTTP 模式：自定义请求头（如 Authorization） |
| tool_timeout | int | 30 | 工具调用超时时间（秒） |
| enabled_tools | list[str] | `["*"]` | 工具白名单，只接入列出的工具；`"*"` 表示全部接入 |

## 代码块 2：MCP 配置示例（YAML）

```yaml
tools:
  mcp_servers:
    # 方式一：stdio 模式（本地进程）
    github:
      type: stdio
      command: npx
      args: ["-y", "@modelcontextprotocol/server-github"]
      env:
        GITHUB_PERSONAL_ACCESS_TOKEN: "${GITHUB_TOKEN}"
      enabledTools: ["*"]

    # 方式二：HTTP 模式（远程服务）
    internal_api:
      type: streamableHttp
      url: http://mcp-internal.company.com/mcp
      headers:
        Authorization: "Bearer ${MCP_TOKEN}"
      tool_timeout: 60
      enabledTools: ["query_employee", "search_docs"]

    # 方式三：SSE 模式
    knowledge_base:
      type: sse
      url: http://kb.company.com/mcp/sse
      enabledTools: ["search_knowledge", "get_document"]
```

三种接入方式的对比：

| 方式 | 示例服务 | 传输类型 | 关键配置 | 适用场景 |
|---|---|---|---|---|
| stdio（本地进程） | github | stdio | command + args + env，通过本地命令拉起服务进程 | 本地 CLI / npx 启动的官方或社区 Server |
| HTTP（远程服务） | internal_api | streamableHttp | url + headers（鉴权）+ tool_timeout，可配白名单 | 公司内部 HTTP 服务，如员工信息、文档检索 |
| SSE | knowledge_base | sse | url，服务端通过 SSE 推送消息 | 知识库等流式推送类服务 |

# 上下文压缩

LLM 存在上下文窗口限制（如 128k tokens）。当对话历史越来越长，token 占用持续增加，
可能超出窗口上限导致 LLM 无法处理。创作助手的上下文压缩采用**分级处理**方式，
实现对上下文更细粒度的管理。

主要的分级策略：

1. 对 Tool 的信息进行折叠。
2. 丢弃太过久远的消息。
3. 对过往消息进行全量摘要。

| 层级 | 策略 | 作用 |
|---|---|---|
| 第一级 | 对 Tool 的信息进行折叠 | 压缩工具元信息占用，只保留当前需要的工具描述 |
| 第二级 | 丢弃太过久远的消息 | 直接删除超出窗口的早期对话，控制上下文长度 |
| 第三级 | 对过往消息进行全量摘要 | 把历史内容压缩为摘要保留要点，大幅降低 token 占用 |

## 本节要点

- 上下文压缩的核心目标是在窗口限制内保留高价值信息，分级策略让管理更细粒度。
- 折叠、丢弃、摘要三者的取舍依次递进：先压缩工具信息，再淘汰旧消息，
  最后对剩余历史做全量摘要。

# 记忆系统

智能创作助手的记忆系统是**分类型**的，它没有把所有记忆都存进 Memory.md，
而是按记忆归属拆分存储。

## 记忆分类存储

- 与用户相关的记忆 → User.md（存储用户偏好）；
- 与工具相关的记忆 → Tool.md（存储用户对工具使用的反馈与注意事项，
  例如：定时发布要通过 MCP Tool 做，而不是 CronJob）。

| 记忆类型 | 存储文件 | 内容 | 示例 |
|---|---|---|---|
| 用户相关记忆 | User.md | 用户偏好 | 喜欢/不喜欢的表达风格、关注领域等 |
| 工具相关记忆 | Tool.md | 工具使用反馈与注意事项 | 定时发布应走 MCP Tool，而不是 CronJob |

## 存储与更新机制

- 目前采用单 Markdown 文件存储，每次与 LLM 交互都会携带记忆内容。
- 记忆的增删由 Agent 自主控制，通过 FileTool 写入记忆系统。
- 新记忆采用**全量覆盖写入**，以此实现删除旧记忆的目的。

## 待迭代空间

记忆系统还有较大迭代空间——并非所有记忆都需要调度进上下文窗口，
需要对记忆进行筛选。主要优化点：

| 优化点 | 现状问题 | 建议方案 |
|---|---|---|
| 存储方式 | 单文件存储容易记忆膨胀，全部带上上下文开销大 | 构建适合大量记忆的存储方式，一般是索引 + 记忆文件的方式 |
| 记忆召回 | 无法按相关性筛选记忆 | 构建记忆召回策略，采用 LLM 召回（RAG）方式，让 Agent 捕捉与当前上下文更相关的记忆（如"我爱 xxx (500)，我讨厌 xxx (500)，chunk"） |

## 本节要点

- 记忆按归属分文件存储（User.md / Tool.md），避免混在一起。
- 写入由 Agent 通过 FileTool 自主控制，全量覆盖即删除旧记忆。
- 演进方向：索引化存储 + LLM 召回（RAG），只把相关记忆调度进上下文。

# 视频剪辑的流程

视频剪辑和一般内容创作不同：它涉及多个关键节点，并且存在不同的创作路径
（起点和终点都不唯一）。因此需要一套固定范式，把视频剪辑流程**原子化**，
再通过组合使其快速适配不同的创作要求。

**核心设计：把剪辑的关键步骤建模为 Node。** 需要注意三点：

1. 流程图并不是 Workflow，而是一个 **DAG（有向无环图）**。
2. Agent 的作用是结合节点描述和用户选择，**选出**最符合的剪辑方案。
3. 视频剪辑不一定要走到 render_video，**在哪里终止取决于模型的判断与用户的要求**。

视频剪辑流程图由业务团队和产品协作给出。流程非常复杂：不仅有严格的输入输出约束，
更有复杂的剪辑路径。Agent 开发的职责就是**规范 LLM 的输出**，
使其能够适配到这些流程中，最终保证 LLM 能按上述流程交付剪辑好的视频。

| 设计要点 | 含义 | 对开发的意义 |
|---|---|---|
| 流程原子化 | 把剪辑拆成独立的 Node（加载、切分、理解、筛选、分组、脚本、配音、BGM、时间线、渲染） | 每个 Node 可独立实现、独立测试、独立复用 |
| DAG 而非 Workflow | 节点间是依赖关系，不是固定顺序的流水线 | 允许跳过、分支、多路径组合，适配不同创作要求 |
| Agent 选路 | Agent 结合节点描述 + 用户选择，决定走哪条剪辑路径 | 需要给 LLM 提供清晰的节点描述（description）与输入输出约束 |
| 终止点不固定 | 不强制走到 render_video，由模型判断与用户要求决定 | Node 编排必须允许提前终止，不能设计成必须走完 |

## 本节要点

- 视频剪辑 = 多关键节点 + 多创作路径，需要用固定范式约束。
- Node 是流程的基本单元，通过组合适配不同创作要求。
- Agent 开发的职责是"规范 LLM 输出"，使其适配业务团队给出的复杂流程。

## MCP 的触发流程和参考实现

MCP 的触发流程完全遵循传统后端开发范式，基本可以理解为 **Java Web 的范式**：

1. LLM Agent 通过 MCP Client 发起 HTTP 请求。
2. MCP 路由到相应的 Tool（路由机制由 Anthropic 的 mcp 第三方组件实现）。
3. MCP Server 执行相应的 Tool，并将执行结果通过 HTTP 响应返回。

**参考实现**：每个 Node 类（如 LoadMediaNode）被包装成一个 MCP Tool。
wrapper 负责从 HTTP 请求中解析会话信息与参数、构造 NodeState；
register 负责扫描节点包、实例化节点并按白名单注册工具。

```python
class LoadMeidaNode(BaseNode):
    ....

async def wrapper(mcp_ctx: Context, **kwargs) -> dict:
    request = mcp_ctx.request_context.request
    headers = request.headers
    session_id = headers.get('X-Storyline-Session-Id')
    # 从 HTTP 请求头中取剪辑会话 ID（session_id），用于关联一次剪辑任务。

    session_manager = mcp_ctx.request_context.lifespan_context
    if hasattr(session_manager, 'cleanup_expired_sessions'):
        session_manager.cleanup_expired_sessions(session_id)
    # 从 lifespan 上下文取会话管理器，清理已过期的会话，避免资源泄漏。

    req_json = await request.json()
    params = kwargs.copy()
    params.update(req_json.get('params', {}).get('arguments', {}))
    # 把 MCP 请求体中的 arguments 合并进调用参数，作为 Node 的执行入参。

    node_state = NodeState(
        session_id=session_id,
        artifact_id=params['artifact_id'],
        lang=params.get('lang', 'zh'),
        node_summary=NodeSummary(),
        llm=make_llm(mcp_ctx),
        mcp_ctx=mcp_ctx,
    )
    # 构造 NodeState：携带会话 ID、产物 ID、语言、节点摘要、LLM 实例与 MCP 上下文，
    # 这是 Node 执行期间共享的状态容器。

    # 这里是在执行具体的 MCP Tool。
    result = await node(node_state, **params)
    return result
    # 调用 Node（__call__ 会执行 process），把结果返回给 MCP Client。

# 注册工具。
def register(server: FastMCP, cfg: Settings) -> None:
    for pkg in cfg.local_mcp_server.available_node_pkgs:
        # 类似于 Java Spring IoC 的注入。
        NODE_REGISTRY.scan_package(pkg)
    # 扫描配置中声明的节点包，把包内的 Node 类注册进 NODE_REGISTRY
    # （类似 Spring 扫描 @Component）。

    all_node_classes = [NODE_REGISTRY.get(name=node_name) for node_name
                        in cfg.local_mcp_server.available_nodes]

    for NodeClass in all_node_classes:
        node_instance = NodeClass(cfg)  # LoadMediaNode
        input_schema = node_instance.input_schema
        # 实例化节点，并读取它的 input_schema（入参 Schema，供 LLM 生成参数）。

        tool_func = wrapper

        tool_name = NodeClass.meta.name
        tool_desc = NodeClass.meta.description
        # 工具名与描述来自 Node 的 meta 元数据。

        server.tool(
            name=tool_name,
            description=tool_desc,
        )(tool_func)
        # 用 FastMCP 的 tool 装饰器把 wrapper 注册为 MCP Tool。
```

代码段与后端概念的对应：

| 代码段 | 职责 | 对应后端概念 |
|---|---|---|
| wrapper：取 session_id | 从请求头读取剪辑会话 ID，清理过期会话 | 过滤器 / 拦截器 |
| wrapper：合并参数 | 把 MCP arguments 并入调用参数 | 请求参数解析（@RequestBody） |
| wrapper：构造 NodeState | 组装节点执行所需的共享状态 | 上下文对象 / Session |
| register：scan_package | 扫描节点包，注册 Node 类 | Spring IoC 包扫描 |
| register：server.tool | 按白名单把 Node 注册为 MCP Tool | Controller 路由注册 |

## Skill 设计

LLM 会基于 Skill.md 确定自己的剪辑流程，然后严格按照 Skill.md 进行工具编排。
Skill 分为两类：**WORKFLOW SKILL**（定义整体剪辑流程）和
**CAPABILITY SKILL**（定义单项能力，如文风仿写）。

### 示例一：通用剪辑流程 Skill（WORKFLOW SKILL）

它把整个剪辑流程写成角色 + 步骤清单，每一步标注对应工具和"可跳过/固定"属性：

```markdown
---
name: default_editing_workflow_skill
description: 【WORKFLOW SKILL】通用剪辑流程。可用于剪辑日常/旅行 vlog，或是任何
  用户需求不明确的场景。A universal editing workflow. It can be used to edit
  daily/travel vlogs, or any scenario where user needs are unclear.
---

# 角色定义 (Role)
你是一个专业的剪辑师，擅长利用现有工具和 Skills 完成剪辑任务。

常规剪辑流程如下，这里每一步都对应一个或多个工具或 Skills 供你使用：
- 搜索素材 "search_media"（可跳过）。如果你发现用户并没有上传素材，可以提示用户
  你可以上网搜索素材。搜索素材后需要运行 load_media 工具才可以真正加载到素材。
- 素材加载 "load_media"（固定）。用于获取输入素材的路径、长宽等基础信息。
- 镜头切分 "split_shots"（可跳过）。将素材按镜头切分成片段。
- 内容理解 "understand_clips"（可跳过）。为每个片段(clips)生成一段描述（captions）
- 镜头筛选 "filter_clips"（可跳过）。根据用户要求，筛选出符合要求的片段(clips)
- 片段分组 "group_clips"（可跳过，但应默认运行）。根据用户要求，对片段进行排序
  和分组，组织合理的叙事逻辑，并辅助后续文案生成。
- 文案生成 "generate_script"（可跳过）。根据用户要求，生成视频文案。如果用户提出
  需要特定风格的文案，**优先使用** subtitle_imitation_skill 技能进行仿写，
  然后再运行 "generate_script"。
- 元素推荐（可跳过，但应默认运行）。根据用户要求，推荐花字、标题、特效、转场、
  配音音色等元素。
- 配音生成 "generate_voiceover"（可跳过）。根据文案生成对应的配音。
- 背景音乐选取 "select_BGM"（可跳过）。选择合适的背景音乐。
- 组织时间线 "plan_timeline"（固定）。根据前面的视频片段、文案、语音和 BGM，
  组织成合理的时间线。
- 渲染成片。"render_video"（固定）。根据时间线渲染成片。
```

步骤约束一览：

| 步骤 | 工具 | 是否可跳过 | 说明 |
|---|---|---|---|
| 搜索素材 | search_media | 可跳过 | 用户未上传素材时可搜索；搜索后仍需 load_media 才能真正加载 |
| 素材加载 | load_media | 固定 | 获取素材路径、长宽等基础信息 |
| 镜头切分 | split_shots | 可跳过 | 按镜头把素材切成片段 |
| 内容理解 | understand_clips | 可跳过 | 为每个片段生成描述（captions） |
| 镜头筛选 | filter_clips | 可跳过 | 按用户要求筛选片段 |
| 片段分组 | group_clips | 可跳过，但应默认运行 | 排序分组、组织叙事逻辑、辅助文案生成 |
| 文案生成 | generate_script | 可跳过 | 需要特定风格时优先用 subtitle_imitation_skill 仿写，再生成 |
| 元素推荐 | （推荐类工具） | 可跳过，但应默认运行 | 推荐花字、标题、特效、转场、配音音色 |
| 配音生成 | generate_voiceover | 可跳过 | 根据文案生成配音 |
| 背景音乐选取 | select_BGM | 可跳过 | 选择合适的背景音乐 |
| 组织时间线 | plan_timeline | 固定 | 把片段、文案、语音、BGM 组织成时间线 |
| 渲染成片 | render_video | 固定 | 根据时间线渲染成片 |

### 示例二：文风仿写 Skill（CAPABILITY SKILL）

它只要求生成脚本，不实现视频渲染，是更复杂的单点能力设计，
包含角色、目标、四步执行流程与约束条件：

```markdown
---
name: subtitle_imitation_skill
description: 【CAPABILITY SKILL】基于用户提供的参考文案样本，对视频素材内容进行
  深度文风仿写，生成风格化脚本。Based on user-provided reference text samples,
  the video material is deeply rewritten in terms of writing style to generate
  a stylized script.
version: 1.0.0
author: User_Agent_Architect
tags: [writing, style-transfer, video-production, creative]
---

# 角色定义 (Role)
你是一位"文风迁移大师"兼"金牌视频脚本撰写人"。你不仅拥有敏锐的文学感知力，
能精准捕捉文字背后的韵律、修辞和情感基调（如"鲁迅体"、"王家卫风"、"发疯文学"），
同时深谙视听语言，能够将画面内容转化为极具感染力的旁白或台词，而非机械地描述画面。

# 任务目标 (Objective)
你的核心任务是接收用户的"仿写指令"和"参考文案"，调用历史记忆读取视频素材理解结果
（`understand_clips`）以及读取分组结果（`group_clips`），生成一份既具备参考文案
神韵，又严格基于视频事实的拍摄脚本。

# 执行流程 (Workflow)

## 第一步：输入校验与意图确认 (Input Validation)
1. **检查输入参数**：检查用户是否提供了用于模仿的 `style_reference_text`（仿写样本）。
2. **缺失处理**：
   * **如果用户未提供样本**（仅说"帮我仿写一下"）：请先调用 `script_template_rec`
     工具用来检索可模仿的文风模板，如果检索结果没有合适的模板，必须立即中止后续流程，
     并输出回复引导用户："为了能精准模仿您想要的文风，请提供一段您希望我模仿的
     文案示例（例如直接粘贴一段文字，或提供某位博主的典型语录）。"
   * **如果用户已提供样本**：进入第二步。

## 第二步：获取素材与分析 (Context & Analysis)
1. **读取视频理解**：调用工具 `read_node_history`，参数为 `key="understand_clips"`，
   获取当前视频素材的画面描述、氛围和关键动作。
2. **风格解构**：在思维链（Chain of Thought）中快速分析用户提供的
   `style_reference_text`：
   * **句式特征**：是短句堆叠，还是长难句？
   * **修辞习惯**：是否喜欢用比喻、反讽、排比？
   * **情感基调**：是治愈、焦虑、犀利还是幽默？

## 第三步：风格化创作 (Creative Generation)
基于素材内容（Content）和分析出的风格（Style），执行脚本撰写。需严格遵守以下创作原则：
1. **拒绝"看图说话" (No See-Say)**：
   * ❌ 错误示范："画面里有一只猫在睡觉，阳光照在它身上。"
   * ✅ 正确示范（如文艺风）："午后的阳光是免费的，但偷得浮生半日闲的勇气却是昂贵的。
     它在做梦，而我在看它。"
2. **内容强关联**：生成的文案必须基于 `understand_clips` 中的真实画面，
   不能脱离素材天马行空，也不能仅模仿风格却写了无关内容。
3. **生动连贯**：脚本必须有起承转合，不仅是句子的拼凑，更是一个完整的小故事或情绪流。

## 第四步：格式化输出 (Formatting)
1. **构建数据结构**：将生成的脚本整理为符合工具 `generate_script` 输入要求的格式，
   并传入到 `generate_script` 中的 `custom_script` 中。格式如下：

```json
{
  "group_scripts": [
    { "group_id": "group_0001", "raw_text": "第一句，第二句，第三句" },
    { "group_id": "group_0002", "raw_text": "第一句，第二句" }
  ],
  "title": "视频标题"
}
```

2. **输出总结**：对用户隐藏结构化文案，而是挑选里面的句子反馈给用户，
   让用户判断是否符合要求，以便做进一步修改。

# 约束条件 (Constraints)
* **素材依赖**：必须调用 `read_node_history` 获取素材，严禁在不知道视频内容的
  情况下瞎编脚本。
* **风格一致性**：生成的文案必须让熟悉该风格的人一眼就能识别出"味道"。
* **拒绝机械描述**：严禁出现"视频显示"、"镜头切到"等说明书式语言，
  除非参考风格本身就是说明书风格。
* **工具对接**：输出内容必须适配 `generate_script` 的字段定义，
  确保下游渲染环节无缝衔接。
```

四步流程与涉及工具：

| 步骤 | 动作 | 涉及工具 |
|---|---|---|
| 第一步：输入校验 | 检查是否提供 style_reference_text；缺失时先查模板，无合适模板则中止并引导用户提供样本 | script_template_rec |
| 第二步：获取素材与分析 | 读取视频理解结果，解构参考文案的句式、修辞、情感基调 | read_node_history（key="understand_clips"） |
| 第三步：风格化创作 | 拒绝看图说话，内容强关联素材，脚本有起承转合 | —（LLM 生成） |
| 第四步：格式化输出 | 输出适配 generate_script 的 group_scripts/title 结构，并对用户做总结反馈 | generate_script（custom_script 入参） |

## 本节要点

- MCP 负责把音视频团队的 Node 能力包装成 LLM 可调用的 Tool
  （Java Web 范式：请求 → 路由 → 执行 → 返回）。
- Skill.md 是 LLM 的"剪辑流程说明书"：WORKFLOW SKILL 定整体流程，
  CAPABILITY SKILL 定单点能力。
- 流程步骤通过"可跳过 / 固定 / 应默认运行"标注，给 LLM 明确的决策空间与强制约束。

# 基于 DAG 的编排引擎设计

视频剪辑的一大难点是流程编排复杂，且起点和终点都不唯一。
核心问题：**如何约束 LLM 的输出，实现如此复杂的流程编排？**
答案是基于 DAG 的编排引擎，并着重使用**拦截器模式**。

## 编排引擎原理

两个关键机制：

1. **DAG 通过 Node 的 require_node 属性定义**：执行某 Node 之前，
   必须先执行过 require_node 规定的 node，依此构建 DAG，require_node 必须指定。
2. **拦截器约束**：LLM Agent 选择一个 MCP Tool 后，真正执行前会经过拦截器；
   如果该 MCP 有 require_node 未执行，则先去执行 require_node 中的 Tool，
   这个过程会**递归进行**，从而约束 LLM 按剪辑流程行动。

```python
class GroupClipsNode(BaseNode):
    requiredNodes = [FilterClipsNode]
    # 声明：执行 GroupClipsNode 之前，必须先执行 FilterClipsNode。

    def process():
        # ...

# 多态
GroupClipsNode(param)
# 通过参数构造具体实例，子类可覆盖 process 实现不同逻辑。

class BaseNode:
    def process():
        pass
    # 基类定义 process 空实现，子类重写。
```

| 概念 | 定义 | 作用 |
|---|---|---|
| require_node / requiredNodes | Node 的前置依赖节点列表 | 构建 DAG 边：依赖关系决定执行顺序 |
| 拦截器（Interceptor） | MCP Tool 真正执行前的检查环节 | 发现未满足的前置依赖时，先递归执行依赖 Tool |
| 递归执行 | 依赖的依赖也会被依次补齐 | 保证 LLM 无论怎么选，执行路径都满足 DAG 约束 |
| BaseNode 多态 | 子类重写 process，可带参数构造 | 同一接口、不同实现，便于扩展新节点 |

完整的 DAG 视频剪辑流程：
Import mcp（Anthropic）→ MCP Interceptor（API）→ 按 DAG 依赖逐节点执行。
**拦截器是约束 LLM 行为的"安全网"。**

# BaseNode 与 Store 机制

为了方便 Node 管理，设计了 BaseNode：所有 Node 必须继承它，
并通过 **Store 机制**串联不同 Node 的输入输出。

**两条设计原则**：

1. 新 Node 只需继承 BaseNode，并重写其中的 process 方法。
2. Node 与 Node 之间的信息传输通过 Store 机制实现。

```python
async def __call__(self, node_state: NodeState, **params) -> Dict[str, Any]:
    inputs = self.load_inputs_from_client(node_state, params.copy())
    # 从客户端请求中加载本节点的入参。

    # 从 Store 中读取前驱节点的结果。
    parsed_inputs = self._parse_input(node_state, inputs)
    # 解析入参：把 Store 中前驱节点（load_media、split_shots 等）的输出取出，
    # 组装成当前节点真正需要的结构化输入。

    outputs = await self.process(node_state, parsed_inputs)
    # 执行当前的 MCP Tool，也就是当前节点。

    packed_output = self.pack_outputs_to_client(node_state, outputs)
    # 将输出打包成返回给客户端的格式。

    # 将当前节点的执行结果存入 Store。
    # （供后续依赖该节点的下游节点读取，构成 DAG 数据流）
```

| 阶段 | 方法 | 职责 |
|---|---|---|
| 1. 加载入参 | load_inputs_from_client | 从客户端请求拿到本节点入参 |
| 2. 解析入参 | _parse_input | 从 Store 读取前驱节点结果，组装结构化输入 |
| 3. 执行业务 | process（子类重写） | 执行节点核心逻辑（音视频处理等） |
| 4. 打包输出 | pack_outputs_to_client | 把输出格式化为客户端需要的结构 |
| 5. 写入 Store | （框架自动） | 结果入库，供下游节点读取 |

inputs 的示例（展示 Store 中已有哪些前驱节点的数据可被读取）：

```json
{
    "load_media": { "media": [...] },
    "split_shots": { "clips": [...] },
    "understand_clips": { "clip_captions": [...] },
    "group_clips": { "groups": [...] },
    "generate_script": { "group_scripts": [...] },
    "artifact_id": "generate_voiceover_1744000000.123",
    "lang": "zh",
    "mode": "auto",
    "user_request": "用温柔的配音"
}
```

| 字段 | 来源 | 含义 |
|---|---|---|
| load_media / split_shots / understand_clips / group_clips / generate_script | Store（前驱节点输出） | 各前驱节点的 payload，按节点名作为 key 存于 Store |
| artifact_id | 会话上下文 | 产物 ID（如 generate_voiceover_1744000000.123），标识本次剪辑产物 |
| lang | 用户配置 | 语言（zh / en 等） |
| mode | 用户配置 | 模式（如 auto） |
| user_request | 用户输入 | 用户的原始需求（如"用温柔的配音"） |

**重要区分**：Store 存储是由**程序控制**的存储侧，因此不属于 Agent Memory。
Agent Memory 应该完全由 Agent 自行控制存储的写入和读取。也就是说：
**Store 是编排引擎的"数据总线"（框架管），Memory 是 Agent 的"长期记忆"
（Agent 自己管），两者不能混为一谈。**

## 本节要点

- DAG 由 require_node 声明式定义，拦截器在 Tool 执行前递归补齐前置依赖，
  从而约束 LLM 的编排行为。
- BaseNode 统一了"取数 → 解析 → 处理 → 打包 → 入库"的执行链路，新节点只需重写 process。
- Store 是程序控制的节点间数据总线，与 Agent Memory（Agent 自主读写）严格区分。

# Agent Team——视频剪辑的分工与合作（Kimi Agent Swarm）

单 Agent 在 DAG 流程编排和 Store 存储机制的协作下，能够很好地完成视频剪辑，
但单 Agent 剪辑速度太慢。引入 Agent Team 可以进一步加快速度。

**Agent Team 三大核心构建：**

1. **Message Center**：实现 Agent 之间的通信（A2A）。
2. **Task Manager**：实现任务拆解和执行认领。
3. **SubAgent Manager**：实现 SubAgent 之间的管理。

## Task Manager 的设计

Task Manager 精准地把剪辑 DAG 流程中的依赖与被依赖关系建模出来，
并持久化到文件系统。

1. **Prompt => main agent loop（Task Manager => .json）**：主 Agent 解析用户 Prompt，
   经 Task Manager 把剪辑任务拆解成 JSON 任务文件。
2. **blockBy 和 Blocks => .py 通过 BFS 算法生成**：依赖关系由程序用 BFS 计算得出。

引入 Task Manager 后，会在 MCP 拦截器中通过递归的 BFS 算法构建出
"入度/出度 Task DAG"，然后由 Agent Team 根据 Task 列表完成剪辑任务。
此外，基于 Store 的存储设计天然解耦了不同 Node 间的联系，
使得多 Agent 认领 Task 更加灵活。

### 一个完整 Task 的生命周期示例

刚创建时：

```json
{
  "id": 3,
  "name": "剪辑主采访片段",
  "description": "需要完成粗剪、去掉口误和长停顿、添加 B-roll 覆盖素材",
  "status": "pending",
  "owner": "subagent_c",
  "blockedBy": [1, 2],
  "blocks": [4, 5]
}
```

被 SubAgent A 认领后（status 变为 on_progress，owner 写入认领者）：

```json
{
  "id": 3,
  "name": "剪辑主采访片段",
  "description": "需要完成粗剪、去掉口误和长停顿、添加 B-roll 覆盖素材",
  "status": "on_progress",
  "owner": "SubAgent A",
  "blockedBy": [1, 2],
  "blocks": [4, 5]
}
```

任务 1 和任务 2 完成后，blockedBy 自动清空（任务回到可执行状态）：

```json
{
  "id": 3,
  "name": "剪辑主采访片段",
  "description": "需要完成粗剪、去掉口误和长停顿、添加 B-roll 覆盖素材",
  "status": "pending",
  "owner": "SubAgent A",
  "blockedBy": [],
  "blocks": [4, 5]
}
```

SubAgent A 完成后：

```json
{
  "id": 3,
  "name": "剪辑主采访片段",
  "description": "需要完成粗剪、去掉口误和长停顿、添加 B-roll 覆盖素材",
  "status": "completed",
  "owner": "SubAgent A",
  "blockedBy": [],
  "blocks": [4, 5]
}
```

此时任务 4 和任务 5 的 `blockedBy` 里的 `3` 会被自动移除，它们就可以被认领了。
对应 `list_all()` 的输出：

```text
[ ] #1: 整理原始素材并分类 @SubAgent B
[ ] #2: 导出音频并完成降噪处理 @SubAgent C
[>] #3: 剪辑主采访片段 @SubAgent A (blocked by: [1, 2])
[ ] #4: 添加字幕和文字动画 (blocked by: [])
[ ] #5: 调色和最终导出 (blocked by: [])
```

字段与流转逻辑：

| 字段 | 含义 | 流转逻辑 |
|---|---|---|
| id | 任务唯一 ID | 创建时分配 |
| name / description | 任务名称与描述 | 由主 Agent 拆解生成 |
| status | 任务状态 | pending → on_progress → completed |
| owner | 认领者（SubAgent） | 认领后写入 SubAgent 名 |
| blockedBy | 前置依赖任务 ID 列表 | 依赖完成后自动清空，随后可被认领 |
| blocks | 被本任务阻塞的任务 ID 列表 | 本任务完成后，下游任务的 blockedBy 中移除本 ID |

## Message Center——SubAgent 的通信渠道

通过 File System 实现 Agent 与 Agent 之间的信息交流（A2A）。
每个 Agent 有一个收件箱文件（jsonl），发消息就是往对方收件箱追加一行 JSON。

```json
// 记录在 sub_agent_a_box.jsonl 中
// sub_agent_c.jsonl
// #{sub_agent_name}.jsonl
{
    "type": "message",
    "from": "main_agent",
    "content": "请完成 id = 3 的 Task",
    "timestamp": 1703123456.789,
    "is_read": "false"
}
```

| 字段 | 含义 | 示例 |
|---|---|---|
| type | 消息类型 | message（普通消息） |
| from | 发件人 | main_agent |
| content | 消息正文 | 请完成 id = 3 的 Task |
| timestamp | 时间戳 | 1703123456.789 |
| is_read | 是否已读 | false / true |

Message Center 的两个关键实现是 send 和 read（read_inbox）：

```python
# tool registry
def send(self, sender: str, to: str, content: str,
         msg_type: str = "message") -> str:
    # sender：发件人名字
    # to：收件人名字
    # content：消息正文
    # msg_type：消息类型，默认是普通 "message"。

    msg = {"type": msg_type, "from": sender, "content": content,
           "timestamp": time.time()}
    # 构造消息字典，包含类型、发件人、正文、时间戳四个基础字段。

    with open(MESSAGE / f"{to}.jsonl", "a") as f:
        f.write(json.dumps(msg) + "\n")
        # 以追加模式打开收件人的收件箱文件（比如 alice.jsonl），
        # 把消息序列化成一行 JSON 写入。

    return f"Sent {msg_type} to {to}"
    # 返回确认字符串，供 LLM 知道发送成功。

def read_inbox(self, name: str) -> list:
    path = MESSAGE / f"{name}.jsonl"
    # 构造该 Agent 的收件箱路径。如果文件不存在，说明没有消息，直接返回空列表。
    if not path.exists():
        return []
    msgs = [json.loads(l) for l in path.read_text().strip().splitlines() if l]
    # 读取文件全部内容，按行分割，过滤空行，把每行 JSON 字符串反序列化成字典，
    # 组成列表。
    path.write_text("")
    # 读完之后清空文件。这实现了"已读即删"的语义，防止下次重复读到同一批消息。
    return msgs
    # 返回这批消息列表，供调用方（agent_loop 或队友线程）处理。
```

| 方法 | 参数 | 行为 |
|---|---|---|
| send | sender, to, content, msg_type="message" | 构造消息字典，追加写入收件人 {to}.jsonl，返回确认字符串 |
| read_inbox | name | 读取 {name}.jsonl 所有行反序列化后清空文件（已读即删），返回消息列表 |

## SubAgent Manager——对 SubAgent 的优化

SubAgent 的四个关键设计：

1. SubAgent 有**独立的工具集**，且这个工具集是 Main Agent 的**子集**（权限收敛）。
2. SubAgent 被引入除 Working 以外的其他状态：**Idle 和 Shutdown**。
   idle 状态的 SubAgent 常驻内存，类似线程池的设计，防止重复引入 SubAgent。
3. SubAgent 的信息会被**持久化到磁盘**，记录这个 SubAgent 的 Prompt 和工作状态。
4. Idle 状态的 SubAgent 有**两种唤醒方式**：一是通过 Message Center 得知自己
   被分配了任务（主动）；二是自驱地扫描 Message Center，发现有新任务可执行（被动）。

用户 A => 对话 A => Sub Agent 配置示例：

```json
[
    {"name": "sub_agent_a", "status": "working"},
    {"name": "sub_agent_b", "status": "shutdown"},
    {"name": "sub_agent_c", "status": "working"},
    {"name": "sub_agent_d", "status": "idle"}
]
```

| 状态 | 含义 | 资源占用 |
|---|---|---|
| working | SubAgent 正在做 Tool Loop（执行任务） | 占用 LLM 调用与工具执行资源 |
| idle | 常驻内存等待任务（类似线程池空闲线程） | 低占用但保持进程，避免重复创建 |
| shutdown | 已停止，不再参与任务 | 释放资源 |

Working 状态本质是 SubAgent 在做 Tool Loop；Idle 状态是一个有限的 while 循环，
包含两个设计：

1. 循环体内设置 `time.sleep()`，通过睡眠等待可执行任务（避免忙等）。
2. 每次循环读取 Message Center 和可用 Task：如果被赋予 Task（主动）
   或有待认领的 Task（被动），则由 Idle 转为 Working。

```python
while True:
    # -- WORK 阶段 --
    for _ in range(50):
        try:
            # 调用 LLM API。
            response = client.messages.create(
                model=MODEL, system=sys_prompt, messages=messages,
                tools=tools, max_tokens=8000)
        except Exception:
            self._set_status(name, "shutdown")
            return
            # LLM 调用失败则置为 shutdown 并退出。

        messages.append({"role": "assistant", "content": response.content})
        if response.stop_reason != "tool_use":
            # 没有 tool call。
            break
            # 模型不再请求调用工具，WORK 阶段结束。

        results = []
        idle_requested = False
        for block in response.content:
            # 执行 tool call。
            if block.type == "tool_use":
                output = dispatch.get(block.name, lambda **kw: "Unknown")(**block.input)
                # 按工具名分发到对应实现；未知工具返回 "Unknown"。
                print(f"  [{name}] {block.name}: {str(output)[:120]}")
                results.append({"type": "tool_result",
                                "tool_use_id": block.id,
                                "content": str(output)})
                # 把工具执行结果包装成 tool_result 消息，回传给模型。
        messages.append({"role": "user", "content": results})

    # -- IDLE 阶段 --
    self._set_status(name, "idle")
    resume = False
    for _ in range(LOOP_TIMES):
        time.sleep(POLL_INTERVAL)
        # 睡眠。
        inbox = self.message_center.read_inbox(name)
        # 查看 Message Center。
        if inbox:
            for msg in inbox:
                messages.append({"role": "user", "content": json.dumps(msg)})
            resume = True
            # 重新 Working。
            break
            # 收到消息（如被分配 Task），唤醒进入 Working。

        unclaimed = []
        for f in sorted(TASKS_DIR.glob("task_*.json")):
            t = json.loads(f.read_text())
            # 查看 Task。
            if t.get("status") == "pending" and not t.get("owner") \
                    and not t.get("blockedBy"):
                resume = True
                # 重新 Working。
                break
                # 发现待认领且无依赖阻塞的 Task，认领后进入 Working。

    if not resume:
        self._set_status(name, "shutdown")
        # 进程 Shutdown。
        return
        # 等待超时仍无任务，转为 shutdown 释放资源。
    self._set_status(name, "working")
```

| 阶段 | 循环条件 | 行为 | 退出条件 |
|---|---|---|---|
| WORK | `for _ in range(50)` | 循环调用 LLM，执行返回的 tool_use，回填 tool_result；最多 50 轮 | 模型不再请求工具，或 LLM 调用异常置 shutdown |
| IDLE | `for _ in range(LOOP_TIMES)` | 睡眠轮询：读收件箱、扫描待认领 Task | 收到消息或有可认领 Task → 转 working；超时无任务 → shutdown |

## 本节要点

- Agent Team = Task Manager（任务拆解与依赖 DAG）+ Message Center（文件系统 A2A 通信）
  + SubAgent Manager（状态与生命周期管理）。
- Task 用 blockedBy / blocks 表达依赖，状态流转 pending → on_progress → completed，
  依赖完成后自动解锁下游任务。
- SubAgent 通过"Working 干完 → Idle 轮询 → 有任务再 Working"的循环实现复用；
  工具集收敛为 Main Agent 的子集。

### 1.2 原稿没讲、面试会问的三个机制

**① InBound / OutBound 为什么是两个 topic?**
执行和展示解耦:入站消息按 session 路由给"某一个执行实例";出站帧要被"所有挂着
该会话 WS 连接的实例"看到(多副本时经 Redis 扇出,见 §8/§9)。一个 topic 做不到
"消费组语义 + 广播语义"并存——入站要竞争消费(一帧一个 worker 执行),出站要扇出
(每个副本都收)。

**② 同会话串行的精确含义。**
不是"同一个用户串行",是"同一个 conversation 串行"。用户 A 的对话 1 和对话 2
并行;分区只是载体——A1 和 C1 可能同分区(原稿的图是对的),同分区内按到达顺序
逐条执行。**推论:分区数不决定并发度上限的粒度,会话数才决定;分区数只决定
"最多同时处理几条消息"。**

**③ handler 异常怎么办(原稿没写)。**
单条消息 handler 抛异常 → 记 `log.exception`(按 topic/group/partition/run_id)
→ 分区继续消费下一条(**不中断、不重投**);同时向 OutBound 发 `error` 帧防止前端干等。
"不重投"是刻意的:执行侧的可靠由 checkpoint 保证(§6),MQ 层重投反而会重复执行工具。

### 1.3 追问链

```
Q: 为什么不用 RabbitMQ / Redis Stream?
→ A: 单副本内存版就够(执行可靠性靠 checkpoint 不靠 broker);需要多副本时
     Kafka 的消费组语义开箱即用。MQ 接口抽象成一 build_message_queue(backend),
     换实现是配置不是代码。
Q: 消息在队列里,进程 crash 了,消息丢吗?
→ A: 内存版丢——但执行侧恢复靠 PG checkpoint 认领 running/failed 的 run,
     用户侧表现为"重试后继续",不靠队列回放。
Q: 为什么 WS 推送不直接在工具/LLM 调用处发?
→ A: 执行可能发生在任意实例(多副本),WS 连接只在其登录的那台;
     统一投 OutBound + ConnectionManager 查表,才能既单副本直连又多副本广播。
```

## §2 Agent Loop(补充)

### 2.1 两层循环的代码对应

```
Main Loop(常驻)                       AgentOnceLoop(单次请求,ReAct)
────────────────────────              ─────────────────────────────
MQ 消费循环(每分区 worker)            _drive(agent.py,77 行骨架)
  └─ SessionConsumer._handle            └─ while iteration < limit:
       └─ Agent.handle / Agent.plan           _settle_pending(审批收口)
          └─ AgentOnceRun.run                 一致点落盘(state.persist + save_progress)
              └─ _drive  ◄─────────           before_iteration 钩子 → LLM
                                              有 tool_calls → _tool_round(三道门)
                                              无 tool_calls → 四道硬保证 → _deliver
```

- **迭代上限默认 40**(`--max-iterations`):整链剪辑十几步工具调用、每步一轮 LLM,
  20 必然半路耗尽。撞上限标记 **failed 而不是 completed**——failed 会被崩溃恢复/「继续」
  接上,completed 就结束了。
- **续跑不是接着数**:续跑轮按"再给一轮预算"处理(`_iteration_limit`),否则
  "从 iteration=40 续跑,一进循环就退出"(README 记录过的真 bug)。

### 2.2 "四道硬保证"与 `_nudge_back`

模型不调工具、直接想收尾时,服务端在收尾那一刻核对四件事,不成立就打回重写
(`_nudge_back`,默认各打回一次,预算用尽补事实说明):
1. **claims_plan_card**:本轮没落过 `submit_plan`,终答却声称"计划卡已给出";
2. **claims_step_executed**:确认过的计划有步骤,本轮却一次步骤工具没调,措辞却
   声称"渲染完成";
3. **ask_gate**:文字在向用户索取(该弹窗)而没调 `ask_user`;
4. **渲染未终态不许收尾**(render gate 配套)。

**为什么是"词面判据 + 退回一次 + 补事实"三段式?** 词面是确定性的、零 LLM 成本,
但认不出刻意绕开的措辞——所以不追求"拦住所有假称",追求"绝不带着假称收尾":
退回一次给模型自纠机会,预算用尽就由服务端在正文末尾补一句事实,把假称对冲掉。

### 2.3 追问链

```
Q: 这符合 ReAct 吗?
→ A: 符合:LLM 输出 Thought(内容)/Action(tool_calls)→ 环境执行(Observation
     以 tool 消息回填)→ 循环。差异点是外面加了工程壳:门控(gate)、一致点、
     对账(hook),即原稿说的"Harness 约束 Loop"。
Q: 为什么要区分 plan() 和 handle() 两个入口?
→ A: 规划轮用独立注册表(物理不含剪辑工具),出口只有 submit_plan/直接回答;
     执行轮才暴露剪辑工具。同一套 AgentOnceRun,换注册表换提示词。
Q: 两个 run 之间共享什么、隔离什么?
→ A: 共享:会话消息链、存储、身份;隔离:工具注册表(规划/执行/子Agent 三套)、
     迭代预算、RunState(按 run 落盘)。
```

## §3 工具注册与执行(补充)

### 3.1 原稿代码 vs 现状:三处演进

1. **错误判定**:原稿 `result.startswith("Error")` 嗅探 → 现在**类型化 `ToolError(tool, detail)`**
   (tool.py:13 注释明写"不再嗅探"),但保留 `_HINT` 文案附加在错误文本尾部(tool.py:32,58)。
   原因:字符串嗅探要求工具"必须用特定前缀报告失败",工具作者一忘就静默变成"成功";
   类型化后由框架统一捕获包装,不可绕过。另有 `UnknownToolError`(注册表查无此名)——
   这种调用从未打到后端,对账/进度不计入。
2. **并发分批**:原稿只按 read_only 分批 → 现在叠加 **DAG 契约读写集**:
   写集相交、或一方写集撞另一方读集即冲突,冲突者退到下一批;贪心且**保持模型给出的
   顺序**;`concurrency_safe=False` 独占一批;**契约取不到 → 保守串行**
   (正确性不依赖契约存在)。
3. **参数校验前置**:`prepare_call` 按 schema 校验+类型转换,失败直接返回错误+_HINT,
   不进工具体——工具实现里不用再防御性检查参数类型。

### 3.2 工具结果怎么进上下文(原稿没讲,很常考)

- 结果文本**截断到 600 字**进 messages(省窗口);但对渲染这类长返回,前端需要的
  结构化视图(`render.status/percent`)单独挂在 WS 帧的独立字段上——**截断截的是
  result,截不掉帧字段**,进度条因此不受影响(tests/test_hooks.py 钉住)。
- 配对靠 `call_id`(模型给的 tool_call_id):同一批两个同名调用(并行渲染两条时间线)
  按"第一个同名气泡"配对会张冠李戴,按 call_id 各回各家。

### 3.3 追问链

```
Q: 工具超时怎么处理?
→ A: MCP 层 tool_timeout(剪辑域 600s,因为渲染在 MCP 之外走提交+轮询,不占
     请求线程);框架层每次调用在 async 任务里,可被取消。
Q: 为什么工具失败要给模型 _HINT 而不是直接抛?
→ A: 抛异常会终结整轮;把错误文本作为 Observation 回给模型,模型能自纠
     (换参数/换工具)——这是 ReAct 的自我修复路径。
Q: 工具执行是并发的,结果顺序怎么保证?
→ A: gather 后按发起顺序回填,与模型 tool_calls 列表一一对应;LLM 协议要求
     tool 消息与 tool_call_id 一一配对,乱序会 400。
```

## §6 Checkpoint 崩溃恢复(补充 ★ 必考深水区)

### 6.1 存储形态:指针行 + 一致点增量链

```
checkpoints(指针行,一行一个 run)            checkpoint_entries(增量链)
┌────────────────────────────┐              ┌─────┬───────┬──────────────┐
│ run_id, status, iteration  │              │ seq │ kind  │ 内容         │
│ artifact_id(产物作用域)    │              │  0  │ full  │ 消息 1..3    │ ← 基准
│ plan json(approval/state)  │    1 : N     │  1  │ delta │ 新增消息 2 条 │
│ message / plan_run_id /    │─────────────▶│  2  │ delta │ 新增 1 条    │
│ forked_from / lease 列     │              │  …  │  …    │              │
└────────────────────────────┘              └─────┴───────┴──────────────┘
重建 = 最近一条 full + 其后全部 delta 逐条重放
压缩改写了旧消息 → 那条退化成新的 full 基准(链从此分叉重算)
```

**为什么不全量快照?** 长会话每轮全量 = O(轮数 × 会话大小) 存储;增量链只存新增,
full 基准只在压缩改写时出现,读路径 O(定位最近 full) + 线性重放,两头都便宜。

**为什么一致点定义在"即将调 LLM 前"?** 此刻上一批工具结果已全部落链
(工具执行完 → 结果回填 → 落盘 → 才进下一轮 LLM),这是**无副作用恢复点**:
恢复 = 重发一次 LLM 调用;若定义在"工具执行前",恢复就要重放工具——渲染/上传
都是分钟级重活,幂等代价高。

### 6.2 状态机与恢复候选

```
running ──► completed            (终态,退出恢复候选)
   │    ──► failed               (会被启动恢复认领重试;撞迭代上限也标 failed)
   │    ──► superseded           (被 fork/跨轮回溯让位,退出恢复候选)
   └──────► awaiting_approval    (挂起等人工;★刻意不在恢复候选里)
```

挂起时不只是"停",而是把 **pending_calls + 结构化 ask(题面/选项/推荐徽标/上限 6 项)
+ fallback_options** 全部落进 approval 列——刷新页面后 `/runs/active` 读它原样重弹。

### 6.3 fork / 时间旅行(五步,背下来)

```
① 定点:在链上找"该工具结果出现之前"的一致点(找不到如实回绝,
        并列出本会话跑过它的历史执行当索引——跨轮就照索引填 run_id 重试)
② 截断:load(run_id, at_seq) 重建上下文
③ 隔离:子 run 换新 artifact_id;父产物集整份 clone_from 复制过去
        (试另一种 BGM 不把父版本改花)
④ 作废:按剪辑 DAG 契约算下游闭包,rerun 节点及其全部下游产物作废
        (不作的后果:拦截器看到"已完成"恰好跳过要求重跑的那步)
⑤ 让位:父 run 置 superseded;新诉求 instruction 作为最新 user 消息接上
        (不接的后果:链尾是父的旧指令,模型连分九次叉选中同一首 BGM——真机踩过)
```

跨轮规则:只认**同一会话**的 run;别人的/已清理/前缀歧义一律如实回绝,绝不猜;
本轮发起的那条也置 superseded(否则崩溃恢复会重播一条已弃用分支)。

### 6.4 RunState:跨挂起的对账事实

挂起→续跑会把进程内存清零,而"批准过的计划/本轮调过哪些工具/qa 片段"这些事实
是**收尾对账**要用的。`run_state.py` 把它们收敛成一个字段清单对象,随指针行落盘:

- 字段:approved_plan、calls_attempted(含失败,供"未调用不许声称已执行")、
  calls_executed(真打到注册表的,供对账)、plan_candidates/warnings/card_pushed、
  audit_pushed、plan_audit、qa_parts;
- **写入点只有 4 处**:`_drive` 开头 / 每个一致点 / 每个挂起点 / 异常路径——
  且**与消息同批落库**,恢复出来的调用清单才和一致点对得上;
- 收尾后 `retain_residue` 只留 approved_plan(它是编译计划的唯一库内落点,分叉要继承);
  调用清单按子 run 上下文里真有的回执重建——否则分叉会把"用户要求重做的几步"判成已履行。

### 6.5 多副本:执行权互斥

```
启动 → claim_recoverable(instance_id):
   ① 认领无主(owner IS NULL)
   ② 认领租约过期(lease_expires_at < now())
   PG 用 FOR UPDATE SKIP LOCKED —— 两副本并发冷启动也不会认领到同一条
租约续期:每次 save_progress(迭代边界)顺带续 → 崩了的实例租约自然过期
归还:complete / mark_failed
```

**单副本时 owner/lease 恒为 NULL,行为不变**——多副本语义是加法不是开关。

### 6.6 追问链(这节一定会被连问)

```
Q: 一致点和数据库事务什么关系?
→ A: 消息与 RunState 同批写入是一个事务;但"工具执行"不在事务里(外部副作用),
     所以一致点选在工具结果落链之后、下次 LLM 之前——把不可回滚的都变成已持久化。
Q: fork 时上游为什么不重跑?
→ A: 产物在 artifacts 表按 (session, artifact, node) 存;子 run clone 了整份
     产物集,只 invalidate 下游闭包——上游的字节复用是"逐字节"的(冒烟验证过)。
Q: 恢复时模型上下文里多一条 user 消息("继续")吗?
→ A: 不。resume 的语义是从一致点原样续,消费层识别"继续"类口令只是触发方式。
Q: 挂起(run 在等审批)时进程死了,恢复会重跑这半轮吗?
→ A: 不会——awaiting_approval 不在恢复候选;审批帧还在库里,approve 之后
     从挂起点续(待批调用受 _repair_orphans 的 keep_ids 保护,不被压缩剥掉)。
```

- 存储:文件系统 → **PG `scheduled_jobs`**(多实例共享、重启不丢);
- 调度骨架语义与原稿一致(找最近 next_run → arm timer → 到点执行 → 单次任务

  为什么:那条消息没有坐在屏幕前的人点确认,拦在规划轮里任务永不落地;

## §9 MCP(补充)

### 9.1 三个关键认知(原稿)的落地形态

1. 客户端 + 服务端:本项目**两边都写了**——客户端 `tools/mcp.py`(**手写 JSON-RPC、
   零额外依赖**,stdio + streamableHttp 两种 transport + FakeTransport 供离线测试);
   服务端 Storyline 用官方 FastMCP。
2. 配置先行:mcp.json(外部工具)+ config.toml [local_mcp_server](剪辑域);
3. schema 动态发现:`tools/list` 拿回 inputSchema → 包成 MCPTool 注册——
   **服务端加节点,客户端不用改代码**,这是 MCP 相对"自写 HTTP API + 手抄 schema"的核心收益。

### 9.2 为什么用 MCP 而不是普通 HTTP API(常考)

```
普通 HTTP API:  每个服务自定义 路由/鉴权/错误格式/schema 文档,Agent 逐个对接
MCP:           统一的 工具发现(tools/list)/调用(tools/call)/传输(stdio|streamableHttp)
               + 标准化的 inputSchema —— Agent 侧一个客户端吃遍所有 Server
```
加上**生态**:任何实现了 MCP 的第三方 Server(数据库/GitHub/内部服务)零代码接入。
选 **streamable-http** 而不是 stdio:剪辑服务是常驻独立进程(渲染分钟级、要自己的
存储连接),进程生命周期不该绑在主服务上。

### 9.3 追问链

```
Q: stateless_http 为什么建议 false?
→ A: 有状态会话让 Server 端能按会话组织 Store/缓存/工作区;stateless 每请求
     重建上下文,渲染这类长任务的对账会复杂化。
Q: MCP 工具和框架原生工具在注册表里是同一待遇吗?
→ A: 是——都包成 Tool(同样的 name/description/parameters/execute),
     Registry 不关心工具从哪来;所以拦截器/并发分批/审批门对 MCP 工具同样生效。
```

## 6. 架构与技术选型:为什么自研不用框架 ★

### 6.1 先摆候选,再逐个说"为什么不是它"

## 7. 什么是 DAG:从概念到三视图落地 ★

### 7.1 概念底座(面试官假定你懂,所以要讲得比他准)

```
图 G = (V, E) 有向:边有方向(A→B 表示 B 依赖 A)      无环:沿有向边走不回起点
Pipeline(流水线):退化成一条链,顺序固定              Workflow:结构固定、条件分支写死在模板里
状态机:节点是状态、边是转移、可回边                  DAG:依赖驱动、可分支汇合、无环 → 可拓扑排序
```

**为什么无环是底线**:环 = "A 等 B、B 等 A" 死锁;拓扑序不存在;
"下游闭包""补齐依赖"这类递归算法不终止。本项目防环靠**声明边固定**(边只能在
节点定义时写死,LLM 只能"选边"不能"造边")+ 计划校验(步骤序与 requires
拓扑相容,前置排在后面直接拒)。

### 7.2 为什么剪辑是 DAG 而不是流水线(用例子讲)

```
                ┌── asr ── correct_transcript ── speech_rough_cut ──┐
load_media ──┤                                                    ├── plan_timeline(三变体平行)── render_video
                └── split_shots ── understand_clips ── filter ── group ── generate_script ──┐
                                                                                              ├── 配音 / BGM / 转场 ↑
```
- **并行**:asr 和 split_shots 无依赖关系 → 并发分批时可以同批跑;
- **分支**:三条 plan_timeline 变体是三条平行路径,按需求选其一;
- **跳步**:纯画面混剪可以不走 asr(用户没上传素材可以走 search_media);
- **提前终止**:终点不唯一——用户可能只要文案不要成片(原稿"终止点不固定")。
这四件事流水线都表达不了。

### 7.3 同一个 DAG 的三视图(本项目精华,务必能画)

```
① 声明视图(节点类上)      class GroupClipsNode: required_nodes = ["filter_clips"]
                              ↓ 服务端启动时归一化
② 契约视图(机器可读)      NodeContract(name, requires, reducer, params)
                              writes = {store:<name>}  reads = {store:<dep>}…
                              GET dag_contract → {nodes:{…}, order:拓扑序}
③ 任务视图(多 Agent)      tasks + task_edges: blockedBy/blocks,依赖完成自动解锁
```
**一份契约三处用**:Interceptor 补齐依赖(执行正确性)、并发分批读写集(吞吐)、
fork 下游闭包作废(时间旅行正确性)。**契约取不到时保守串行——正确性从不依赖
契约存在**;契约存在时,三处共享同一真相,不会互相漂移。

### 7.4 两个经典算法在这里的形态(面试常考"怎么实现的")

- **拓扑序**:启动时从契约算出 order,用于:计划卡步骤校验(前置必须排在后面前)
  和 dag_contract 返回值(前端 PIPE_ORDER 排序)。
- **下游闭包(fork 作废)**:从 rerun 节点沿 requires **反向**做传递闭包
  (BFS/DFS),得到"所有直接或间接依赖它的节点"集合 → 逐个 invalidate。
  复杂度 O(V+E),节点数 20,无所谓。

### 7.5 拦截器为什么是"软调度"(与 Workflow 引擎的本质区别)

Workflow 引擎:结构已知 → **调度**执行(它决定下一步跑什么)。
本项目:LLM 决定下一步(可能跳步/乱序),拦截器只做**约束兜底**——
"你选的这个节点的依赖没跑?先递归补齐再跑你的"。即:
**自由度给模型,正确性给框架。** 这是"规范 LLM 输出"的准确含义:
不是让 LLM 听话,而是让它怎么选都落在合法路径上。

## 9. 可靠性工程专题:五个"不"(把散落机制组织成体系,面试结构化加分)

| 不 | 机制 | 一句话 |
|---|---|---|
| **不丢** | checkpoint 增量链 / qa.parts 持久链接 / render_jobs 落库 / PG+MinIO | 崩了从一致点回来;成片链接刷新不丢;渲染状态重启可查 |
| **不重** | 渲染 enqueue 同 (session,artifact) 去重 + `_reaped` / 迁移幂等自然键 / 记忆整行相同不重写 / 分片 complete 幂等 | 每类副作用都有自然幂等键 |
| **不假** | 三道假称核对 / 证据五级分级 / 死链拒绝("请重跑产出它的节点")/ dry_run 零留痕 / 失败不静默兜底 | 没做的说没做;验不了的标 UNVERIFIED |
| **不卡** | 渲染 grace+轮询+代查 / 停滞看门狗(无进展 600s)/ 启动 reap_hanging / WS 环形缓冲重连补帧 | 每种"等"都有上限和收口;等待方永不无限等 |
| **不串** | 身份 ContextVar / 作用域键 u:c / 跨 owner 读空写 409 / token 只存 sha256 / 工作区 root 收窄 | 多用户多会话多 run 的每层归属都有显式键 |

**面试话术**:"这个项目把我对分布式可靠性的理解落到了 Agent 场景——
比如看门狗按'无进展时长'而不是'总耗时'判死,是因为慢渲染每 1% 写一次行,
真在跑的不会被误杀;比如幂等不是靠重试去重,而是每类副作用设计自然键。"

## 10. LLM 应用工程专题(把"调模型的工程"讲成体系)

1. **提示词资产化**:8 份 .md 落盘 + 占位符只替换提供的键 + `{?key}` 块守卫
   + 内联回落;漂移守卫(磁盘与内联逐字一致)+ 迁移前 9 条金样逐字比对 +
   prompt 指纹入 eval。**改文案不改代码,改坏了测试立刻红。**
2. **输出契约**:节点参数用 JSON Schema 校验 + 类型转换;自由文本永不进节点参数;
   卡面枚举可反查(枚举是承诺);LLM JSON 失败有确定性兜底(分组摘要句)。
3. **行为闸(防幻觉三件套)**:计划门(结构性)+ 假称词面核对(交付态)+ 弹窗硬保证
   (交互态);共同哲学:**不追求拦住一切,追求"绝不带假称收尾"**——退回一次,
   预算用尽由服务端补事实。
4. **性能工程**:thinking 默认关(实测 2.1×/1.7×,生效写法只有
   `{"thinking":{"type":"disabled"}}`,另两种写法服务端默默收下照样思考——这是
   "文档没写就只能实测"的典型坑);understand_clips 批 8 帧/并发 8(一次成片
   上百次带图往返,吞吐就是用户等待时间);字幕层扁平化(渲染从 30 分钟到分钟级)。
5. **上下文预算**:三级压缩 + 轻量清单注入(技能/工具描述)+ 600 字结果截断 +
   token 估算偏保守;始终为"当前 user + system"保底。
6. **评测通道**:ScriptedLLM 离线 golden(4 条用例,钉路径形状不钉模型质量)+
   prompt 指纹归因 + `--live` 真机评测位 + 真机冒烟 credit_gate(区分"代码坏了"
   和"账户空了")。

## 11. 存储层:18 张表与产物引用契约(原稿无此章,补遗)

### 11.1 双后端与表清单

```python
build_storage("pg_minio" | "memory")   # 同一套仓储接口,两种实现
# 启动即 ping + ensure_schema,连不上直接退出——不带病服务
# memory 后端:离线测试秒级全量跑;生产切 pg_minio 只改一个参数
```

PG 侧:SQLAlchemy 2.0 async + asyncpg;调用方**不写 SQL**,走 `Cond` DSL +
schema.sql 白名单列名(db.py);15 个 repo 挂在 Storage 上;连接池三参数
(`PG_POOL_MAX_OVERFLOW` 溢出 / `PG_POOL_PRE_PING` 先 ping 防死连接 / `PG_POOL_RECYCLE_SEC` 换新)。

18 张表按职责分组:

| 组 | 表 | 存什么 |
|---|---|---|
| 身份与会话 | users / conversations / messages / inbox_messages | token 的 sha256、会话、消息链、Agent 收件箱 |
| 执行状态 | checkpoints / checkpoint_entries / tasks + task_edges(+task_seq) | 指针行、一致点增量链、任务板 |
| 素材与产物 | materials / artifacts / upload_sessions / render_jobs / timelines | 素材元数据、节点产物(obj: 引用)、分片账本、渲染任务、时间线 |
| 能力配置 | memories / skills + skill_files / app_secrets / token_usage / scheduled_jobs / subagents | 记忆、技能正文与附件索引、明文密钥、token 用量、定时任务、常驻子 Agent |

MinIO 侧:官方 SDK(同步)+ 每调用包 `asyncio.to_thread`;七方法接口
(put/get_stream/head/delete/list_prefix/presign_get/localize);sha256 内容寻址缓存。

### 11.2 产物引用契约(payload 里只有 obj:)

| 键布局 | 存什么 |
|---|---|
| `users/{owner}/convs/{conv}/{material_id}{ext}` | 上传/链接取料的素材 |
| `renders/{safe_sess}/{artifact}.mp4` | 成片 |
| `derived/{sess}/{artifact}/{stage}/{name}` | 派生字节(voiceover/bgm/转场) |

- 写:`publish` / `publish_derived` 字节进 MinIO,payload 只留 `obj:` 键;
- 读:`Workspace.localize_ref` 是**唯一**取字节入口(sha1 槽位同名不互盖、命中直返、并发锁);
- **会过期的 presigned 直链标 ephemeral** 只回调用方、不落库——读侧按对象键现签;
- 引用取不到字节 = 产物失效,当场报"请重跑产出它的节点",
  **绝不产出引用死链的"成功"**(与"失败不静默兜底"同一哲学)。

### 11.3 大文件分片上传(桶即账本)

```text
POST /upload/init    → 服务端定切法,回 part_size/part_count(片号从 0 起)
PUT  /upload/part    → 逐片原始字节 + 该片 sha256(边写边核,不符 422 重传该片)
POST /upload/complete→ 请求体带按序逐片摘要清单,与桶里真存字节逐片比;
                       不符只作废那几片并回 missing_parts;整文件 sha256 可选第三道
POST /upload/abort   → 字节与账本一起删净;后台清扫回收静置会话
```

三道内容校验(逐片 / 按序清单 / 整文件);**"传到哪了"的答案在桶里**
(list_prefix 一次带回片号+字节+sha256 元数据),没有需要人维护的进度状态;
代价 = 拼装期约 2× 桶占用峰值(刻意取舍);前端按 2MB 分流(小文件单请求,
大文件逐片 + `crypto.subtle` 逐片指纹 + 取消按钮)。

### 11.4 追问链

```
Q: 为什么不用 MongoDB?
→ A: checkpoint 增量链/外键身份/租约(SKIP LOCKED)/窗口聚合——全是关系语义;
     文档库表达这些要自己造约束。
Q: presigned URL 为什么不落库?
→ A: 会过期;落库就是持久化一个死链。读时按对象键现签,链接永远新鲜。
Q: 迁移怎么保证不重复?
→ A: 每类自然幂等键(users=遗留 id、messages={文件}#{行号}、checkpoints=run_id…),
     第二遍只见"跳过",且从不覆盖库里已有行。
```

### 12.2 鉴权与作用域

- token:32 字节随机,**库里只存 sha256**;HTTP 走 Bearer;WS 浏览器不能带自定义头
  → 查询参数,失败 close 4401;校验失败统一 401 不区分原因;
- **跨 owner 语义**:读返回"空"不返回 403(不泄露会话存在性);写 409;别人的 run 一律 404;
- 身份经 `Identity(user_id, conversation_id, artifact_id)` **ContextVar** 注入,
  工具是进程级单例,owner 条件跟"这次是谁在跑"走——模型看不到也改不了;
- 内部身份 `default`/`cron` 启动登记,业务写入路径不自建用户行
  (来路不明的 user_id 被外键直接拒绝)。

### 12.3 界面中文名:一份词表、两个出口

- 三处声明汇一表:框架工具 `display_name` + MCP `title` + 技能 frontmatter `display`;
- 两个出口全覆盖:HTTP `CatalogJSONResponse`(序列化前 rewrite_obj)、WS `_emit`
  (流式 delta 走每连接 StreamRewriter,代码段状态跨帧续判);
- **双轨不替换**:`KEEP_KEYS`(机器名是键,原值保留另挂 `*_display`)、
  `OPAQUE_KEYS`(文件名/对象键/id 是用户内容,整条不动)、参数名另表
  (防"按 name 排序"被换成"按 名称 排序")。

### 12.4 追问链

## 13. 前端与帧协议(原稿无此章,补遗)

### 13.1 WS 帧类型(前端唯一的数据源)

| 帧 | 时机 | 关键字段 |
|---|---|---|
| connected | WS 建立后 | — |
| delta / stream_end | LLM 流式 | 逐字;`replayed:true` 标补发帧 |
| tool_call / tool_result | 每次工具 | call_id 配对;**render 视图独立字段**(不随 result 600 字截断丢) |
| plan(计划卡) | submit_plan 落地后 | 卡面参数开关/skills_hint_display |
| approval(审批/提问) | 挂起时 | 题面/选项/推荐徽标/多题分页 |
| media(成片卡) | 渲染 done | 现签 media_url + 证据账本摘要 |
| run_adopted / error / answer | 续跑接管 / 异常 / 收尾 | answer 触发环形缓冲"整轮保留" |

### 13.2 三个前端机制(被问"前端怎么做的"时)

1. **断线重连补帧**:重连只重开 socket 不重拉历史 → 服务端环形缓冲按 run_id
   保留完整一轮(answer 后清中间帧),客户端按 `replayed:true` 去重;
2. **上传**:2MB 分流;大文件逐片 XHR(进度逐片可见)+ 逐片 sha256 + 取消按钮;
   刷新后续传(服务端 init 幂等接回同一 upload_id);
3. **执行记录抽屉**:列 run 状态/一致点链(每点带 tools)→ 点选分叉点 →
   fork(预勾重跑节点、可另写新诉求)/ resume;父 run 就地变"已让位"。

**诚实边界**:整个前端是一个 4546 行的 App.vue 单文件——功能内聚但已是最大技术债。

### 14.2 配置与密钥

- `.env` 五项必须(PG_DSN + MINIO_*),代码/配置文件里无密钥值;
- 模型密钥解析链:**页面设置(PG app_secrets,按 user)→ OPENAI_API_KEY →

  两个服务共用启动路径;`/settings/test` 走生产同款通道发两次请求(文本+48×32 渐变图)
  ——只测文本会漏掉"key 有效但模型不吃图"这类静默降级。

### 14.3 装配期一致性检查(consistency.py)

启动时跑一次(非空只告警不拦启动),防**四份互不校验的清单漂移**:
提示词点名的工具 / 真实注册表 / 计划门白名单 / 技能正文里的工具名。
真机事故:提示词写 `read_node_artifact`、真实叫 `read_node_history` →
UnknownToolError → 白烧一轮迭代预算。教训:字段名来源要收全
(规划注册表的 param_options 也算,漏了就是假告警)。

### 14.4 运维坑清单(面试讲"你踩过什么坑"的素材)

- 同一套 PG 另起临时实例要 `--no-resume`(否则它替别人重放在途 run);
- `start.bat` 起的进程不带 -u 且会抢端口(Errno 10048);
- 模型 402(余额)时 run 全在 iteration=0 failed——credit_gate 因此而生;
- MQ worker 曾吞 handler 异常 → run 无声消失 → 按 topic/group/partition/run_id
  记 log.exception 后才可定位。

5. **"一套 key 挂了全站不可用?"** — 是已知边界(402 事件真发生过);缓解:

6. **"最难的 bug?"**(准备一个真实故事)推荐:渲染进度条"永远 queued"——

7. **"如果重做?"** — 三个具体:App.vue 拆组件(可测性)、记忆索引+召回、

   逻辑)、哪些是你做的(框架/Harness/门控/存储/测试)。说"全是我写的"被追问

## 续-A · Agent Team 一致性加固(任务幂等 + 锁)★

**原稿与下篇 §7 讲的是"任务板怎么用";本轮补的是生产语义——两个 Agent 抢活儿时不出错。**

- **认领已是原子的**:`db.claim` 在 PG 用 `FOR UPDATE SKIP LOCKED`、内存引擎锁内
  比较-改写(`db.py:303`);`claim_one` 只在 `status=pending` 时改写,抢不到返回 None
  ——两个协程/实例并发认领同一条任务,恰好一个成功。
- **交付纪律**:`TaskManager.complete(task_id, owner)` 重写(task_manager.py)——
  只有**认领者本人**能交付(原子条件改写 `claimed AND owner=?`);
  pending 不能跳过认领直接交付;他人任务给出精确错误。
- **交付幂等**:同 owner 重复 complete 原样返回、不二次解锁下游——崩溃恢复重放
  这条指令不产生副作用。这条和 §9 的"不重"呼应:每类副作用都要有自然幂等键。
- **收件箱恰好一次**:旧实现"先 peek 再逐行 update",两个消费者并发读同一收件箱
  会把同批消息各消费一遍;改成 `db.claim` 原子领取(领取与打 consumed_at 同一笔
  原子改写)。消息带 `_id`;`send(dedup_key=)` 投递幂等——同键未消费消息只投一次。
- **工具层**:`complete_task(task_id, owner=main_agent)`。

**追问链**
```
Q: 为什么不靠 MQ 重试去重?
→ A: 执行可靠性在本项目从不押在 broker 上(§1);幂等靠每类副作用的自然键:
     任务=(scope,id,status/owner),消息=(收件箱,dedup_key),产物=(session,artifact,node)。
Q: complete 幂等为什么重要?
→ A: 崩溃恢复会重放"最后一条未完成指令";若 complete 不幂等,重放会二次解锁下游,
     下游被认领两次。
Q: 单进程 asyncio 下这算不算过度设计?
→ A: 不算——语义是给多副本的,而租约/SKIP LOCKED 的先例(checkpoint)已在;
     内存替身同语义,离线测试钉住(22 项)。
```

## 续-D · 执行流水沉淀为技能(★ 本轮之眼,闭环的最后一块)

### D.1 三层流水处理(每层都在回答一个质量问题)

```
原始流水(全部 tool_calls + 结果)
  ↓ ① 净化 clean_steps:剔控制面调用(submit_plan/ask_user/render_status/
      read_node_history/协作面)、剔失败尝试(Error 形态结果)、
      紧邻同名同参纯重试合并取成功那次——「改了三次才成」的弯路不进技能
  ↓ ② 合并 merge_runs(会话级):跨执行同名工具只保留**最后一次**
      ——后一次代表用户修正后的做法;位置留在首次出现处,主流程顺序不乱;
      artifact_id 不参与指纹(分叉换作用域≠换动作)
  ↓ ③ 泛化 draft_body:流程正文讲**意图与参数推导**(NODE_INTENT 意图表 +
      易变参数改写为「按当次诉求确定」),具体值(素材 ID/时长/曲目)
      降级为文末「本次执行参数示例(仅参考)」附录
```

- **两档质量,功能永远可用**:有模型密钥走 LLM 润色(提示词第一原则是泛化);
  润色失败/输出过短/**流程段还焊着素材对象键** → 守卫判不合格,退回泛化模板。
- **双模式**:`POST /skills/from_run {run_id}` 单条;`{conversation_id}` 整会话
  (全部已完成执行按时间正序合并)。前端只暴露会话级入口——**一个会话一篇技能**,
  执行是账本单位(时间旅行用),不该同时是沉淀单位(这是迭代中真实返工过的一课)。
- 归属核对与 `_owned_run_row` 同口径(session_id 首段= user_id);别人的 run 按 404。

### D.2 设计上的三个"为什么"

1. **为什么泛化是第一原则?** 技能的读者是"下一个同类任务"。焊着 mat-0fe987 的
   流程是执行回放,不是技能;素材/时长/比例必须写成"按当次诉求确定"。
2. **为什么净化剔失败但不剔"不同参的重复"?** 失败重试是噪声;同名不同参的连发
   是真实的多次使用(如抓两条链接)——后者删了就丢了信息。
3. **为什么模板档永远保留?** 402 余额/无密钥/LLM 抽风都不该挡住"把经验记下来";
   质量可以分档,功能不能失效——与 credit_gate 的教训同源。

**追问链**
```
Q: 沉淀出的技能和预置技能怎么共存?
→ A: 同一张 skills 表、同一条渐进式注入链;沉淀技能 description 自动带原始诉求,
     规划轮按「何时使用」自行判断是否纳入流程。
Q: 为什么 LLM 润色的产出还要过守卫?
→ A: 润色的失败模式是"复述流水"(把 JSON 原文照抄)——恰好违背泛化原则;
     流程段出现 obj: 对象键即判不合格。生成的内容必须被校验,和自己写的代码一样。
Q: 用户改完保存走哪条路?
→ A: PUT /skills/{name}(upsert):弹窗表单直接编辑 frontmatter+正文,附件原样保留。
```

## 续-E · 工具库 UI 演进(五轮返工的教训)

最终形态:**双栏 master-detail**——左栏分类(工具/技能/MCP)常驻、选中加深;
右栏默认完整清单占满,点分类切子清单;每条目 = 名字 + ✎ + 单行截断简介;
✎ 弹窗统一增删改查(工具详情含参数表与"不可在线改写"边界说明;技能详情含
正文编辑;MCP 含启停/删除)。左栏可收起(» / «),抽屉可拖宽(300~720,
localStorage 记忆)。

**返工记录(每一轮都是真实反馈驱动的取舍)**:
```
平铺全列表 → 两级整屏替换(用户:一级也要常驻) → 手风琴上下展开
(用户:要左右分栏) → 左右双栏但右栏空半屏(用户:默认要占满)
→ 终版:双栏 + 默认完整清单。
按钮:名字下换行堆叠(用户:铅笔在名字后不换行、去掉复制钮)
→ 介绍占太高(用户:默认不展示) → 单行截断简介(终版)。
```
教训:**UI 的"对"不靠设计判断,靠用户看一眼;迭代速度比一次做对更值钱**——
每轮都是"改→build→截图→给用户看"的循环,五轮总共不到一小时。

## 续-F · 缺参数时的三层保障(与沉淀技能直接相关)

技能正文把参数写成"按当次诉求确定"之后,执行时缺参数靠什么?三层,层层兜底:

1. **模型主动弹窗**:`ask_user` 触发 → run 挂起 `awaiting_approval` → 选项卡
   (2~6 项+推荐+自定义)→ 作答以 role=user 进链续跑;挂起态落库,崩溃不丢;
2. **ask_gate 强制**:模型只在文字里问(不调 ask_user)→ 收尾时词面判据打回
   一次,强制弹窗;预算用尽附"本该弹窗"说明——缺条件一定会以弹窗形式问到;
3. **工具校验兜底**:schema required + 服务端真实性校验(material_ids 必须真实
   存在且属于该用户),编造参数当场被拒,模型收类型化错误自纠。

另两条相关路径:计划卡阶段缺参数以参数开关/自定义输入暴露在卡上;渲染前有确认门。
