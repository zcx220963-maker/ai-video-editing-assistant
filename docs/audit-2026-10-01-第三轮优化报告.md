## 0. 这一轮抓到的最要紧的一个

**工具参数被解析失败，一整轮白跑。**

真机现场：模型两次调用 `submit_plan`，服务端两次都回

```
Error: missing required params ['plans']
```

模型只能告诉用户「工具侧参数解析有问题」，用户拿不到计划卡。查 checkpoint 链里原始参数：

```
参数串长度 4252
'{' 出现 58 次，'}' 出现 59 次      ← 多了一个收尾括号
剥掉尾部 1 字后可解析（顶层键 ['plans']）
```

**内容完全正确**的计划，因为流式拼接多吐了一个 `}`，被 `json.loads` 判失败、
降级成 `{"_raw": "…"}`，于是工具层看到的是「没有 plans 参数」。

修法：只在**整体括号不平衡（多闭合）**时，试剥末尾 1~3 个字符再解析；
**少闭合（截断）不救**——那属于模型真传错了，硬修会把错误悄悄变成"成功"。
修的时候打 warning 留痕。

实测：

```
OK  正常 JSON 原样解析
OK  真机那个 case（多一个 }）被保守修复，内容一字不差
OK  多两个/三个 } 也能修
OK  截断（少括号）保持 _raw，不动它
OK  不是 JSON / JSON 数组 → 原样放进 _raw
```

## 1. 这一轮修完的清单

### 渲染代查期间租约过期 → 两条 run 抢同一部片子

一次长渲染代查可以持续几十分钟，而 checkpoint **租约只有 10 分钟**
（`CheckpointManager.lease_sec=600`）。原先代查循环期间不落盘、不续租，
多副本部署下别的实例会判定「租约过期」把这条 run 抢走——**同一部片子被渲两遍**。

修法：代查循环里每 120 秒（`_RENDER_BEAT_SEC`）`save_progress` 一次，
顺带续租并把当前消息链落一次盘（中途被 kill 时恢复点不退回代查之前）。

### 素材可见性过滤：全表扫 + 每行一次会话查询

```python
return [r for r in rows if await self._visible(r, user_id, conv_id)]
#                              ^^^^^ 每行撞到「不是本人所有」就再查一次 conversations
```

这是 `search_media`（剪辑链**第一步**）、`/materials`、`/bgm` 的共同入口，
素材越多查询越多。

修法：把「这个会话是不是我的」提到循环外算一次，行内判定退化成纯内存比较；
判据（本人所有 / 落在本人拥有的会话里）一字未改。

实测：60 条别人的素材 + 1 条自己的 → **1 次存储调用**（原实现 ≥60 次）。

### seq 分配是 O(n²)（两个引擎各有一处）

`db.max()` 的实现是「`select` 全表 + Python `max`」，而它每追加一条消息就调用一次
（分配会话内 seq）→ 整条会话 O(n²)。真机表现为「聊久了明显变卡」。

修法分两层：

1. **PG 侧**：新增 `max_value()` 把聚合下推到 SQL（`SELECT MAX(col)`），不再搬全表。
2. **内存侧**：`max_value` 仍是线性扫描，于是实测 600 条要 111ms。进一步发现真正的
   大头在 `_check_unique`——它给**每个**唯一约束都线性扫全表，所以「插第 n 行」是 O(n)。
   PG 靠唯一索引是 O(log n)，这个坑只落在内存引擎上（离线测试、单机演示、memory 后端全吃它）。
   改成给每个约束维护键集合、增删改时增量维护。

实测（写 100 / 600 条消息）：

| | 100 条 | 600 条 | 单条耗时比 |
|---|---|---|---|
| 修复前 | 13ms | **997ms** | 6.1x（线性膨胀） |
| 仅下推 max | 1.4ms | 9.7ms（insert） | — |
| 再加唯一索引 + max 索引 | 3ms | **20ms** | **1.03x（持平）** |

`{` 那 997ms 是 `insert`，其中主要是 `_check_unique`。

### seq 撞号：并发追加会撞唯一约束

`(conv_id, seq)` 与 `(run_id, seq)` 都是唯一键，而取号是「先读 max 再插」。
两条路径同时驱动同一条 run 时（启动恢复 + 用户此时发消息触发的续跑；
或 `/runs/{id}/resume` 连点两次）会算出同一个 seq，后插的撞约束失败。

修法：撞号就重读 max 再试（最多 5 次）。重试是安全的——append 是「写下一个一致点」
的幂等追加语义，不是「写第 N 个」。顺手把归属校验提到取号之前（越权不必浪费一次取号）。

实测（20 条消息 / 15 个一致点全部并发写同一会话与同一 run）：

```
消息：成功 20 / 失败 0；seq 序列 1..20 连续，20 条内容各不相同
一致点：成功 15 / 失败 0；seq 序列 0..14 连续
```

### `/timelines*` 在 memory 后端必定 500

这几个端点直接调 `storage.db._run("… extract(epoch from updated_at) … CAST(:payload AS jsonb) …")`，
而 `_run` 只定义在 `PgDatastore` 上。`--storage memory`（离线演示、单机跑、测试）下
一律 `AttributeError: 'MemoryDatastore' object has no attribute '_run'`。

修法：新增 `TimelinesRepo` 走通用 repo；`updated_at → epoch` 的转换从 SQL 挪到 Python
（PG 与内存都是 datetime，都能 `.timestamp()`）。`/latest_timeline` 同样从 `_run` 改成 `db.select`。

实测（真 TestClient + memory 存储，20 条断言全过）：空列表 200、保存/列表/取回/删除、
**越权按 id 读回 404 且看不到别人的列表**、`video_url` 为 null 时保留旧值（原 COALESCE 语义）、
`/latest_timeline` 无产物回 404 而不是 500。

### 任务板 N+1

`_with_open_deps` 每条任务都自己 `select` 一次「已完成集合」；`_closure` 每访问一个节点
调一次 `get()`，而 `get()` 内部又查一次已完成集合——每节点两次查询。

修法：一次算好已完成集合向下传；闭包先把本 scope 任务读成 `id→行` 再纯内存 BFS。

### 子 Agent：IDLE 只有 0.15 秒 + 抢任务失败静默死掉

1. **IDLE 窗口**：默认 `loop_times=3 × poll_interval=0.05` = **总共 0.15 秒**。
   一轮 WORK 刚结束，0.15 秒内没新任务就 SHUTDOWN——「常驻复用、像线程池」名存实亡，
   每个任务都要重建子 Agent。改成模块级默认窗口（可注入）：
   生产给常驻窗口，生命周期测试给短窗口。
2. **抢任务失败会杀死协程**：`await self.task_manager.claim(...)` 在「已被他人抢先认领」时
   抛 `TaskError`，此处不接 → 异常冒到 `run()` → 协程死掉，而 `subagents` 表那行还停在
   `idle`，看起来「就绪」其实已经没了。多个子 Agent 并发抢同一批任务时命中率很高。
   改成接住 `TaskError` 继续轮询（这一拍不算醒，不是死）。

### `start.bat` 的 `--no-resume`

带上它，主服务启动会把库里所有 `running/failed` 直接标成 `failed`——**关掉崩溃恢复**。
改成不加，并修掉另一个坑：原脚本用 `python -m storyline_server.server`，
那会因为相对导入拿不到包而**起不来**（`storyline_err.log` 里那句
`No module named storyline_server.__main__` 就是这类写法留下的）。改用包内启动器
`run_storyline.py`，日志重定向到 `.storyline/storyline.log`。

### 提示词搬出 `.py` + 接上 Bootstrap（这一轮的结构性改动）

**问题**：项目对外说「LLM 驱动 + 提示词和 skill 动态加载」，实测只有工具与技能是动态的；
系统提示词与 5 类纠错 nudge 全部硬编码在 `.py` 里，改一句话要动代码、走评审与发布。
`ContextBuilder` 其实早就实现了读磁盘的 Bootstrap 机制（`bootstrap_dir`），
但生产装配里**那个参数从来没传过**——口子一直空着。

**做法**（有意划边界）：

- 新增 `agent_framework/prompts.py`：`PromptLibrary` 按名读 `prompts/*.md`，带 mtime 缓存。
- 新增 `prompts/` 目录共 6 份：`system_prompt.md` + 5 条纠错说明。
- `build_prompt_library(None)` **默认接仓库自带的 `prompts/`**——让「搬到磁盘」默认生效，
  而不是又一个要记得打开的开关（Bootstrap 当年就是死在这一点上）。
- **只搬「整段、可独立成文」的文本**。规划轮段**没搬**：它是几十行按条件拼装、
  中间插节点白名单与参数事实，正确性依赖代码同时维护的数据；把拼装逻辑一起搬进模板，
  只会把「改文案」变成「改模板语言 + 调试渲染」。先让「改一句话」不再需要改代码。
- 占位符替换**只换明确给出的键**，其余原样保留。提示词里天然有 `{"plans": [...]}`、
  `{clip, start, end}` 这类 JSON 片段，按 `str.format_map` 会当占位符直接 KeyError 或吃字符。
- 文件缺失逐段回落到内联默认值 → **行为等价**，增量迁移安全。

启动日志现在会自报来源（以前没人能判断提示词来自哪）：

```
[startup] 提示词库已接线：6 份来自 …\prompts（系统提示 + 纠错说明，改文案不必动代码）
```

实测（20 条断言全过）：搬运无损（文件内容与内联默认值一致）、替换语义正确
（JSON 示例不被误吃、未知键原样保留）、缺目录逐段回落、显式 `False` 可关闭、
`_refresh_prompt_texts` 确实把 agent 的提示换成了磁盘版本、**改文件 + reload 即生效且指纹随之变化**。

## 4. 仍然没做的（诚实清单）

到这一轮为止，前面两轮列的「还没做」基本清空了。剩下的是**更大范围的工程改造**，
不是缺陷：

1. **规划轮段仍在 `.py` 里拼装**（见上文边界说明）。要真搬出去，得先把它依赖的
   数据（节点白名单、开关枚举、会话历史）定义成模板变量契约，这是独立一项工作。
2. **`plan_gate.py` 1356 行 6 种职责、`_drive` 169 行 god method**——拆解会牵动大量
   既有断言，建议单独一轮做，且要先把 `ctx.extras` 里那 7 个「不进 checkpoint」的临时键
   收敛成显式状态（那正是 resume 丢对账的根因）。
   ——**已按这条建议的顺序做完**（先收敛状态、再拆两处）：2026-10-02，见
   `audit-2026-10-01-缺陷修复记录.md`「结构性改造 3」与「结构性改造 1+2」两节。
3. **多副本广播时没挂 WS 的会话帧不入缓冲**（`broadcast.py`）。单副本无碍。
4. **连接池固定 5 条、无 overflow / pre_ping**（`.env PG_POOL_SIZE=5`），
   长任务与 HTTP handler 共享。数据量大时应调大并加 `pool_pre_ping`。
   ——**已做**（2026-10-02）：`PG_POOL_MAX_OVERFLOW` / `PG_POOL_PRE_PING` /
   `PG_POOL_RECYCLE_SEC` 三条可选参数已接进 `PgDatastore` 与 `build_storage`，见
   `audit-2026-10-01-缺陷修复记录.md`「结构性改造 6+7」。
5. **checkpoint_entries / messages 的 seq 撞号已加重试**（见上文），
   但从根上消掉还要靠数据库序列或 `RETURNING`；当前重试已足够覆盖已知并发路径。
6. **`.env` 里 `DEEPSEEK_API_KEY` / `SILICONFLOW_API_KEY` 没人读**——代码只认
   `OPENAI_API_KEY` 与页面设置。要么改代码认这两个名字，要么从 `.env.example` 删掉，
   否则会让人以为填了就生效。
7. **`.runtime/legacy-credentials.txt` 存着明文 token**。建议删掉，并把
   `--emit-credentials` 的输出改到仓库外。
